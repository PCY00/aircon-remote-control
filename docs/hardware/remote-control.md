## 사진 기반 확인 결과

- 유형: LCD를 사용하는 상태형 에어컨 IR 리모컨
- 통신 방향: 리모컨에서 에어컨으로의 단방향 송신
- IR 송신부: `IR1`로 표기된 투명 5mm LED
- IR 구동부: `Q1` 트랜지스터와 주변 저항
- MCU: Sino Wealth `SH66P51F-AE031`
- PCB: `R51D/E(SH66P51F-044FR).D.20.YP2-1`
- PCB 버전 표기: `V1.8`, `2011.12.05`

`2011.12.05`는 PCB 설계 또는 리비전 날짜로 보이며 실제 제품 제조일로 확정하지 않는다.

## 실물 앞면에서 확인된 기능

LCD와 외장 인쇄에서 다음 기능을 직접 확인했다.

- 운전 모드 표시: `자동`, `냉방`, `제습`
- 희망 온도: ℃ 숫자 표시와 온도 내림·올림 버튼
- 풍량 표시: `송풍`, `강`, `중`, `약`
- 기본 제어: `운전선택`, `운전/정지`, `풍량선택`
- 풍향: `풍향선택`, `풍향고정`
- 특수 기능: `경제운전`, `LED`, `쾌속냉방`
- 예약: `예약선택`, `예약취소`
- 핀홀: `리셋`, `잠금`

사진의 LCD는 `18℃`를 표시하며 좌측 화살표는 냉방, 우측 화살표는 강풍 위치다. 사용자가 이 사진이 첫 온도 올림 캡처 직후 상태 그대로임을 확인했으므로 `temp-up-test-01`의 최종 상태를 `냉방 18℃ / 강풍`으로 확정했다. 사진만으로 전원과 풍향 상태는 판독하지 않는다.

## 점퍼 설정 추정

PCB 후면의 설정표와 전면 부품 실장 상태를 대조하면 냉방 전용, 섭씨 표시, Protection Normal, Mid-wind 사용, Timer ON/OFF 방식으로 보인다. 실물 LCD에 섭씨가 표시되고 운전 모드 목록에 난방이 없으며 예약선택·취소 버튼이 존재하므로 냉방 전용·섭씨·타이머 구성 추정을 추가로 뒷받침한다. Protection과 Mid-wind 설정의 정확한 동작은 신호 비교로 검증해야 한다.

## 첫 원시 신호 측정

HW-477 수신기를 GPIO17에 연결하고 온도 올림 버튼을 한 번 눌러 첫 신호를 측정했다.

- 총 타이밍 토큰: 200개
- 데이터 펄스 중앙값: 약 546µs
- 짧은 공백 중앙값: 약 517µs
- 긴 공백 중앙값: 약 1611µs
- 시작부: 약 4.3ms pulse / 4.3ms space
- 프레임: 같은 48비트 프레임 2회
- MSB 우선 관측 바이트: `b2 4d 3f c0 10 ef`

각 두 바이트가 보수 관계인 패턴이 관찰됐지만 프로토콜명, 비트 순서와 필드 의미는 아직 확정하지 않는다. 원시 신호와 메타데이터는 `signals/remote-16214-15597/`에 보존했다.

### 풍량 상태 비교

냉방 18℃에서 풍량선택을 순환하며 다음 관측 바이트를 얻었다.

| LCD 풍량 | 3·4번째 관측 바이트 |
|---|---|
| 화살표 없음(자동) | `bf 40` |
| 약 | `9f 60` |
| 중 | `5f a0` |
| 강 | `3f c0` |

각 값은 뒤 바이트가 앞 바이트의 보수이며 동일 신호가 한 번의 버튼 입력에서 두 프레임 반복됐다. Carrier CS-A Series 설명서는 풍량 순서를 약 → 중 → 강 → 자동으로 명시하므로 화살표 없음 상태를 자동풍량으로 확정한다.

### 온도 상태 비교

무표시 풍량 상태를 고정하고 온도를 연속 측정해 다음 값을 얻었다.

| 온도 | `온도-17` | 그레이 코드 | 5·6번째 관측 바이트 |
|---|---:|---:|---|
| 17℃ | 0 | `0` | `00 ff` |
| 18℃ | 1 | `1` | `10 ef` |
| 19℃ | 2 | `3` | `30 cf` |
| 20℃ | 3 | `2` | `20 df` |

따라서 3·4번째 바이트는 풍량, 5·6번째 바이트는 온도이며 각 짝의 뒤 바이트는 앞 바이트의 비트 보수다. 5번째 바이트의 상위 4비트는 `(설정 온도-17)`을 이진 그레이 코드로 변환한 값과 일치한다. 17–19℃로 세운 규칙이 20℃의 실측값 `20 df`를 정확히 예측했으므로 온도 인코딩 규칙을 확정한다. 아직 확인할 것은 리모컨의 실제 최고 온도와 다른 운전 모드에서도 같은 온도 필드를 사용하는지 여부다.

### 운전 모드 상태 비교

사용자가 17℃·강풍을 기준으로 운전선택을 네 번 눌러 제습 → 송풍 → 자동 → 냉방 순서를 확인했다.

| 운전 모드 | 관측 바이트 |
|---|---|
| 제습 | `b2 4d 1f e0 04 fb` |
| 송풍 | `b2 4d 3f c0 e4 1b` |
| 자동 | `b2 4d 1f e0 08 f7` |
| 냉방 | `b2 4d 3f c0 00 ff` |

각 패킷은 같은 48비트 프레임을 두 번 보내며 모든 바이트쌍은 보수 관계를 유지한다. 냉방·제습·자동은 5번째 바이트 하위 니블이 각각 `0`, `4`, `8`로 분리된다. 다만 제습·자동에서는 3·4번째 바이트가 `1f/e0`, 송풍·냉방에서는 `3f/c0`로 나타났고 송풍은 5·6번째 바이트도 `e4/1b`라는 특수값을 쓴다. 따라서 모드가 하나의 독립 니블에만 들어간다고 아직 단정하지 않고, 모드별 풍량 제약이나 고정 상태가 패킷에 함께 반영되는지 추가 비교한다.

### 전원 OFF·ON 상태 비교

냉방 17℃·강풍에서 운전/정지를 두 번 눌러 OFF와 재시작 신호를 연속 수집했다.

| 동작 | 관측 바이트 |
|---|---|
| OFF | `b2 4d 7b 84 e0 1f` |
| ON(냉방 17℃·강풍) | `b2 4d 3f c0 00 ff` |

OFF는 별도의 명시적 상태 패킷이며, ON은 앞서 얻은 냉방 17℃·강풍 패킷과 완전히 같다. 따라서 API에서는 불확실한 단일 토글보다 명시적 OFF 패킷과 원하는 운전 상태 패킷을 분리해 사용할 수 있다. 서로 다른 이전 설정에서 OFF 패킷이 동일한지는 나중에 한 번 더 비교한다.

### 경제운전·쾌속냉방 1차 비교

냉방 17℃·강풍에서 경제운전을 두 번, 이어 쾌속냉방을 두 번 눌러 연속 수집했다. 경제운전 첫 입력 후 강풍 화살표가 사라졌지만 냉방·17℃ 표시는 유지됐고 별도 옵션 아이콘은 나타나지 않았다. 두 번째 경제운전에는 추가 표시 변화가 없었다. 이 상태에서 풍량선택을 누르면 약풍부터 시작한다는 사용자 관찰도 있어 무표시를 자동풍량 계열로 보는 근거가 강화됐다. 쾌속냉방은 두 번 모두 LCD에 아무 변화가 없었다.

- 경제운전 1차 입력: `b2 4d e0 1f 03 fc` 1회 뒤 `b2 4d bf 40 00 ff` 2회
- 경제운전 2차 입력: `b2 4d bf 40 00 ff` 2회
- 쾌속냉방 1차 입력: `b5 4a f5 0a a2 5d` 2회
- 쾌속냉방 2차 입력: `b5 4a f5 0a a2 5d` 2회

경제운전 첫 입력은 이 프로젝트에서 처음 관찰한 3프레임 메시지다. 첫 특수 프레임은 경제운전 동작 명령, 뒤의 두 프레임은 변경 결과인 냉방 17℃·무표시 풍량 상태로 해석할 수 있다. 이미 무표시 상태에서 다시 누르면 현재 상태 프레임만 전송됐다. 쾌속냉방은 기존 `b2/4d` 시작과 다른 `b5/4a` 시작을 사용하지만 세 바이트쌍 모두 보수 관계다. 두 번 모두 같은 패킷이고 LCD 상태를 바꾸지 않으므로 리모컨 관점에서는 ON/OFF 상태가 없는 즉시 실행 명령으로 분류한다.

### LED·풍향고정 명령 비교

냉방 17℃·무표시 풍량 상태에서 LED를 두 번, 풍향고정을 두 번 눌렀다. 같은 버튼의 두 입력은 각각 동일한 값을 보냈다.

| 버튼 | 관측 바이트 | 한 번 누를 때 프레임 수 |
|---|---|---:|
| LED | `b5 4a f5 0a a5 5a` | 2 |
| 풍향고정 | `b2 4d 0f f0 e0 1f` | 1 |

두 버튼 모두 리모컨이 ON/OFF 상태를 패킷에 구분해 보내지 않는 즉시 명령형 후보다. LED는 쾌속냉방과 같은 `b5/4a f5/0a` 명령 계열이고 마지막 바이트쌍으로 기능이 구분된다. 사용자는 이 버튼이 에어컨 본체에 있는 표시 LED를 토글하는 기능으로 추정했다. 같은 패킷을 반복하고 리모컨 LCD가 상태를 보존하지 않는 구조와 잘 맞지만, 본체 앞에서 실제 LED 변화를 확인하기 전까지 사용자 추정으로 표시한다. 풍향고정은 현재까지 관찰한 일반 버튼 중 유일하게 한 번의 48비트 프레임만 보냈다.

### 풍향선택 스윙 토글

풍향선택을 네 번 연속 눌렀고 모든 입력이 `b2 4d 6b 94 e0 1f`를 동일한 두 프레임으로 보냈다. 사용자는 첫 입력에서 에어컨 풍향 날개가 계속 움직이기 시작하고 두 번째 입력에서 현재 위치에 멈추는 것을 확인했다. 따라서 풍향선택은 리모컨이 상태를 기억하는 ON/OFF 패킷이 아니라, 본체가 현재 상태를 기준으로 스윙 시작과 정지를 번갈아 처리하는 동일 토글 명령이다. 세 번째와 네 번째 입력도 같은 명령임은 측정했지만 본체 동작은 별도 문장으로 확인받지 않았다.

### 제조사 설명서로 추가 확인한 범위

사용자가 제공한 Carrier CS-A Series 설명서의 리모컨 관련 PDF 21–26쪽을 텍스트 추출과 페이지 렌더링으로 함께 확인했다.

- 운전선택 순환: 자동 → 냉방 → 제습 → 송풍
- 풍량 순환: 약 → 중 → 강 → 자동
- 희망온도: 17–30℃
- 풍향선택: 연속 스윙 시작과 현재 위치 정지를 같은 버튼으로 전환
- 예약선택: TIMER ON 켜짐 예약
- 예약취소: TIMER OFF 꺼짐 예약
- 예약 시간: 0.5–10h는 0.5h 단위, 이후 24h까지 1h 단위, 0.0h는 취소

상세 근거와 Raspberry Pi 예약 구현 결정은 [설명서 확인 기록](../references/carrier-cs-a-series-manual.md)에 정리했다.

### TIMER ON 1.5h 커밋 패킷

TIMER ON 1.0h에서 예약선택을 한 번 눌러 1.5h로 만든 뒤 약 1초 기다리자 `b2 4d 3f c0 03 05`가 두 프레임 전송됐다. 예약 숫자를 편집하는 동안에는 IR이 없고 TIMER 표시가 확정되는 순간 패킷이 나온다. `03`은 0.5시간 세 단계와 일치하며 마지막 바이트쌍은 일반 상태의 보수 규칙을 따르지 않는다. 추가 TIMER ON/OFF 값으로 시간과 종류 필드를 분리한다.

## 아직 확정하지 않은 항목

- IR 반송파 주파수
- 체크섬 또는 상태 바이트 구조
- 정확한 에어컨 본체와 리모컨 외장 모델명
- 모드·풍량·풍향·옵션별 비트 필드
