# Step 2 — IR 수신·패킷 복제 구현 계획

> 2026-08-29 단계 정정: Step 2는 수신·분석·저장까지만 다룬다. UI는 Step 3,
> 송신 회로와 실제 IR 제어는 Step 4로 분리했다. 이 문서 아래쪽의 송신 항목은
> 앞선 조사 기록으로 유지하되 Step 2 완료 조건에는 포함하지 않는다.

## 목표와 범위

기존 에어컨 리모컨의 IR 신호를 Raspberry Pi에서 반복 가능하게 캡처·분석·저장하고,
원본 파형과 향후 재생 가능한 형식을 함께 보존한다.

Step 2에는 다음이 포함된다.

- 보유 IR 관련 모듈 식별
- 안전한 수신 배선 설계
- Linux IR 장치 구성
- 리모컨 원시 신호 캡처와 분석
- Python IR 수신 계층, 리모컨 프로필과 신호 저장소
- 실제 하드웨어를 호출하는 수신 API

다음은 Step 2 범위가 아니다.

- 최종 사용자 UI(Step 3)
- IR 송신 회로·송신 백엔드·실제 에어컨 제어(Step 4)
- 일반 인터넷 공개 또는 공유기 포트포워딩
- 실제 상태를 확인할 수 없는 에어컨 상태를 확정값으로 표시하는 기능
- 신호 캡처 전에 추측한 GPIO 배선

## 전체 흐름

```text
[학습 경로]
기존 리모컨 → IR 수신기 → Linux IR 장치 → 캡처 도구 → 원시 신호·메타데이터

[제어 경로]
FastAPI → 명령 검증 → IR 서비스 → 저장된 신호/인코더 → IR 송신기 → 에어컨
```

IR 수신기는 기존 리모컨을 학습하는 장치이고, 실제 에어컨 제어에는 IR 송신기와 안전한 LED 구동 회로가 필요하다.

수신기는 학습 단계의 임시 장비다. 필요한 원시 신호를 모두 캡처하고 송신 재현성을 검증한 뒤에는 최종 운영 장치에서 제거할 수 있다. 기존 리모컨 신호를 계속 관측해 추정 상태를 보정하려는 경우에만 선택적으로 유지한다.

## 2.1 보유 장비 식별

필요 자료:

- 각 모듈의 앞면과 뒷면 사진
- 보드에 인쇄된 모델명, 핀 이름과 전압 표기
- 센서 또는 LED 부품의 근접 사진
- 모듈 개수와 함께 보유한 저항·트랜지스터·브레드보드·점퍼선 목록

판별 항목:

- IR 수신기, IR 송신기, 장애물 감지기 또는 다른 종류의 센서인지
- 동작 전압과 출력 전압
- 핀 배열
- 38kHz 복조 수신기인지 원시 광센서인지
- 송신 LED에 트랜지스터 구동부와 전류 제한 저항이 포함됐는지

완료 조건:

- 사진이나 데이터시트 근거로 각 모듈의 역할·핀·전압을 확정한다.
- 확정 전에는 Raspberry Pi GPIO에 연결하지 않는다.

## 2.2 배선과 GPIO 설계

- Raspberry Pi GPIO는 3.3V 로직을 기준으로 한다.
- 수신 모듈 출력이 5V일 가능성이 있으면 GPIO에 직접 연결하지 않는다.
- IR LED는 GPIO에서 직접 구동하지 않고 저항과 트랜지스터 또는 MOSFET을 사용한다.
- BCM 번호와 물리 핀 번호를 모두 기록한다.
- 배선은 Pi 전원을 끈 상태에서 변경한다.
- 송신 LED의 방향, 저항값, 예상 전류와 구동 전압을 도식으로 남긴다.

완료 조건:

- 수신·송신 회로도와 핀 표가 문서화된다.
- 전원 투입 전 단락·극성·전압을 검토한다.

## 2.3 Linux IR 장치 구성

예상 경로는 Raspberry Pi 커널의 `gpio-ir` 수신 오버레이와 `gpio-ir-tx` 송신 오버레이, `ir-ctl` 도구를 이용하는 것이다. 실제 모듈과 핀이 확정된 후 적용한다.

이 단계에서 예상되는 Pi 변경:

- 부팅 설정 백업
- IR 수신·송신 오버레이 추가
- 필요 패키지 확인 또는 설치
- 재부팅
- `/dev/lirc*`와 송수신 기능 확인

완료 조건:

- 수신 장치와 송신 장치가 예상한 GPIO에 연결된다.
- `ir-ctl`이 장치 기능을 읽고 수신·송신 가능 여부를 구분한다.
- 설정 복구 절차가 문서화된다.

Pi 설정 변경과 재부팅은 별도 계획을 제시하고 사용자 승인을 받은 뒤 수행한다.

## 2.4 기존 리모컨 신호 캡처

전체 기능 수집 순서와 상태별 반복 횟수는 [IR 신호 전체 수집 매트릭스](ir-signal-capture-matrix.md)를 따른다. 에어컨 리모컨이 버튼 코드가 아니라 전체 상태를 전송할 가능성을 고려해, 한 필드씩 바꾼 차이 분석을 우선한다.

최소 캡처 세트:

- 명시적 전원 OFF
- 냉방 ON, 24℃, 자동 풍량
- 냉방 ON, 25℃, 자동 풍량
- 동일 상태에서 같은 버튼을 다시 누른 신호

각 상태는 최소 3회 캡처하고 다음 정보를 기록한다.

- 리모컨·에어컨 식별 정보
- LCD에 표시된 전체 상태
- 누른 버튼
- 수신기와 리모컨 사이 거리·각도
- 반송파 설정
- pulse/space 타이밍과 반복 구간
- 캡처 성공·실패와 주변광 조건

완료 조건:

- 같은 상태의 반복 캡처가 비교 가능한 형태로 저장된다.
- 프레임 시작·끝과 반복 패턴을 구분한다.
- 추정값과 측정값을 명확히 나눈다.

## 2.5 신호 저장 형식

원시 신호는 코드와 분리해 다음 구조로 관리하는 것을 기본안으로 한다.

```text
signals/
  <remote-id>/
    raw/
      power-off-01.ir
      cool-24-auto-01.ir
    metadata/
      power-off-01.json
      cool-24-auto-01.json
```

`.ir`에는 `ir-ctl`로 재생 가능한 pulse/space 데이터를, `.json`에는 모델·상태·캡처 조건·검증 결과를 기록한다. 실제 도구 출력 확인 후 포맷을 최종 확정한다.

## 2.6 제한된 IR 재생 검증

검증 순서:

1. 카메라 등으로 IR LED 발광 여부 확인
2. 에어컨을 향하지 않은 상태에서 짧은 송신 시험
3. 명시적 OFF 신호를 에어컨에 제한된 횟수로 시험
4. 냉방 24℃ 자동 풍량 프리셋 시험
5. 각 신호를 최소 3회 반복해 성공률 기록

완료 조건:

- OFF와 냉방 프리셋 하나 이상이 반복적으로 동작한다.
- 실패한 송신도 거리·각도·반복 횟수와 함께 기록한다.
- 송신 LED나 구동 소자의 과열이 없다.

## 2.7 Python IR 계층

애플리케이션 코드는 GPIO나 명령줄 도구를 API 라우터에서 직접 호출하지 않는다.

예상 구성:

```text
app/ir/
  models.py       # 명령과 상태 모델
  backend.py      # 송수신 인터페이스
  irctl.py        # Raspberry Pi ir-ctl 구현
  mock.py         # PC 테스트용 가짜 구현
  store.py        # 신호와 메타데이터 로딩
```

필수 동작:

- 지원하지 않는 명령 거부
- 동시에 두 신호를 보내지 않도록 직렬화
- 송신 시간·결과·오류 기록
- 로컬 테스트에서는 실제 GPIO 없이 mock backend 사용
- Pi에서는 명시적으로 real backend 선택

## 2.8 API 계약

초기 후보:

- `GET /api/v1/capabilities`: 실제 검증된 모드·온도·풍량 목록
- `GET /api/v1/state`: Pi가 마지막으로 전송한 추정 상태
- `POST /api/v1/commands`: 결과 상태가 명확한 제어 명령
- `GET /api/v1/commands/{id}`: 송신 결과 조회

명령 예시:

```json
{
  "power": "on",
  "mode": "cool",
  "temperature_c": 24,
  "fan": "auto"
}
```

OFF 명령 예시:

```json
{
  "power": "off"
}
```

`POWER_TOGGLE` 대신 결과가 명확한 상태 명령을 사용한다. 실제 API 스키마는 캡처로 확인된 기능만 노출한다.

## 상태의 한계

이 에어컨 통신은 단방향 IR로 보이며 Pi는 에어컨의 실제 수신·동작을 확인할 수 없다. 따라서 `/state`는 다음을 구분해야 한다.

- `last_commanded`: Pi가 마지막으로 전송한 상태
- `confirmed`: 실제 에어컨 피드백이 없으므로 기본적으로 false
- `source`: API, 기존 리모컨 관측 또는 복구된 저장 상태

기존 리모컨을 별도로 사용하거나 에어컨 전원이 차단되면 Pi의 추정 상태와 실제 상태가 달라질 수 있다.

## 정정된 Step 2 완료 기준

- 사용한 수신 모듈과 GPIO 핀이 문서화돼 있다.
- 원시 신호와 메타데이터가 코드와 분리돼 보존된다.
- 범용 파서와 캐리어 전용 프로필이 분리돼 다른 리모컨을 추가할 수 있다.
- 로컬 mock 테스트와 Pi `ir-ctl` 수신 백엔드 검증이 모두 통과한다.
- API가 한 번에 하나의 원샷 수신만 실행하고 성공·시간초과·취소·실패를 구분한다.
- 실패·복구 과정과 측정 조건이 블로그 자료로 기록된다.

Step 2를 Pi에서 검증한 뒤 Step 3 UI를 진행한다. 송신 완료 조건은 Step 4에서 별도로 정의한다.
