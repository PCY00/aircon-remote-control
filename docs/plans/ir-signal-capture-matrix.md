# IR 신호 전체 수집 매트릭스

## 목표

실물 리모컨이 제공하는 일반 제어 기능을 빠짐없이 Raspberry Pi에서 재현한다. 에어컨 리모컨은 버튼별 고정 코드보다 현재 설정 전체를 담은 상태 패킷을 보낼 가능성이 있으므로, 모든 조합을 원시 파일로 무작정 저장하지 않고 다음 순서로 진행한다.

1. 한 번에 한 상태 요소만 바꿔 원시 신호를 수집한다.
2. 반복 캡처로 동일 상태의 신호가 재현되는지 확인한다.
3. 차이 분석으로 모드·온도·풍량·풍향·옵션·체크섬 필드를 찾는다.
4. 패킷 인코더로 유효 조합을 생성하고 대표 조합을 실제 기기에서 검증한다.
5. 해독할 수 없는 기능만 검증된 원시 신호 프리셋으로 보관한다.

첫 `temp-up-test-01`은 수신 파이프라인 확인용으로 시작했지만, 사용자가 이후 제공한 LCD 사진이 캡처 직후 상태 그대로임을 확인했다. 따라서 최종 상태 `냉방 18℃ / 강풍`은 확정했으며, 누르기 전 상태와 전원·풍향 상태만 미확정으로 남긴다.

## 실물에서 확인된 기능

| 구분 | 표시 또는 버튼 |
|---|---|
| 운전 모드 | 자동, 냉방, 제습 |
| 희망 온도 | ℃ 숫자 표시, 온도 내림·올림 |
| 풍량 | 송풍(자동으로 보임), 강, 중, 약 |
| 전원 | 운전/정지 |
| 모드 | 운전선택 |
| 풍량 | 풍량선택 |
| 풍향 | 풍향선택, 풍향고정 |
| 특수 기능 | 경제운전, LED, 쾌속냉방 |
| 예약 | 예약선택, 예약취소 |
| 핀홀 | 리셋, 잠금 |

리셋은 일반 원격 제어 신호로 취급하지 않는다. 잠금 핀홀은 LCD/버튼 잠금 기능일 가능성이 높으므로 IR을 실제로 송신하는지 먼저 관찰한 뒤 수집 여부를 정한다.

## 공통 캡처 규칙

- 리모컨과 HW-477 거리는 5–10cm, 각도는 정면으로 유지한다.
- 에어컨이 의도치 않게 동작하지 않도록 리모컨을 에어컨 반대 방향으로 향한다.
- 캡처마다 누르기 전 상태, 누른 버튼, 누른 후 LCD 전체 상태를 기록한다.
- 기준 상태는 가능한 경우 `냉방 24℃ / 자동 풍량 / 풍향 OFF 또는 고정 / 특수 기능 OFF`로 맞춘다.
- 하나의 필드만 바꾸고 나머지 상태는 고정한다.
- 기준 상태와 핵심 운영 상태는 최소 3회, 필드 탐색 상태는 최소 2회 캡처한다.
- 길게 누르지 않고 한 번 짧게 누른다. 길게 누르기 동작이 별도로 있으면 따로 기록한다.
- 주변광·거리·각도가 달라졌거나 신호가 끊기면 실패 캡처도 삭제하지 않고 원인을 기록한다.

## 1차 필수 수집 세트

| 그룹 | 바꿀 값 | 고정할 값 | 반복 |
|---|---|---|---:|
| 기준 상태 | 냉방 24℃, 자동 풍량, 풍향 고정 | 특수 기능 OFF | 3회 |
| 명시적 OFF | 기준 상태에서 운전/정지 | 이전 상태 기록 | 3회 |
| OFF 비교 | 서로 다른 모드·온도에서 OFF | 이전 상태만 변경 | 각 2회 |
| 온도 | 리모컨에서 가능한 모든 ℃ 값 | 냉방, 자동 풍량, 풍향 고정 | 각 2회 |
| 풍량 | 송풍/자동·강·중·약 | 냉방 24℃, 풍향 고정 | 각 2회 |
| 운전 모드 | 자동·냉방·제습 | 각 모드가 허용하는 기본값 | 각 3회 |
| 풍향선택 | 표시되는 모든 단계 | 냉방 24℃, 자동 풍량 | 각 2회 |
| 풍향고정 | 고정 전·후 | 냉방 24℃, 자동 풍량 | 각 2회 |

## 2차 옵션 수집 세트

| 기능 | 캡처 방식 |
|---|---|
| 경제운전 | 기준 상태에서 ON·OFF 각각 2회 |
| LED | ON·OFF 각각 2회 |
| 쾌속냉방 | 기준 상태에서 ON·해제 각각 2회 |
| 예약선택 | TIMER ON 1.5h 커밋 패킷 1건을 연구 자료로 보존. 제품 기능은 Pi 서버 스케줄러로 구현 |
| 예약취소 | 추가 TIMER OFF 패킷 해독은 필수 범위에서 제외. 예약 시각에 명시적 OFF 패킷 전송 |
| 잠금 | IR 송신 여부를 먼저 확인하고 송신할 때만 수집 |

## 상호작용 검증

필드 구조를 추정한 뒤 모든 조합을 실제로 캡처하지 않고 다음 경계 조합을 확인한다.

- 최저·최고 온도 × 최저·최고 풍량
- 자동·냉방·제습 × 각 모드에서 허용되는 온도·풍량 경계
- 풍향 동작·고정 × 기준 온도
- 경제운전 또는 쾌속냉방 상태에서 온도·모드 변경
- 서로 양립할 수 없는 옵션을 리모컨이 자동 해제하는지 여부
- OFF 패킷이 이전 모드·온도 정보를 포함하는지 여부

## 파일 구조와 필수 메타데이터

```text
signals/
  remote-16214-15597/
    raw/
      cool-24-auto-fixed-01.compact
      cool-24-auto-fixed-01.ir
    metadata/
      cool-24-auto-fixed-01.json
```

각 JSON에는 캡처 시각, 이전 상태, 누른 버튼, 최종 LCD 상태, 거리·각도, 반복 번호, 수신 명령, 프레임 수, pulse/space 통계, 반복 일치 여부와 원본 파일 경로를 기록한다. 프로토콜·필드·체크섬은 `확정`, `추정`, `미확정`을 구분한다.

## 완료 기준

- 실물 리모컨의 모든 일반 버튼이 목록화돼 있다.
- 각 독립 상태 값마다 최소 두 번 이상의 비교 가능한 캡처가 있다.
- OFF와 냉방 24℃ 자동 풍량 등 핵심 상태는 최소 세 번 일치한다.
- 온도·풍량·모드·풍향·옵션 필드와 체크섬을 생성할 수 있거나, 해독하지 못한 기능은 검증된 원시 프리셋으로 남아 있다.
- 생성한 경계 조합과 핵심 프리셋을 실제 에어컨에서 제한된 횟수로 검증했다.
- UI와 API에는 검증을 통과한 기능만 노출한다.

여기서 “모든 신호”는 리모컨이 제공하는 모든 유효 기능과 상태를 재현한다는 뜻이다. 온도 × 풍량 × 모드 × 풍향의 모든 조합을 각각 원시 파일로 저장한다는 뜻은 아니다. 구조 해독에 성공하면 조합은 코드로 생성하고, 실패한 부분만 원시 신호 라이브러리로 보완한다.

## 현재 해독 진행 상황

- 풍량 필드: 무표시(자동 후보)·약·중·강의 네 상태를 분리했다.
- 온도 필드: 17–20℃ 연속 실측으로 `(온도-17)`의 그레이 코드 규칙을 확정했다.
- 운전 모드: 제습·송풍·자동·냉방의 첫 연속 캡처를 완료했다. 모드별 풍량 제약과 반복성을 추가 확인한다.
- 옵션: 경제운전의 3프레임 구조와 쾌속냉방의 무상태 즉시 명령을 분리했다.
- 예약: TIMER ON 1.5h 커밋 패킷을 연구 자료로 확보했다. 추가 해독은 중단하고 Pi 서버 스케줄러를 제품 구현으로 확정했다.
- 남은 온도 작업: 실제 최고 온도 경계 확인과 생성 신호의 대표값·경계값 송신 검증이다.
