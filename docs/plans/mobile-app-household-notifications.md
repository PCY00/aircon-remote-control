# Android 앱·가구별 권한·FCM 알림 구조 제안

작성일: 2026-10-01
상태: **검토용 제안 — 구현·클라우드 생성·Pi 배포 전**

## 요구사항

- 동일한 APK를 여러 가구가 설치한다.
- 각 가구의 Raspberry Pi에는 소유자가 허용한 여러 사용자가 연결된다.
- 타 가구의 알림·센서 기록·제어 기능에 접근할 수 없어야 한다.
- 인터넷 연결과 Android 알림 허용 조건에서 외부에서도 알림을 받는다.
- 가족은 개별 계정을 사용하고, 소유자가 초대·권한 변경·접근 해제를 관리한다.

## 현재 로컬에서 확인한 출발점

- `app/events.py`의 EventHub는 센서·기기·자동화 이벤트를 메모리 큐와 SSE로 전달한다.
- `app/automations/service.py`에는 문 열림·에어컨 상태 기반 자동화 평가가 있다.
- 기존 이벤트 스트림은 영구 알림 발송 큐가 아니다. 프로세스 재시작 시 보존과
  발송 재시도·중복 방지·수신자 권한 검사는 별도로 구현해야 한다.
- 기존 Pi API의 포트 8001과 Tailscale 접근 정책을 유지한다.
- 이번 검토에서 원격 장비 점검·서비스 변경·실제 알림 검증은 수행하지 않았다.

## 권장 역할 분리

1. Raspberry Pi: 해당 집의 센서·IR 제어·자동화·로컬 기록을 담당한다.
2. 중앙 서비스: 사용자 인증, 집 소속과 역할, 허브 등록, 이벤트 수신,
   알림 수신 대상 선정과 FCM 발송을 담당한다.
3. Android 앱: 로그인, 집 등록·초대 수락, 알림 권한과 설치별 FCM 등록,
   허용된 집의 알림 이력 조회를 담당한다.
4. FCM: 중앙 서비스가 지정한 앱 설치 대상으로 푸시를 전달한다.
   가족 권한을 판단하는 주체로 사용하지 않는다.

Pi는 자신의 개별 자격 증명으로 중앙 서비스에 TLS 연결을 시작한다.
집 라우터의 포트포워딩이나 Pi API의 공용 인터넷 노출은 필요하지 않다.
FCM 발송용 서비스 계정 자격 증명은 중앙 서비스에만 보관한다.
같은 발송용 비밀 키를 판매할 모든 Pi 또는 APK에 넣지 않는다.

중앙 서비스 없는 Pi 직접 FCM 발송도 기술적으로 가능하지만, 제품화에서는
가구별 등록·초대·기기별 자격 증명·권한 해제와 발송 권한 관리 때문에 위 구조를 제안한다.
중앙 서비스 운영 비용과 장애 복구 책임은 추가된다.

## 데이터와 권한 경계

| 대상 | 의미 |
| --- | --- |
| Home | 가구를 구분하는 권한 경계 |
| Hub | 특정 Home에 연결된 Pi와 개별 기기 자격 증명 |
| User | 로그인으로 확인한 사용자 |
| Membership | Home–User 소속, 역할, 활성 상태 |
| AppInstallation | 사용자와 연결된 앱 설치별 푸시 수신 주소·갱신 시각 |
| Invitation | 특정 Home의 역할을 부여하는 만료·일회성 초대 |
| Event | Home·Hub·이벤트 ID·발생 시각·유효기간 |

한 사용자가 여러 Home에 가입하고 휴대폰 여러 대를 사용할 수 있도록 관계를 분리한다.
초기에는 Home당 Hub 한 대로 제한할 수 있다.
Home ID, Hub ID, FCM 수신 주소는 가족 소속을 증명하는 로그인 자격 증명이 아니다.

- 사용자 API는 검증한 로그인 사용자와 활성 Membership으로 접근을 판단한다.
- Hub 이벤트의 Home은 서버의 Hub 등록 관계에서 결정한다.
  Pi가 보낸 임의 Home ID로 발송 대상을 바꾸지 못하게 한다.
- 조회·제어·실시간 구독·발송·초대 등 모든 경로에 동일한 가구 경계를 적용한다.
- 발송 시점에 활성 소속·알림 권한·사용자별 알림 설정을 다시 확인한다.
- FCM topic 이름을 가구 접근 제어로 사용하지 않는다. 서버가 허용된 설치별
  수신 주소를 선택하여 발송한다.

역할 제안: Owner(집·허브·가족 관리), Member(조회·제어·알림),
Viewer(조회·알림). 알림 항목별 설정은 역할 권한과 별도로 둔다.

## 등록·초대·권한 해제

- 최초 등록: 로그인한 구매자가 QR의 기기 식별 정보를 읽고, 허브 화면에서
  발급한 짧은 유효기간의 일회성 코드 또는 물리적 확인으로 소유를 입증한다.
- 중앙 서비스는 미등록 Hub만 원자적으로 Home에 귀속시키며 중복 등록을 거부한다.
- 제품 겉면의 영구 QR과 기기 일련번호만으로 소유권을 획득하게 하지 않는다.
- 가족 추가: Owner가 만료되는 일회성 초대를 만들고, 초대받은 사용자가
  자신의 계정으로 수락한다. 계정 비밀번호나 영구 Hub 비밀을 공유하지 않는다.
- 가족 제거: Membership 비활성화, 기존 실시간 세션 종료, 후속 조회·제어·발송 거부.
- 로그아웃·계정 전환 시 해당 설치의 기존 사용자 연결을 해제하고 재등록한다.
- FCM에 이미 제출된 알림은 회수할 수 없다. 민감한 상세 정보는 권한을
  다시 검사하는 API에서 조회하고, 잠금화면 푸시에는 최소한의 내용을 넣는다.
- 중고 판매·소유자 변경은 기존 소유자 승인 또는 별도 복구 절차로 다룬다.

## 알림 흐름과 장애 처리

센서 → Pi 자동화 판단 → 영구 발송 대기 기록 → 중앙 서비스의 Hub 인증
→ 이벤트 저장·중복 검사 → 활성 가족 조회 → FCM → 각 휴대폰.

- Pi 인터넷 단절 중에도 기존 로컬 제어·자동화를 유지한다.
- 이벤트 ID로 재전송을 중복 처리하고, 복구 후 오래된 경고를 무조건 푸시하지 않는다.
- 알림 종류별 만료시간과 재알림 간격을 둔다.
- FCM 접수 성공과 실제 휴대폰 수신을 구분한다. 앱에서 조회할 알림 이력을 유지한다.
- 설치별 수신 주소 갱신과 무효 주소 정리를 구현한다.
- Pi 전원·인터넷이 끊긴 사실은 Pi 자체가 알릴 수 없으므로 향후 중앙 서비스의
  마지막 연결 시각으로 판단한다. 상시 감시는 이번 검토에서 활성화하지 않는다.

## 단계별 구현 제안

1. 사용자·Home·Membership·Hub 등록 구조와 가구 격리 검증.
2. Android 로그인·집 등록·초대 수락·알림 허용·설치별 푸시 등록.
3. 기존 자동화 경고의 영구 발송 큐와 중앙 서비스 연동, 알림 이력.
4. 가족 제거·계정 전환·주소 변경·네트워크 복구 시험.
5. 별도 설계 후 원격 제어 중계 확장. 알림 수신 경로와 제어 경로를 구분한다.
   첫 버전의 외부 제어는 기존 Tailscale 경로를 유지한다.

실제 구현 전 정할 사항: 계정 로그인 방식, Android 개발 방식, 중앙 서비스
호스팅·데이터베이스, 허브 소유 확인 UI, 알림 내용과 보존 기간.
현재는 Firebase Authentication을 로그인 후보, FCM을 푸시 전달 수단으로 제안한다.

핵심 검증: A집 사용자·Hub가 B집 기록을 조회하거나 B집에 발송·제어할 수 없음,
권한 제거 후 신규 발송 대상에서 제외됨, 초대 만료·재사용·중복 Hub 등록 거부,
로그아웃·재설치·주소 갱신 처리, 재시작·재전송 중복 및 만료 경고 처리.
