# Zigbee 센서 모니터링과 갱신 정책

## 목표

Zigbee2MQTT에서 받은 원시 메시지를 대시보드가 직접 해석하지 않도록 FastAPI에서 공통
센서 상태와 이벤트로 정규화한다. 첫 대상은 `sensor_door_01`과
`sensor_temperature_01`이다.

## 도어센서 상태와 이력

도어센서의 현재 상태와 상태 전환 이력은 별도로 저장한다.

- `contact=true`는 닫힘, `contact=false`는 열림으로 정규화한다.
- 열림→닫힘 또는 닫힘→열림처럼 값이 실제로 바뀐 때만 이벤트 한 건을 추가한다.
- MQTT retained 메시지 재수신, FastAPI 재시작과 같은 값의 반복 보고는 새 이벤트로
  기록하지 않는다.
- 저장 시각은 UTC로 보존하고 UI에서는 한국 집 기준 `Asia/Seoul`로 표시한다.
- 센서가 자체 시각을 제공하지 않는 현재 TS0203에서는 Pi가 메시지를 받은 시각을
  `occurred_at`의 근거로 사용한다.
- 대시보드에는 현재 상태, 마지막 변경 시각과 최근 열림·닫힘 이력을 표시한다.

초기 이벤트 모델은 다음과 같다.

```json
{
  "id": 1,
  "device_id": "sensor_door_01",
  "previous_state": "closed",
  "state": "open",
  "occurred_at": "2026-09-07T00:00:00Z",
  "source": "zigbee2mqtt"
}
```

SQLite에 인덱스를 둔 이벤트 테이블로 저장하고, 보존 기간과 최대 건수는 Step 3 구현 때
설정값으로 확정한다. 상태 변경 이력은 온습도 자동 갱신 시간대와 무관하게 항상 받는다.

## 온습도 갱신 정책

`07:00–19:00`은 자동 갱신 허용 시간이 아니라 **수동 갱신 전용 시간**이다. 이 시간에는
자동 갱신하지 않고 사용자가 요청할 때만 갱신한다. 기본 자동 갱신 허용 시간은 이를 제외한
`19:00–다음 날 07:00`이며, 수동 전용 시간의 시작·종료 시각, 자동 갱신 활성화 여부와
간격은 사용자가 UI에서 변경할 수 있다. 기본 간격은 5분이고 설정은 브라우저 로컬
저장소에 보존한다. 수동 갱신과 최초 화면 로드는 시간과 관계없이 최신 저장값을 읽는다.
정지 구간 판단도 브라우저의 지역 시간대가 아니라 `Asia/Seoul`을 사용한다.

```json
{
  "auto_refresh_enabled": true,
  "manual_only_window_start": "07:00",
  "manual_only_window_end": "19:00",
  "interval_minutes": 5,
  "timezone": "Asia/Seoul"
}
```

배터리식 TH01은 잠자는 Zigbee End Device이며 확인한 Zigbee2MQTT 정의는 능동 `get`을
지원하지 않는다. 따라서 현재 구현의 자동 갱신 간격은 센서의 측정·송신 주기가 아니라
서버의 최신 저장값을 화면에 반영하는 주기다. 수동 버튼도 새 측정을 요구하지 않고
최신 저장값을 다시 읽는다고 표시한다.

- 실제 새 보고를 받으면 서버의 `last_reported_at`과 측정값을 갱신한다.
- 수동 전용 시간에도 장치가 자발적으로 보낸 보고는 버리지 않고 저장한다.
- 온습도 SSE 이벤트는 카드에 즉시 반영하지 않는다. 자동 REST 결과를 반영할 때
  자동 갱신 활성화 여부, KST 정지 구간과 마지막 화면 갱신 이후 간격을 모두 검사한다.
- SSE 재접속이나 가입 화면의 강제 자동 조회도 이 온습도 정책을 우회하지 않는다.
- 도어 SSE와 도어 상태 변경 이력 수집에는 온습도 화면 갱신 정책을 적용하지 않는다.
- 향후 능동 조회 가능한 센서를 추가하면 새 보고, 조회 요청 후 보고 대기와 캐시 재조회를
  구분하는 상태 모델을 확장한다. 현재 TH01에 보고 대기 기능이 구현된 것처럼 표시하지 않는다.

## UI에서 Zigbee 센서 추가

향후 센서를 추가할 때 SSH나 Zigbee2MQTT 관리 화면을 직접 열지 않아도 되도록 기존 기기
추가 화면에 `Zigbee 센서 추가` 흐름을 넣는다.

1. 사용자가 `기기 추가 → Zigbee 센서`를 선택한다.
2. UI가 페어링 허용 시간을 보여주고 사용자가 시작하면 FastAPI가 Zigbee2MQTT에 제한
   시간 가입을 요청한다.
3. 센서 종류별 초기화·버튼 누르는 방법을 화면에 안내하고 남은 시간을 표시한다.
4. 새 장치가 발견되면 제조사, 모델, 지원 여부와 제공 기능을 보여준다.
5. 사용자가 표시 이름, 공간과 아이콘을 정하면 충돌 없는 내부 ID를 자동 생성한다.
6. 지원 장치는 기능에 맞는 카드와 상태 필드를 자동 등록한다. 미지원 장치는 지원되는
   것처럼 등록하지 않고 진단 정보와 모델 추가 요청 흐름으로 보낸다.
7. 성공, 취소 또는 시간 만료 시 `permit_join=false`를 확인하고 마법사를 닫는다.

UI에는 IEEE 주소나 MQTT 비밀번호를 노출하지 않는다. 장치 종류는 고정 목록에만 의존하지
않고 Zigbee2MQTT가 알린 `exposes` 기능을 공통 capability로 변환해 이후 센서 종류를 쉽게
늘릴 수 있게 한다.

## API와 화면 경계

```text
Zigbee2MQTT MQTT
      ↓
FastAPI MQTT 어댑터
      ↓
정규화된 현재 상태 ── SQLite 상태 전환 이력
      ↓                         ↓
REST 현재값·이력 API + SSE 실시간 알림
      ↓
모바일 / PC / 13인치 터치 대시보드
```

화면에는 최소한 다음을 제공한다.

- 도어: 현재 열림/닫힘, 마지막 변경 시각, 최근 이벤트 목록, 배터리
- 온습도: 값, 마지막 실제 보고 시각, 신선/오래됨 상태, 수동 갱신 버튼
- 설정: 자동 갱신 활성화, 수동 전용 시작·종료 시각, 갱신 간격; 시간대는 `Asia/Seoul` 고정
- 기기 추가: 제한 시간 페어링, 발견 상태, 이름·공간·아이콘과 지원 여부
- 연결: API, MQTT, Zigbee 상태와 갱신 실패 또는 대기 중 피드백

## SSE와 로컬 자동화 구현

`GET /api/v1/events`는 서버에서 브라우저로 상태를 보내는 SSE 스트림이다. MQTT 콜백은
별도 스레드에서 실행되므로 `EventHub`가 FastAPI asyncio 루프에 안전하게 이벤트를 넘긴다.
브라우저는 연결 복구 때 REST로 최신 상태를 다시 읽어 유실 구간을 보정한다. 도어와
자동화 상태는 복구하되, 온습도 화면 반영에는 위 갱신 정책을 유지한다. 자동화 화면은
`stream.ready`에서도 규칙·현재 경고·이력을 REST로 다시 조회한다.

첫 자동화는 `door-open-aircon-warning`이며 기본 5분 지연을 사용한다. 열린 도어센서와
마지막 성공 IR 명령상 켜진 에어컨이 동시에 있을 때만 조건이 성립한다. 규칙 설정과 상태,
발생·해제 이력은 `runtime/automations/automations.sqlite3`에 저장한다. 활성 경고 플래그로
같은 조건의 반복 평가를 한 건으로 제한한다.

2026-09-08 Pi v0.7.0에 승인된 11개 파일을 배포하고 SHA-256 일치, 앱·키오스크의
`active`/`NRestarts=0`, MQTT 연결과 센서 2개를 확인했다. SSE HTTP 200, 연결 준비
이벤트와 keep-alive까지 관찰했으며, 실물 조작 없이 새 센서 이벤트 0건·IR 명령 0건이었다.
규칙은 활성·300초 지연·경고 없음·이력 0건이었다. Python 74개·Node 12개 테스트는
통과했지만 실제 문 전환과 경고 발생·해제, MQTT 단절·화면 회전/절전 현장 검증은 남았다.
근거는 [운영 배포 기록](../journal/2026-09-08-step3-pi-live-deployment.md)에 보존한다.

## 검증 항목

1. 닫힘→열림→닫힘에서 시각이 있는 이벤트가 정확히 두 건 생성되는지 확인한다.
2. 같은 상태 반복 메시지와 서비스 재시작으로 이벤트가 중복되지 않는지 확인한다.
3. UTC 저장과 `Asia/Seoul` 화면 표시가 일치하는지 확인한다.
4. `07:00–19:00` 수동 전용 경계와 이를 제외한 자정 넘김 자동 갱신 구간을 테스트한다.
5. TH01의 능동 조회 지원 여부, 잠든 상태와 버튼으로 깨운 상태를 구분해 검증한다.
6. MQTT 단절과 오래된 값이 최신 측정처럼 보이지 않는지 확인한다.
7. 센서 추가 성공·취소·시간 만료 뒤 `permit_join=false`가 되는지 확인한다.
