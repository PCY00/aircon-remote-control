## 작업 목표

Step 3에 남아 있던 두 항목을 로컬 기준본에서 구현했다.

1. MQTT로 새 센서 보고가 들어오면 브라우저에 즉시 전달한다.
2. 문이 열린 채 에어컨이 일정 시간 켜져 있으면 경고와 이력을 남긴다.

이번 기록 시점에는 로컬 구현과 테스트까지 완료했고 Raspberry Pi 운영 배포와 실물 센서
통합 검증은 승인 후 진행한다.

## SSE를 선택한 이유

현재 필요한 실시간 흐름은 서버에서 브라우저로 보내는 단방향 상태 알림이다. 브라우저에서
서버로 보내는 제어 명령은 기존 REST API가 이미 담당한다. 따라서 양방향 WebSocket보다
연결 복구가 단순하고 브라우저 기본 `EventSource`를 사용할 수 있는 SSE를 선택했다.

```text
Zigbee2MQTT → Paho MQTT 스레드 → SensorService → SQLite
                                      ├─ EventHub → /api/v1/events → 브라우저
                                      └─ AutomationService
```

`EventHub`는 MQTT 콜백 스레드와 FastAPI의 asyncio 루프 사이를 연결한다. 구독자별로
크기가 제한된 큐를 사용하고, 느린 브라우저의 큐가 가득 차면 가장 오래된 항목을 버린 뒤
최신 상태를 넣는다. SSE 연결에는 15초 keep-alive를 보내며 재연결 시 REST로 최신 전체
상태를 한 번 다시 읽는다. 따라서 연결이 끊긴 사이의 일회성 이벤트를 재생하지 않더라도
현재 센서 카드는 최신 저장 상태와 다시 일치한다.

브라우저는 새 `sensor.updated` 이벤트에서 해당 센서 객체만 바꾼다. 도어 상태가 실제로
변해 `event_recorded=true`인 경우에만 그 센서의 최근 이력을 다시 요청한다. 기존의 센서
ID별 DOM 재사용과 함께 전체 카드 재생성을 피한다.

## 첫 자동화 규칙

첫 규칙 ID는 `door-open-aircon-warning`이다.

```text
조건: 열림 상태인 도어센서가 1개 이상
  AND last_desired_state.power=true인 에어컨이 1개 이상
지연: 기본 5분, UI에서 1·3·5·10·15·30분 선택
동작: 대시보드 경고 표시 + SQLite 이벤트 기록
해제: 문이 닫히거나 에어컨이 꺼지면 경고 해제 이벤트 기록
```

에어컨은 IR이 상태를 되돌려 주지 않으므로 실제 상태가 아니라 마지막으로 성공한 명령에서
추론한 `last_desired_state`를 사용한다. UI에도 이것을 확정 상태로 과장하지 않는 기존
원칙을 유지한다.

자동화 설정, 현재 조건 시작 시각, 경고 활성 상태와 발생·해제 이력은
`runtime/automations/automations.sqlite3`에 저장한다. 같은 조건이 계속 유지되는 동안은
`warning_active`가 이미 참이므로 경고 이벤트를 한 번만 만든다. FastAPI 백그라운드 작업이
5초마다 조건을 평가하므로 센서의 추가 보고가 없어도 지연 시간이 지나면 경고가 발생한다.

API는 다음과 같다.

- `GET /api/v1/automations`: 규칙과 현재 조건·경고 상태
- `PATCH /api/v1/automations/{rule_id}`: 활성화와 지연 시간 변경
- `GET /api/v1/automations/events`: 최근 발생·해제 이력
- `GET /api/v1/events`: 센서·기기·자동화 SSE 스트림

자동화 화면의 기존 시간 예약 카드는 실제 서버 저장이 아닌 UI 시안이었다. 이번에는 이를
운영 규칙처럼 보이지 않게 제거하고, 브라우저를 닫아도 Pi에서 계속 감시되는 실제 안전
자동화 카드와 경고 기록으로 교체했다.

## 로컬 검증과 발생한 문제

Ruff, 전체 Pytest 74개와 두 JavaScript 파일의 구문 검사가 통과했다. 테스트는 다음을
포함한다.

- SSE 이벤트 전달과 wire format
- 문 열림+에어컨 켜짐 조건의 지연 후 경고
- 같은 조건 반복 평가의 중복 방지
- 조건 해제와 해제 이력
- 규칙 활성화·지연 설정의 앱 재시작 후 영속성
- 잘못된 설정과 없는 규칙의 API 오류

로컬 미리보기를 처음 `127.0.0.1:8768`에 열 때 Windows `10048` 주소 사용 중 오류가
발생했다. 기존 프로세스를 종료하지 않고 포트 사용 범위를 보존한 채 `8771`의 별도 임시
런타임 디렉터리로 다시 실행했다. 자동화 REST 응답, 빈 이력과 SSE의 `stream.ready`를
실제 HTTP로 확인했다. 운영 포트 `8001`이나 Raspberry Pi에는 영향을 주지 않았다.

## 남은 현장 검증

- Raspberry Pi에 승인된 파일만 배포하고 서비스·SSE 연결을 확인한다.
- 실제 문 열림·닫힘을 한 번씩 수행해 새 보고가 화면에 즉시 반영되는지 확인한다.
- 안전을 위해 지연을 1분으로 임시 설정하고 에어컨을 켠 상태에서 경고 한 건만 생기는지
  확인한 뒤 기본 5분으로 복구한다.
- 문을 닫거나 에어컨을 껐을 때 경고가 해제되고 이력이 한국 시간으로 보이는지 확인한다.
- MQTT 단절·복구와 화면 회전·절전 현장 설정은 별도 최종 점검으로 남긴다.

## 배포 전 읽기 전용 확인

배포 스크립트의 preview 모드로 운영 대상 11개 파일, 총 225,863바이트를 확인했다. 이
모드는 원격 파일을 바꾸지 않는다. Pi는 `aircon-controller=active`, 설치 버전 `0.6.0`이며
새 `events.py`, `app/automations/`, `automations.js`는 아직 없는 정상적인 이전 상태였다.

첫 버전 확인은 PowerShell·SSH·원격 Python의 중첩 인용에서 배포 패키지 이름 양쪽에 공백이
들어가 `PackageNotFoundError`가 발생했다. 파일이나 서비스를 바꾸지 않는 조회 명령이었고,
중첩 Python을 없앤 `python -m pip show ... | grep '^Version:'`으로 바꿔 0.6.0을 확인했다.
실제 배포는 별도 승인 후 한 번만 실행한다.
