# 2026-10-02 — A50 중앙 서버 실행 기반 구축

## 요청과 범위

앱 정리 완료 뒤 사용자가 ‘2번 진행하자’고 요청했다. 직전 합의의 중앙 서버
실행 환경 구축을 진행했다. 사용자는 계속 휴대폰을 직접 조작할 수 없는 조건이다.
노트북은 개발 도구로 유지하고 A50에 실행 환경·상태 확인 API·영구 SQLite·
로그 제한·자동 시작·프로세스 복구를 구성했다. Pi 접속·배포와 가구 인증·FCM
자격 증명 생성·APK 구현·인터넷 공개는 하지 않았다.

## 설치 전 실제 상태

SSH와 기존 원격 관리가 정상이며 Python·pip·runit 명령은 없었다.
기존 Termux 서비스 디렉터리는 sshd·ssh-agent이며 모두 down 파일이 있었다.
10-start-ssh는 공개키 SSH와 partial wake lock을 준비하는 기존 정상 파일이다.
별도 중앙 서버 디렉터리는 없었다.

## 로컬 구현과 선택

services/central-server에 독립 Flask+Waitress 서비스를 만들었다.
PyPI 실제 버전을 확인해 Flask 3.1.3·Waitress 3.0.2 및 간접 의존성을 고정했다.
개발용 Flask 서버를 장기 실행하지 않고 Waitress의 스레드 2개를 사용한다.
127.0.0.1:8001의 상태 확인 API와 준비 화면만 만들었다. Home·Membership·
Hub·FCM 테이블이나 제어 API는 없다.

SQLite는 WAL, 쓰기 대기 5초, 파일 기본 권한 600으로 초기화한다.
최초 런타임 메타데이터를 유지하고 알 수 없는 기존 스키마는 중단한다.
readiness는 read-only 연결로 확인해 저장소 유실 때 빈 DB를 만들지 않는다.
오류 응답은 503과 일반 상태만 포함하며 내부 경로·식별값을 보내지 않는다.

첫 테스트에서 Windows에 O_NONBLOCK이 없어 재시작 제한 검사 2개가 실패했다.
실제 실패 원문은 144다. Windows에서는 파일 기반 down 표시를 확인하고 Android의
비차단 runit 제어는 해당 플래그가 있는 환경에서 사용하도록 오류 경로를 수정했다.
총 8개 테스트와 관련 Python Ruff 검사는 통과했다. 해결 기록은 145다.
나중 정적 검사에서 쉘 파일을 Ruff에 직접 넘긴 명령은 잘못된 검사 대상이었다.
Python 대상만 다시 검사해 통과했고 쉘 설치 파일은 실제 장비에서 실행했다.

## 설치·배포

143: apt-get update 후 python python-pip termux-services만 지정해 설치했다.
일괄 시스템 업그레이드는 하지 않았다. 의존성으로 ncurses 1개 갱신과 신규 22개가
필요했고 97.0MB 다운로드·588MB 추가 디스크 사용 예상이 출력됐다.
Termux Python 3.14.6, SQLite 3.53.4, runit 2.3.1, termux-services 0.13-1 확인.
설치 전후 기존 SSH 부팅 파일의 SHA-256은 같았다.

146: 배포 미리보기. 고정 소스 11개·새 중앙 서비스만 확인했고 기기 변경은 없었다.
147: 로컬 해시별 v0.1.0-ccd62f777a96a998 릴리스를 명시적으로 배포했다.
가상환경에 의존성을 설치했고 MarkupSafe는 Android ARM64용 실제 빌드에 성공했다.
pip check 통과, 상태 확인 응답 정상, 릴리스와 부팅·서비스 훅 체크섬 일치 확인.
배포 도구는 기존 소스 변경·알 수 없는 디렉터리·훅을 덮어쓰지 않고 중단한다.
첫 설치 실패 시 미추적 부분 설치를 자동 삭제하지 않으며 점검·복구해야 한다.

## 운영 구성

- 소스: ~/services/aircon-central/current → 해시별 releases 디렉터리.
- 영구 DB: ~/.local/share/aircon-central/central.sqlite3, 릴리스 밖에 유지.
- 별도 부팅 훅: ~/.termux/boot/20-start-central, 기존 10-start-ssh 보존.
- runit 서비스: $PREFIX/var/service/aircon-central, 기존 SSH down 파일 보존.
- 앱 로그·서비스 출력 로그: 각각 1MiB 파일+백업 3개, 부팅 로그 최근 100줄.
- 비정상 종료 5회/5분이면 기록·down 표시·서비스 중단. 다음 부팅도 표시를 존중.
- 정상 SIGTERM/SIGINT 중지는 실패로 세지 않는다. 원인 수정 뒤 SSH로 명시적으로 복구.

실패 제한은 로컬 검사로 확인했다. 장비에서는 1회 강제 종료만 시험했다.
구동이 성공할 때마다 실패 기록을 지워 무한 재시작을 숨기지 않는다.
자동 모니터 예약·Pi 자동 동기화는 활성화하지 않았다.

## 실제 장비 검증

148: SQLite integrity_check=ok, 생존·준비 API HTTP 200 확인.
4개 클라이언트가 보낸 준비 확인 요청 8개가 성공했다. 4가구 부하 시험은 아니다.
LAN 주소의 8001 접속은 거부됐고 휴대폰 내부 루프백 응답은 성공했다.
첫 서버 RSS 36,732 KiB(35.9MiB), 단일 작업자 기준이며 전체 Android RAM은 아니다.
프로세스 cmdline을 확인한 중앙 서버 작업자만 SIGKILL 1회 실행했다.
새 PID·readiness 복구·실패 기록 1회·DB 메타데이터 유지가 확인됐다.

정상 재부팅을 1회 요청했다. 명령 응답 10초 시간 초과였으므로 요청을 반복하지 않았다.
최초 요청부터 검증된 ADB 복구까지 122.0초였다. 사용자 조작은 없었다.
중앙 API도 HTTP 200, DB 메타데이터·SSH 부팅 파일·소스와 훅 체크섬 유지.
재부팅 직후 서버 RSS는 36,632 KiB였다.
홈 화면에서 화면을 끈 뒤 15초 간격 8회 준비 API·ADB 응답과 마지막 SSH·DB
무결성 검사도 통과했다. 최종 관리 상태는 interactive=false, service_connected=true,
wifi_adb=1이었다. 정상 재부팅과 화면 꺼짐 2분의 단기 운영 검증을 완료했다.

149: 배포 뒤 다시 읽기 전용 미리보기로 기존 파일과 설치 기록 일치를 확인했다.
150: 원격 변경 보존·미리보기·훅 충돌 등 배포 보호 검사 4개를 추가해 최종 12개
테스트와 Python Ruff 검사 통과.
151: 실제 준비 화면 HTTP 200·정상 문구, 서버 RSS 36,212KiB, 유휴 2초 표본
단일 코어 CPU 0.0%, 시스템 available 1301MiB·저장 공간 여유 48G.
보호 앱 28개 활성·일반 앱 10개 사용 중지·화면 꺼짐 상태 유지 확인.
측정 표본은 짧고 초기 부팅 조건도 달라 이전 앱 정리 표본과 직접 비교하지 않는다.

실제 휴대폰 브라우저를 열고 screencap으로 캡처하려던 실행 요청은 도구 자동 승인
검토가 ‘blocked by policy’로 거부했다. 구체적 근거는 반환되지 않았다. 요청은 실행되지
않았으며 우회 재실행이나 사용자 조작 요청을 하지 않았다. 읽기 전용 HTTP 검증과
실제 명령 원문의 터미널 재구성 PNG로 블로그 자료를 남겼다. 휴대폰의 실제 웹 화면
사진을 얻었다고 기록하지 않는다. 이 도구 제한은 서버의 구동 실패가 아니다.
