# 2026-08-29 — IR 수신 소프트웨어 구현

## 범위 정정

프로젝트 순서를 환경 → 수신 → UI → 송신으로 정정했다. 송신기 회로는 다음 날로
미루고, 오늘은 수신 패킷을 안전하게 복제할 코드와 API를 완성한다.

## 구현

- Raspberry Pi `ir-ctl`과 로컬 mock을 같은 인터페이스로 분리했다.
- 범용 타이밍 파서는 두 프레임의 경계와 0/1 공간 길이를 분석한다.
- 캐리어 `16214-15597` 프로필은 프레임당 48비트를 검증한다.
- 한 번에 하나의 수신 작업만 허용하며 충돌은 HTTP 409로 반환한다.
- 원샷 작업은 완료·시간초과·실패·취소 상태를 구분한다.
- 성공 시 JSON, signed-microseconds 원본과 `ir-ctl` 재생용 파일을 원자적으로 저장한다.
- API 라우터는 GPIO나 프로세스를 직접 다루지 않는다.

## 구현 중 이슈

첫 대형 패치는 같은 파일을 삭제와 추가 대상으로 동시에 지정해 패치 도구가 전체를
거부했다. 일부만 반영된 상태는 아니었다. 이후 설정·하드웨어/파서·서비스/API·테스트로
패치를 나눠 적용해 대상 중복을 없앴다.

첫 검사에서 수신 기능 테스트 12개는 통과했지만 기존 `/` 응답 테스트가 이전 단계의
`environment-ready`를 기대해 1개 실패했다. 새 단계 상태인 `ir-receiver-ready`로 계약과
테스트를 맞췄다. Ruff가 지적한 취소 예외 처리와 긴 줄도 수정했다.

개발 테스트 의존성을 잠시 `httpx`로 바꿨지만 현재 Starlette 1.6 환경에는 `httpx2`가
실제로 설치돼 있고 기존 호환성 결정과도 맞음을 `pip show`로 재확인했다. 변경을 바로
되돌려 새 환경에서도 기존 테스트 경로가 유지되게 했다.

합성 파형 테스트가 끝난 뒤 기존 실제 캡처 30개를 모두 파서에 통과시켰다. 29개는
성공했고, 원샷이 아니라 시간 제한으로 수집한 초기 파일 하나는 마지막 stop pulse 뒤의
긴 idle space까지 포함해 49번째 비트처럼 해석됐다. 프레임 토큰 수가 짝수이면 마지막
space는 뒤따르는 pulse가 없는 유휴 구간이라는 일반 규칙으로 제외했다. 회귀 테스트를
추가한 뒤 30개 모두 정상 해석됐다.

## Raspberry Pi 배포

사용자 승인 후 21개 파일 41,620바이트를 `/home/air/aircon-controller`로 전송했고,
전송 후 모든 SHA-256이 로컬과 일치했다. 편집 가능 설치 메타데이터를 0.2.0으로
갱신하고 사용자 systemd 서비스를 재시작했다.

설치·재시작은 성공했지만 한 줄로 묶은 첫 검증에서 PowerShell이 원격 Bash의
`$(tailscale ip ...)`를 먼저 해석했다. Windows에 없는 `head`를 실행하려다 변수가
깨졌고 curl 확인만 실패했다. 원격 명령 전체를 PowerShell 단일 인용 문자열로 바꿔
재실행했다. 최종 결과는 서비스 active, health 정상, `ir-ctl`과 `/dev/lirc0` 모두
준비 상태였고 캐리어·범용 프로필 두 개가 API에 노출됐다.

## 실제 API 원샷 수신 검증

사용자가 수신기 앞에서 온도 올림 버튼을 한 번 눌렀다. API는 약 10초 안에 작업을
`completed`로 종료했고 199개 타이밍 토큰을 동일한 48비트 프레임 두 개로 분석했다.
관측 바이트는 두 프레임 모두 `b2 4d 3f c0 13 04`였다. 마지막 바이트쌍은 보수가
아니지만 캐리어 프로필은 아직 해독되지 않은 의미를 추측하지 않고 48비트 구조와
원본 파형을 그대로 보존하도록 설계했으므로 정상 수신으로 처리했다.

Pi의 `runtime/captures/`에는 같은 UUID를 가진 JSON 메타데이터, `.compact` 원본과
`ir-ctl` 송신용 `.ir` 파일이 모두 생성됐다. 이로써 mock, 과거 실제 캡처 30개와
새 API 실기 수신까지 검증돼 Step 2를 완료했다.
