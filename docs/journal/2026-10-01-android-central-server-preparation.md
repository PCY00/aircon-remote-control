# 2026-10-01 — Galaxy A50 중앙 서버 준비와 블로그 기록

이 문서는 연결 전 준비 당시의 기록이다. 아래의 미확인 표시는 당시 상태를 뜻한다.
이후 실제 ADB·SSH·화면 꺼짐·부팅 복구 결과는
[2026-10-02 검증 기록](2026-10-02-a50-background-ssh-verification.md)에 정리했다.

## 사용자 요청과 작업 경계

- 최신 요청: 접속 후 **화면 꺼짐·백그라운드 SSH/Termux 유지와 복구를 가장 먼저**
  구성·검증한다. 단계별 실제 캡처를 보존하고, 이후 요청 시 재접속해 서버를 관리할 수
  있는 접속 경로를 마련한다. 무중단·상시 접근 성공은 아직 검증되지 않았다.
- 사용자는 긴 공개키 명령을 휴대폰에서 손으로 입력하기 어렵다고 밝혔고,
  연결 방식 질문에 **Wi-Fi만 사용**한다고 답했다.
- 동일한 앱을 사용하는 여러 가구의 Pi·가족 권한·알림을 분리하는 구조를 논의했다.
- 사용자는 현재 노트북의 운영 설정 변경을 원하지 않으며, Galaxy A50 공기계를
  중앙 서버 후보로 시험하기로 하고 공장초기화를 먼저 진행하겠다고 밝혔다.
- 단계별로 진행하며 블로그용 기록·필요한 사진 요청·실제 실행 캡처를 남긴다.
- 사용자는 휴대폰의 SSH 접근도 허용했다. 실제 주소·계정·포트·인증 방식은
  확인되지 않았으며 연결을 시도하지 않았다.
- 프로젝트 코드·문서는 로컬을 기준본으로 유지한다. 휴대폰에서도 배포본을
  직접 수정해 별도 버전을 만들지 않는다.
- 노트북은 기존 개발·문서 작업 도구로 사용하며 중앙 서버 운영 설정을 변경하지 않는다.

## 현재 상태 — 완료 사실과 미확인 사항

확인된 사실:

- 사용자가 **공장초기화 완료**를 보고했다. 이는 사용자 확인이며 직접 실행·화면
  검증은 아니다. 재부팅·환영 화면 사진은 사용자 요청에 따라 생략했다.
- 사용자가 서버 후보를 Galaxy A50 공기계로 지정했다.
- 사용자가 기기에 표시된 모델번호를 **SM-A505N**으로 확인해 알려줬다.
- 사용자 확인 소프트웨어: **Android 11, One UI 3.1**.
- 사용자가 **Termux 설치 완료**를 보고했다. 앱 실제 버전·첫 실행 출력은 아직
  직접 확인하지 않았다. 다음 단계로 OpenSSH 패키지 설치와 사설망 접속 정보 확인을 안내한다.
- 사용자가 `whoami` 결과와 `ifconfig`의 사설 IPv4 주소를 알려줬다.
  접속 정보는 대화에서 확인한 값을 사용하며 공개 기록에는 사용자명·IP를
  `[REDACTED_PHONE_USER]`, `[REDACTED_PHONE_IP]`로 표기한다.
- 개발 PC에 A50 접속용 Ed25519 키를 생성했다. 개인키는 저장소 밖의 사용자
  SSH 디렉터리에 보관하고 공개키만 휴대폰 등록을 위해 전달한다.
  명령 종료 코드 0과 키 종류를 확인했고 실제 기록은
  `../assets/terminal/78-a50-ssh-client-key.txt`와 같은 이름의 PNG에 보존했다.
- 사용자가 전달한 보안 표기 원문은 `ASKS v4.5 Release 20220314`,
  `ADP v3.0 Release 20191001`, `SMR Feb-2023 Release 1`이다.
  보안 소프트웨어 버전 항목으로 추정하며, 별도의 Android 보안 패치 수준
  날짜는 아직 확인되지 않았다. `2023-02-01`처럼 날짜를 추정해 확정하지 않는다.
- 삼성 국내 SM-A505N 지원 페이지의 공식 사양은 옥타코어 CPU, RAM 4GB,
  내장 저장 용량 64GB다. 이는 제조사 사양이며 실제 여유 메모리·남은 공간 측정은 아니다.
- 2026-10-01 삼성 정기 보안 업데이트 대상 목록에서 A50을 찾지 못했다.
  마지막 국내판 배포 날짜와 실제 설치된 보안 패치는 확인되지 않았다.
  현재 시험은 사설망에서 진행하고 고객용 상시 운영 적합성은 별도로 판단한다.
- 로컬 프로젝트에는 EventHub·SSE와 센서 기반 자동화 평가 코드가 있다.
- 기존 저장소에 터미널 기록 PNG 생성·이미지 개인정보 메타데이터 검사 도구가 있다.
- 가구 권한·FCM 구조 제안은 `../plans/mobile-app-household-notifications.md`에 기록했다.

미확인:

- Wi-Fi 연결 여부, Android 보안 패치 수준의 정확한 날짜·사용 가능한 메모리·남은 저장 공간.
- 실제 Termux 앱·패키지 버전, SSH 설치·실행 여부, 공개키 등록과 접속 성공.
- 화면 꺼짐·재부팅·Wi-Fi 재연결 중 서버 생존 여부.
- 중앙 서버 실행, Firebase 설정, 실제 휴대폰 알림 전달.

## 설계 가설

가벼운 중앙 API·가구별 권한·소규모 데이터베이스·FCM 발송은 A50에서 시험할 수
있을 것으로 예상한다. 이는 측정된 처리량이나 24시간 운영 검증이 아니다.
Android의 절전·백그라운드 제한과 자동 복구가 주요 검증 대상이다.

초기에는 Termux와 소형 데이터베이스로 시작하는 방식을 검토한다. 루팅·펌웨어
교체는 현재 작업에 포함하지 않는다. 정확한 실행 환경은 장비 상태 확인 후 정한다.

## 사진 요청과 증거 수집

현재 단계:

사용자는 재부팅 사진을 찍지 않고 초기화만 진행하겠다고 명시했다.
최신 요청에 따라 재부팅·환영 화면 촬영은 생략하며, 현재 단계에서 추가 사진을
요구하지 않는다. 초기화 완료 여부는 사용자 보고로 기록하고 사진 검증과 구분한다.
기본 설정·Wi-Fi 연결은 초기화 완료 후 다음 단계로 안내한다.

초기화와 Wi-Fi 연결 후 다음 단계:

- Android·One UI 버전 화면과 저장 공간 화면 요청. 모델 확인 화면은 IMEI·일련번호를 가린다.
- 초기화 직전 사진을 놓쳤다면 완료 후 재초기화하지 않고 미확보로 기록한다.

SSH 연결 후:

- 실제 명령·출력에서 민감정보를 제거해 `../assets/terminal/`에 번호가 이어지는
  UTF-8 `.txt`와 같은 이름의 `.png`를 보존한다.
- 기존 마지막 번호는 이번 읽기에서 77까지 확인했지만, 새 캡처 저장 직전에 다시 확인한다.
- 실패 출력도 원인·수정·재검증 결과와 함께 보존한다.
- 기록 PNG는 `scripts/render_terminal_capture.py`로 만든 재구성 자료이며 실제
  휴대폰 화면 캡처와 구분한다. 설치·실행 성공 화면을 만들어내지 않는다.
- 휴대폰 설정 화면은 일반 Termux SSH만으로 볼 수 없다. 사용자 사진·스크린샷,
  또는 실제 접근 가능한 별도 화면 캡처 경로를 확보한 뒤 수집한다.
- 사진을 저장소에 추가하면 `scripts/sanitize_blog_images.py --apply docs/assets/`
  방식으로 메타데이터를 정리하고, 게시 전 검사에서 `PRIVATE_METADATA_COUNT=0`을 확인한다.
- 이미지 픽셀에 보이는 계정·SSID·IP·IMEI·일련번호·QR·인증정보는 메타데이터
  제거로 가려지지 않으므로 저장·캡처 전에 따로 제거한다.

## 다음 단계

사용자의 초기화 방법 질문에 삼성 공식 설정 초기화 절차를 확인해 안내했다.
경로는 `설정 → 일반 → 초기화 → 디바이스 전체 초기화`이며 이후 초기화·모두 삭제와
기기 내 인증을 진행한다. 실제 메뉴 표시는 직접 확인하지 않았고, 이후 사용자가
초기화 완료를 보고했다.
공식 안내 출처는 블로그 준비 글에 추가했다.

Android 11·One UI 3.1을 사용자 보고로 확인했다. Termux의 Android 7 이상 지원
조건을 충족하므로 다음 단계는 Wi-Fi 연결 후 Termux 설치·첫 실행이다.
2026-10-01 확인한 F-Droid 페이지의 `suggested` 버전은 0.118.3이다.
페이지 내 해당 버전의 Download APK로 직접 설치하고, 앱 시작에 필요한 초기
환경 구성이 끝난 터미널 화면 사진·스크린샷 1장을 요청한다.
이후 사용자가 Termux 설치 완료를 보고했다. 실제 설치 버전과 첫 실행 출력은
이후 화면·명령으로 확인한다.
정확한 Android 보안 패치 날짜 확인은 후속 상태 점검에 남겨두며 설치의 차단 조건으로 삼지 않는다.
그 뒤 사설망 SSH 연결을 순서대로 진행한다. 비밀번호·개인키를 대화나
문서에 요구하지 않고, 필요한 경우 공개키 인증으로 연결 절차를 구성한다.
공용 인터넷 SSH 노출·포트포워딩은 설정하지 않는다.

### Termux 설치 완료 후 안내

- A50을 개발 노트북과 같은 Wi-Fi에 연결한다.
- Termux에서 `pkg update`, `pkg install openssh`, `whoami`를 한 줄씩 실행한다.
- 설치·사용자명 확인 화면과 Wi-Fi 상세 화면의 실제 IP 주소를 요청한다.
- 아직 비밀번호 설정·SSH 서버 실행·인증 설정·자동 시작 설정은 안내하거나 실행하지 않았다.
- 사용자명·IP를 사용자 보고로 확인했다. 접속용 공개키 등록과 사설망 SSH 접속을 진행한다.
- 원격 주소·사용자명은 추측하거나 네트워크 탐색으로 찾지 않는다.
- 로컬 Windows의 `ssh.exe`·`ssh-keygen.exe` 존재를 읽기 전용으로 확인했고,
  이후 접속용 키 생성도 완료했다. 아직 휴대폰 연결은 시도하지 않았다.

### 공개키 등록 안내

Termux의 `~/.ssh` 디렉터리를 준비하고, 기존 내용을 보존하는 append 방식으로
전달한 공개키를 `authorized_keys`에 등록하도록 안내한다. 디렉터리 권한 700,
파일 권한 600을 설정하고 `sshd -p 8022 -o PasswordAuthentication=no -o
KbdInteractiveAuthentication=no`로 공개키 인증 SSH를 실행한다.
8022는 이번 안내에서 명시적으로 사용할 포트이며 실제 실행 성공은 미확인이다.
영구 SSH 설정·자동 시작·공용 인터넷 노출은 적용하지 않는다.

### 최신 경로 변경 — Wi-Fi 무선 디버깅 가능 여부 확인

공개키를 손으로 입력하는 안내는 보류한다. Android 11의 무선 디버깅(ADB)
메뉴가 실제 기기에 있는지 확인한 뒤, 가능하면 Wi-Fi ADB로 휴대폰에 접근해
공개키 등록·SSH 실행·Android 화면 캡처를 직접 처리한다.
이후 사용자가 무선 디버깅 메뉴가 있으며 켰다고 확인했다. 실제 페어링과 접속은
아직 미확인이다.

개발 PC에 Google 공식 Windows SDK Platform-Tools를 `tmp/android-platform-tools/`
아래로 내려받아 준비했다. 이는 저장소에서 제외되는 휴대용 도구이며 PATH·Windows
서비스 설정은 변경하지 않았다. 실제 `adb version` 출력은 1.0.41,
Platform-Tools 37.0.1-15733141이었다. 기록은
`../assets/terminal/79-a50-wireless-adb-tools.txt`와 같은 이름의 PNG에 보존한다.
아직 ADB 데몬 실행·기기 연결·휴대폰 설정 변경은 하지 않았다.

첫 단계는 휴대폰의 소프트웨어 정보에서 빌드 번호를 7번 눌러 개발자 옵션을
열고, 무선 디버깅 메뉴 존재 여부를 확인하는 것이다. 실제 인증값·페어링 코드와
IP·기기 식별자는 공개 기록에서 제거한다.

ADB가 가능하면 연결 후 실제 화면을 캡처하고, 장기 관리 경로는 공개키 SSH로
검증한다. 무선 디버깅만으로 재부팅 후 항상 연결된다고 간주하지 않는다.
메뉴가 없다면 짧은 명령으로 임시 SSH를 시작하고, 비밀번호를 채팅에 받지 않는
로컬 입력 방식으로 공개키를 설치하는 경로를 다시 준비한다.

### 무선 디버깅 활성화 사용자 확인

- 사용자가 메뉴 존재와 활성화를 확인했다. 직접 화면 검증은 아직 하지 않았다.
- 다음 사용자 조작은 무선 디버깅의 `페어링 코드로 기기 페어링`을 열고, 표시되는
  실제 IP·페어링 포트를 알려주는 것이다. 코드는 채팅으로 요청하지 않는다.
- `scripts/android/pair_wireless_adb.py`를 로컬에 준비했다. 실제 주소를 받은 뒤
  노트북의 마스킹 입력창을 띄워 사용자가 6자리 코드를 직접 입력하게 한다.
- 코드는 명령 인자가 아닌 subprocess 표준입력으로 전달한다. 결과 기록은
  주소·코드·기기 GUID를 제거하며 취소 시에는 실행한 것처럼 기록하지 않는다.
- 로컬 구문 검사, 잘못된 주소·포트 거부, 코드·주소·GUID 제거 검사를 통과했다.
  정적 검사에서 발견된 import 순서·긴 줄을 수정한 뒤 정적 검사도 통과했다.
- 입력창을 아직 실행하지 않았고 실제 페어링·휴대폰 연결을 시도하지 않았다.
