# 2026-10-02 — A50 화면 꺼짐 SSH·부팅 자동 복구 검증

## 범위와 확인 사실

사용자가 Wi-Fi만으로 휴대폰에 접근하고, 첫 작업으로 화면 꺼짐 중 SSH·Termux
유지를 설정해 달라고 요청했다. A50만 변경했다. 라즈베리파이 코드는 배포하지 않았다.

기기 직접 확인: SM-A505N, Android 11, 보안 패치 2023-02-01,
Termux 0.118.3, OpenSSH 10.5p1. One UI 3.1과 공장초기화 완료는 사용자 보고다.
Termux:Boot는 F-Droid 0.8.1을 설치하고 최초 실행했다.

## 실제 작업

- 무선 ADB 페어링·접속 성공. 페어링 코드·주소·기기 식별자를 공개 기록에서 제거했다.
- Termux와 Termux:Boot를 Android 배터리 최적화 예외에 추가했다.
- Termux foreground service와 실제 partial wake lock을 확인했다.
- PC 전용 Ed25519 공개키를 authorized_keys에 기존 내용을 보존하며 등록했다.
- 8022 SSH에서 비밀번호·키보드 대화형 인증을 끄고 공개키로 접속했다.
- 부팅 스크립트를 로컬에서 작성하고 SSH로 단방향 배포했다.
  로컬·기기 파일 SHA-256 일치와 셸 구문 검사를 확인했다.
- 부팅 로그는 실행마다 이전 내용을 100줄로 제한한다.
- 접속 키·호스트 기록은 저장소 밖에, 연결 정보는 Git 제외 .deploy/a50/에 보관한다.
  scripts/android/a50_ssh.py로 다음 작업 시 재접속할 수 있다.

df -h의 데이터 영역 52G 중 49G 여유. 재부팅 직후 측정값이며 처리량 시험이 아니다.

## 실패와 해결

1. run-as는 F-Droid 패키지가 debuggable이 아니어서 거부됐다.
   초기 명령을 ADB 터미널 입력으로 실행했다.
2. input text의 %s 공백 치환이 printf 형식 문자열을 바꿔 공개키 등록이 실패했다.
   echo로 공개키 한 줄을 등록한 뒤 실제 SSH 연결로 검증했다.
3. APK 설치가 25초에서 시간 초과됐다. no-streaming 설치도 원격 대상
   디렉터리 오류가 발생했다. 명시적인 원격 APK 경로로 전송하고 잠금 해제 뒤
   더 긴 제한으로 pm install을 실행해 성공했다. 초기 시간 초과의 단일 원인은 미확정이다.
4. Windows text=True 표준입력으로 보낸 셸 파일이 CRLF로 바뀌어 구문 검사가 실패했다.
   UTF-8 bytes로 LF를 유지해 배포했다. 실패 파일은 실제 부팅 경로에 설치하지 않았다.

실패를 기록 81, 83, 86~89에, 해결을 84, 90~91에 남겼다.

## 자료와 남은 일

초기 검증에서 실제 폰 화면 3장과 기록 80~93의 TXT·PNG를 보존했다.
PNG 터미널 자료는 실제 출력을 민감정보 제거 후 렌더링한 것으로 폰 스크린샷과 구분한다.
수집한 폰 화면은 Termux 실행, SSH 준비 완료, Termux:Boot 최초 실행이다.
사용자가 생략한 초기화·환영 화면 사진은 추가로 요구하지 않았다.

Python 구문 검사와 ruff 정적 검사를 통과했다. Git 제외 경로를 확인했고,
공개 자료에서 실제 접속 주소·앱 사용자명·공개키 문자열이 없는지 검사했다.
이미지 개인정보 메타데이터 검사도 PRIVATE_METADATA_COUNT=0이었다.
로컬 검증 출력은 기록 94에 보존했다.

초기 검증 범위는 같은 Wi-Fi, 충전 상태, 초기 2분 동작과 정상 재부팅 1회다.
야간·24시간, 네트워크 단절·DHCP 변경, 삼성 절전 앱 장기 영향,
외부 사설망 관리, 중앙 API·FCM은 아직 검증·구현하지 않았다.
초기 단계에서는 자동 감시나 예약 작업을 활성화하지 않았다.

## 후속 요청 — 무선 디버깅 관리부터 자동화

사용자는 1편을 초기화부터 원격 관리 준비까지로 합치고 2편에서 운영 환경 정리와
중앙 서버 구축을 진행하기로 했다. 필수 휴대폰 기능을 없애지 말라고 명시했으며,
앱 정리보다 사람이 매번 디버깅을 켜고 포트를 알려주는 문제를 먼저 해결해 달라고 요청했다.
앱 삭제·사용 중지는 아직 실행하지 않았다.

### 구현과 실패 분석

- scripts/android/a50_adb.py: 페어링된 TLS mDNS 서비스만 발견하고 모델·기기 식별을
  검증한 뒤 명령을 실행한다. 사설 주소·식별값은 Git 제외 설정에만 저장한다.
- 포트 발견 도구만 적용한 첫 재부팅은 ADB 복구 실패, SSH 복구 성공이었다(97).
- 일반 Termux SSH의 Android 관리 권한을 가정하지 않고 자체 복구 앱을 로컬 구현했다.
  소스는 android/a50-manager/, 빌드는 scripts/android/build_a50_manager.py다.
- 공식 휴대용 Java·Android 도구를 체크섬 검증해 준비했다(99).
  aapt의 한글 경로 오류(100)는 ASCII 임시 경로에서 패키징해 해결했다(101).
  서명 키·암호는 저장소 밖에 둔다. 서명·매니페스트 권한을 검증한 APK를 설치했다.
- 사용자가 무선 디버깅을 켠 뒤 IP·포트 입력 없이 재발견·설치·권한 부여·최초 실행을
  마쳤다(102). 관리 앱은 adb_wifi_enabled 하나만 변경하며 최초 설정 권한과
  배터리 최적화 예외를 부여했다. Android 신뢰·페어링은 우회하지 않는다.
- 부팅 완료 수신과 Android JobScheduler의 15분 보조 복구를 구성했다.
  즉시 실행·정확한 주기·모든 장애 복구를 보장하지 않는다. Codex 예약 작업이나
  Pi 자동 배포·상시 감시는 만들지 않았다.
- 첫 APK 적용 재부팅에서는 123.9초의 발견 대기 후 새 포트로 ADB 명령이 성공하고
  SSH도 돌아왔다(103). 그러나 4분 뒤 ADB가 끊겼다. SSH는 계속 정상(104).
  사용자가 Wi-Fi 허용 팝업을 확인했다. SSH로 관리 앱을 다시 열 수 있었지만
  이 동작만으로 Android의 최초 Wi-Fi 허용 확인을 대신할 수 없었다.
- 사용자에게 해당 팝업의 항상 허용 저장을 요청했고 완료 답변을 받았다.
  실제 ADB 명령에서 연결 마커·모델 SM-A505N·adb_wifi_enabled=1을 확인했다.
  그 뒤 정상 재부팅·5분 연결·화면 꺼짐 후속 검증을 별도로 진행한다(105).

추가 실제 폰 화면은 관리 앱 최초 설정 화면 1장이다. 화면의 상태 표시를 지속 연결
성공 증거로 사용하지 않으며 실제 명령 응답과 후속 실패 기록을 함께 보존한다.

### 항상 허용 이후의 실제 후속 결과

105는 240초 내 복구 실패다. 5분 연결·화면 꺼짐 시험은 수행되지 않았다.
사용자가 항상 허용을 체크해도 팝업이 반복된다고 보고했다.
현재의 신뢰 저장 접속 지점 1개와 실제 접속 지점의 일치를 확인했다.
부팅 로그에는 Expected keyStore, but got tag=null 및 초기 Wi-Fi 미연결 메시지가 있었다(107).
파일이 비었는지 제조사 동작인지 아직 확정하지 않았다. 시스템 파일을 덮어쓰거나
페어링을 초기화하지 않았다. 임시 app_process 읽기 진단은 실패했다(106).

0.2.0에서 소유자가 승인한 현재 Wi-Fi 이름만 권한 보호 구성으로 등록했다.
기존 접근성 서비스 목록을 보존해 자체 서비스만 추가했다(110). 네트워크·일반 권한창
전체를 확인하는 기능이 아니다. 등록 네트워크 이름 판별의 양성·음성 사례 9개를
JVM에서 검사했고 통과했다. ADB 기기 선택·SSH 복구 경로 로컬 테스트 5개도 통과했다.
StatusReceiver는 설정을 수정하지 않으며 비밀정보 없는 상태만 읽을 수 있다.

112도 ADB 자동 복구 실패다. SSH로 서비스 연결 상태와 wifi_adb=0을 확인했다.
사용자에게 허용 버튼을 누르지 않고 화면만 켜는 시험을 요청했다.
실물 SystemUI APK를 SSH로 읽어 Android 11의 실제 클래스·문구·체크박스 ID를
확인했다(113). 소스 0.3.0에는 복구 시 15초 화면 wake lock과 진단 상태를 추가했다.
빌드·서명 검사는 통과했지만 0.3.0은 아직 실물에 설치하지 않았다(114·115).
화면 꺼짐 조건의 원인 판별과 최종 자동 복구 검증이 남아 있다.

마지막 확인에서도 SSH는 정상, 관리 앱은 연결된 서비스 상태, wifi_adb=0이었다(117).
로컬 접속 도구의 자동 Activity 재호출은 일시 중지했다. 기기 자체 부팅·15분 보조
구성은 남아 있다. 0.3.0 설치 전이며 화면만 켜는 사용자 시험 응답을 기다린다.
현재 자동 복구를 완료로 처리하지 않는다. 앱 정리·중앙 API·FCM은 진행하지 않았다.

추가 실행 기록 95~117은 실제 출력 기반 TXT·PNG 쌍으로 보존했다.
5개 Python 검사·9개 JVM 조건 검사는 통과했다(116).
공개 자료의 실제 접속 값 검사는 0건, 전체 이미지 157개의 개인정보 메타데이터 검사도
PRIVATE_METADATA_COUNT=0이었다. 실패한 시험에서 실행하지 못한 지속성 단계를 표시했다.

## 후속 수정 — 실제 창 확인과 0.4.0 적용

사용자가 화면만 켰지만 ADB는 돌아오지 않았다. 일반 Termux UID에서 읽기 전용
Java 진단을 실행해 실제 접근성 서비스 활성화·Wi-Fi 연결·화면 켜짐·설정 권한과
설치 버전 0.2.0을 확인했다. 초기 ContentResolver 설정 읽기는 등록되지 않은
IApplicationThread 때문에 거부돼 진단에서 제외했다. 추가 관리 권한을 부여하지 않았다.
현재 기록 118은 업데이트 후 0.4.0의 실제 진단이며 서비스 flags=80, 패키지 필터
System UI·설정·android, 서비스 활성화와 설정 권한을 확인했다.

0.4.0은 이벤트마다 검사 대기를 취소하지 않는 방식, 여러 시스템 창 조회,
실제 서비스 연결·검사 횟수 진단, 15초 화면 깨우기, Wi-Fi 이름과 접속 지점의 정확한
일치, 비공개 난수 토큰이 필요한 SSH 복구 수신기를 포함한다. Activity 시작 성공만으로
복구를 판단하지 않는다. 최초 구성은 WRITE_SECURE_SETTINGS 권한으로 보호한다.
토큰·접속 값은 비공개 앱 설정과 Git 제외 로컬 설정에만 보관한다.

사용자가 기존 집 Wi-Fi 허용창을 허용한 뒤 주소·포트 입력 없이 ADB를 재발견했다.
같은 서명 키로 0.4.0을 업데이트하고 원격 APK SHA-256과 로컬 검증 APK의 일치를 확인했다(122).
다른 접근성 서비스 목록과 앱 데이터는 보존했다. 핵심 Android 앱 정리는 수행하지 않았다.

자동 처리를 잠시 끄고 실제 System UI의 WifiDebuggingActivityAlias에 현재 Wi-Fi/AP를
전달해 창을 확인했다(123). 실제 제목과 본문·체크박스는 영어, 취소 버튼은 한글이었다.
런타임 체크박스 ID는 android:id/alwaysUse였다. 원본 UI XML과 화면은 네트워크 식별
정보가 있어 Git 제외 임시 폴더에만 보관했다. 공개 기록에서는 식별값을 제거했다.
첫 기록 출력은 Windows cp949가 Wi-Fi 본문의 비분리 하이픈을 인코딩하지 못해 중단됐다.
UTF-8 출력으로 수정해 같은 창을 재조회했다. Android 설치·연결 실패와 구분한다.

잘못된 복구 토큰은 result=0, RECOVERY_REQUEST_REJECTED로 거부됐다.
자동 처리를 다시 켠 뒤 앱이 정확한 집 Wi-Fi/AP의 계속 허용 체크박스와 Allow 버튼을
처리했고 last_approval=APPROVED_KNOWN_WIFI, 실제 ADB 기기 검증 성공을 확인했다.
이때 SSH 복구 요청은 수락 result=1인데 TermuxAm이 프로세스 종료 코드도 1로 반환했다.
클라이언트가 이를 실패로 판단한 문제를 수정해 명시적 수락 응답과 종료 코드 0 또는 1을
함께 검사한다. 기록 123의 SSH_RECOVERY_REQUEST_ACCEPTED=False는 수정 전 관측값이다.

수정 후 화면을 끄고 adb_wifi_enabled를 한 번 0으로 설정했다. SSH RPC를 거쳐
약 9초 뒤 ADB가 다시 연결됐다(124). 이후 화면을 다시 끄고 15초 간격 8회 연결 검사를
통과했으며 새 SSH 연결도 정상이다. 최종 라이브 상태의 interactive=false도 확인했다.
신뢰 저장의 현재 Wi-Fi/AP 일치를 확인했지만 부팅 keyStore 오류의 근본 원인은 미확정이다.
시스템 신뢰 파일을 수정하거나 페어링을 초기화하지 않았다.

### 재부팅의 드래그 잠금과 사용자 요청에 따른 해제

첫 0.4.0 재부팅(125)에서는 SSH가 복구됐으나 ADB가 바로 연결되지 않았다.
복구 RPC는 수락됐지만 wifi_adb=0이었다(127). 사용자는 Wi-Fi 허용창이 떠 있으며,
재부팅의 드래그 잠금화면을 직접 밀어 해제하자 앱이 즉시 허용했다고 보고했다.
실제 앱 로그도 그 시점의 허용 완료를 확인했다(128). 235초 뒤 ADB 연결 성공은
사용자의 잠금화면 해제 도움이 포함된 결과로 바로 정정했다. 15초 간격 8회까지
연결을 확인한 뒤 시험을 중단했고 5분·화면 꺼짐 단계 완료로 기록하지 않았다.

이는 암호·패턴 잠금이 없는 것과 드래그 화면까지 없는 상태를 구분해야 한다는 근거다.
이 관측이 신뢰 파일 파싱 오류의 원인까지 확정하는 것은 아니다.
PC 도구도 복구 요청 수락 후 실제 ADB가 나타날 때까지 30초 이상 간격·최대 8회 내에서
재시도하도록 고쳤다. 요청 수락을 실제 연결 성공으로 취급하지 않는다.

사용자가 드래그 잠금화면을 직접 없애거나 해제해 달라고 명시적으로 요청했다.
이 요청에 따라 확인된 A50에서 locksettings get-disabled=false, 비밀번호 인자 없는
locksettings verify 성공을 확인한 뒤 locksettings set-disabled true를 실행했다(129).
설정 재조회는 true다. 암호·패턴·PIN을 입력·변경·초기화하지 않았고 clear 명령도 쓰지 않았다.
추가 잠금 해제 권한을 관리 APK에 넣는 대신 Android의 잠금 없음 설정을 사용했다.
반복 부팅에서도 유지되는지와 수동 조작 없는 자동 연결은 새 시험(130)으로 검증한다.
사용자가 요청한 잠금 없는 시험 서버 조건이며 보안 잠금을 다시 설정한 조건은 별도다.

두 번째 정상 재부팅(130)에서는 사용자 화면 조작 없이 ADB를 새 포트로
발견하고 기존 기기 정보를 검증했다. 명령 뒤 5초를 기다려 시작한 발견 대기는 131.7초였다. 이때 PC의 SSH 복구 요청 없이 관리 앱 부팅 복구가
동작했다. 재조회 adb_wifi_enabled=1, locksettings get-disabled=true이며 부팅 후 앱 로그에
등록 집 Wi-Fi 허용창 자동 확인 완료가 있었다. 이후 지속 연결·화면 꺼짐 후속 시험을 진행했다.

이 재부팅 도중 읽기 진단 업로드는 SSH 준비 전 연결 거부로 한 번 실패했다(131).
복구 뒤 추가한 KeyguardManager 읽기 진단은 일반 Termux app_process에서 WindowManager
서비스 객체가 없어 NullPointerException으로 실패했다(132). 잠금 상태 판단 근거로 쓰지 않았다.
추가 진단을 제외하고 기존 읽기 전용 진단은 다시 정상이다(118). 접근성 서비스 활성화,
flags=80, 버전 0.4.0과 설정 권한을 확인했다. 실제 잠금 없음 유지 판단은 ADB의
locksettings get-disabled=true와 손대지 않은 재부팅에서의 허용 완료를 사용했다.

로컬 기기 선택·RPC 응답·수락 후 실제 연결까지의 재시도 검사 11개와 Wi-Fi/AP 정책
14개, Android 관련 Python 정적 검사를 통과했다(126). 실제 0.4.0 관리 화면을 한 장 더
보존했다. 새로운 원본 Wi-Fi 허용창 캡처는 식별값이 있어 비공개 임시 폴더에만 둔다.

### 최종 검증 결과

130의 수동 조작 없는 재부팅 후 ADB 15초 간격 20회, 총 5분 검사를 모두 통과했다.
그 뒤 홈 화면으로 보내고 화면을 끈 상태의 15초 간격 8회, 총 2분 검사도 통과했다.
Termux partial wake lock, adb_wifi_enabled=1, 잠금 없음 true와 새 SSH 응답을 확인했다.
최종 읽기 점검(133)도 서비스 실제 연결·화면 꺼짐 interactive=false·SSH 정상이며
부팅 로그에 SSH_START_COMMAND_COMPLETED가 있다. 실물 설치 소스는 0.4.0이며 체크섬은 122에서 일치했다.

따라서 같은 집 Wi-Fi·충전·암호 없는 조건의 초기 자동 관리 검증은 완료다.
24시간, 네트워크 단절·DHCP 변경·새 AP·외부 사설망, PIN/패턴 추가 조건은 미검증이다.
앱 정리·중앙 API·FCM은 아직 실행하지 않았다. load average가 높게 유지되는 원인도
이 단계에서 해결됐다고 기록하지 않는다. 다음 단계의 측정·정리 대상으로 남긴다.

최종 공개 자료 점검(134)은 실제 접속 값·토큰·네트워크 식별값 0건, A50 TXT/PNG
누락 0건, 1편의 이미지 연결 누락 0건이었다. 비공개 설정·원본 작업 폴더의 Git 제외를
확인했고 전체 이미지 175개의 PRIVATE_METADATA_COUNT=0도 확인했다.
