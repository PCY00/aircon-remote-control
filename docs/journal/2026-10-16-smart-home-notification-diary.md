# 2026-10-16 스마트홈 알림 일기

## 색은 정리됐는데 화면 구성이 별로라는 말을 들었다

　전날 밤 어두운 원형 다이얼로 바꾼 가족 앱 0.6.1 캡처를 보고, 00:01에 사용자가 "UI는 깔끔해졌는데 UI 구성도 별로"라고 했다. 캡처를 다시 보니 색과 모양만 바뀌었고 화면 배치는 예전 앱 그대로였다.

- 제목이 두 번씩 나왔다. 홈에는 집 이름 아래 "우리 집 한눈에", 조작 화면에는 "에어컨 조작" 아래 "거실 에어컨"이 또 있었다. 카드마다 비슷한 안내문도 붙어 있었다.
- 에어컨 조작 화면이 한 화면에 안 들어갔다. 최근 요청 카드가 다이얼을 아래로 밀어서 운전 모드부터는 스크롤해야 보였고, 상세 화면인데 하단 탭바까지 있어 아래가 좁았다.
- 앱을 열면 집 목록부터 나와서 집이 하나여도 매번 "집 열기"를 한 번 더 눌러야 했다.
- 홈의 "최근 기록"이 기록 탭과 겹쳤다.

## 다른 앱을 참고한 구성안 네 가지를 보여줬다

　00:02에 사용자가 다른 앱들을 참고해서, 지금 구조에 얽매이지 말고 추천안을 여러 개 보여 달라고 했다. 시안에 넣을 기능이 실제와 맞는지 먼저 확인했다. 장치 프로필에 절전(`economy`)·터보·스윙이 있고 앱에도 해당 버튼이 있었다. 반면 가족 앱에는 자동화를 만들거나 고치는 화면이 없다.

　모든 안에 공통으로 넣은 원칙은 마지막에 쓴 집으로 바로 열기, 위쪽에서 집 바꾸기, 에어컨 조작은 스크롤 없이 한 화면, 상세 화면에서는 탭바 숨기기, 겹치는 제목과 안내문 빼기였다.

| 안 | 참고한 앱 | 구성 |
|---|---|---|
| 1 | Google Home, Nest | 홈 위쪽 즐겨찾기 타일에서 바로 ± 온도 조절. 누르면 전체 화면 다이얼 조작 |
| 2 | Apple 홈 | 집 상태 요약 칩과 공간별 타일. 타일을 누르면 세로 슬라이더 조작 시트 |
| 3 | SmartThings, LG ThinQ | 기기 카드 목록이 첫 화면. 기기 상세 안에 조작과 그 기기 기록 탭 |
| 4 | 토스 같은 국내 생활 앱 | "거실은 26.2°예요" 같은 한 문장 상태, 큰 빠른 실행 버튼, 오늘 타임라인. 세부 조절은 아래 시트 |

　2안의 "자동화" 탭은 지금 앱에 없는 기능이라, 고르면 기록 탭으로 바꿔야 한다. 사용자는 아직 고르지 않았다.

## 어두운 다이얼 0.6.1 정식 빌드는 끝났지만 쓰지 않는다

　전날 밤 시작한 0.6.1 정식 빌드(단위 테스트 포함)가 `FAMILY_APK_BUILD=PASS`로 끝났다. 하지만 이 빌드는 구성을 바꾸기 전 화면이라 바탕화면으로 옮기거나 설치하지 않았다. 구성안이 정해지면 그 구조로 다시 만들고 검사한 뒤 넘긴다.

## 확장성이 없다는 말을 듣고 바탕 구조부터 다시 잡았다

　사용자가 나중에 전등 제어와 여러 센서가 추가될 걸 생각하면 네 안 모두 확장성이 없고, 알림도 여러 종류가 올 거라며 다시 생각해 오라고 했다. 맞는 말이었다. 네 안 모두 에어컨 하나와 센서 둘에 맞춰 화면을 짰다.

　코드를 다시 읽어 보니 문제는 화면보다 아래에 있었다. 중앙 서버의 기기 표는 기기 ID와 이름만 저장한다. 알림 설정도 문·온습도·경고 세 칸으로 고정돼 있어서 새 센서가 생기면 표와 앱 화면을 함께 고쳐야 한다. 반면 Pi의 장치 프로필(`profile.json`)에는 이미 전원·모드·온도 범위 같은 기능 목록이 있고, Pi 센서 표에도 공간 이름이 있다. 다만 Pi 연결 서비스는 개인정보 때문에 공간 이름을 서버로 보내지 않는다.

　그래서 공통 바탕 두 가지를 먼저 정하고 그 위에 첫 화면 세 안을 그렸다.

- 기능 블록: 기기를 전원·밝기·색온도·설정온도·모드·바람·측정값·열림 감지·움직임·누수·배터리 같은 블록의 조합으로 본다. 타일과 상세 화면은 블록을 쌓아서 자동으로 만든다. 전등이 들어와도 새 화면을 만들지 않는다.
- 알림 체계: 알림을 안전·보안·기기·환경·정기 보고·자동화·가족 종류로 나누고, 종류마다 긴급·알림·조용히·끔 중 하나를 고른다. 계속되는 상태(문 열림 지속, 응답 없음, 배터리)는 알림 센터 위에 고정했다가 해결되면 사라지게 하고, 같은 기기의 반복 알림은 한 줄로 접는다. 방해 금지 시간에는 긴급만 울린다.

| 안 | 참고한 앱 | 첫 화면 |
|---|---|---|
| 1 공간 중심 | Apple 홈, Google Home | 종류별 모아보기 칩, 즐겨찾기, 공간별 타일 |
| 2 종류 중심 | SmartThings, Home Assistant | 조명·냉난방·보안·환경·안전·전력 카드와 "모두 끄기" 같은 묶음 동작 |
| 3 상황 중심 | Ring, Nest, 아파트 월패드 | 지금 확인할 것, 빠른 실행, 켜져 있는 기기만 |

　1안에 3안의 "지금 확인할 것" 영역을 넣는 쪽을 추천했다. 공간과 기기 종류 어느 쪽이 늘어도 버티고, 알림이 주인 이 앱에서 해결 안 된 일을 첫 화면에 보여줄 수 있기 때문이다. 빠른 실행과 자동화 탭은 지금 가족 앱에 없는 기능이라 나중 단계로 표시했다. 사용자는 아직 고르지 않았다.

## 안 1에 확인할 것 영역을 넣기로 하고 공통 형식부터 정했다

　사용자가 안 1(공간 중심)에 "지금 확인할 것" 영역을 넣는 안으로 진행하라고 했고, 공간 이름은 Pi에서 보내라고 했다. 공간 이름이 Pi 밖으로 나가는 것은 이번에 사용자가 직접 승인한 범위다. Zigbee 주소나 MQTT 원본 내용은 계속 보내지 않는다.

　서버·Pi 연결 서비스·앱이 같은 형식을 쓰도록 먼저 결정 문서 `docs/decisions/0019-capability-inventory-and-alert-levels.md`를 썼다.

- Pi가 `PUT /v1/hub/inventory`로 기기 목록(이름, 공간, 종류, 기능 블록, 현재 상태, 마지막 보고 시각)을 보낸다. 바뀌었을 때와 5분마다 보내고, 간격은 최소 15초다.
- 서버는 모르는 종류·블록도 형식만 맞으면 받는다. 전등 같은 새 기기를 붙일 때 서버를 고치지 않기 위해서다.
- 센서 ID는 Zigbee 이름 대신 Pi 안에서만 아는 값으로 해시한 32자를 쓴다. 문·온습도 기록에도 같은 ID를 붙여 앱이 기록에 기기 이름을 보여줄 수 있게 했다.
- 알림은 안전·보안·기기·환경·정기 보고·자동화·가족 일곱 종류와 긴급·알림·조용히·끔 네 단계로 바꾼다. 예전 앱이 쓰는 문·온습도·경고 설정도 계속 받는다.
- 방해 금지 시간은 휴대폰 시계 기준으로 앱에서 처리한다.

　그다음 A50 중앙 서버(0.7.0, DB 스키마 7), Pi 연결 서비스(0.7.0), 가족 앱 0.6.1 화면 재구성을 나눠서 동시에 만들기 시작했다. 배포는 셋 다 로컬 테스트를 통과한 뒤 A50 서버, Pi, 앱 순서로 한다. 새 Pi가 보내는 기기 목록을 예전 서버가 거절하기 때문에 이번에는 A50 서버를 먼저 올려야 한다.

## 서버와 Pi 연결 서비스를 먼저 만들고 올렸다

　A50 서버와 Pi 연결 서비스 작업이 먼저 끝났다. 서버 쪽 테스트는 596개가 통과했고 3개는 건너뛰었다(전날 464개). 작업 중에 원래 있던 버그도 하나 찾았다. 에어컨 이름에 짝 없는 서로게이트 문자가 섞이면 제어 heartbeat가 500 오류로 끝났다. 이런 문자는 지우고 거절하도록 고치고 테스트를 추가했다. 앱 작업은 사용량 한도에 걸려 멈췄다가 03시 20분에 한도가 풀린 뒤 이어서 진행했다.

　배포는 A50 서버부터 했다. `deploy_a50_central.py`로 미리보기를 한 뒤 반영했고, 설치 도구가 DB를 백업한 다음 0.7.0으로 바꿨다. 스키마는 7이 됐다. 집 2·허브 1·가족 2·설치 4는 그대로였고, 기록은 배포 사이 들어온 것까지 1,044건이었다. 휴대폰 4대의 예전 알림 선택은 새 중요도 표 12행으로 옮겨졌다. 서버 신원 지문이 이전과 같고 `roomrelay.top` 상태 확인이 200인 것도 봤다. 처음에 지문 확인 명령은 가상환경 경로를 잘못 줘서 127로 실패했고, 경로를 고쳐 다시 실행했다. 예전 Pi 연결 서비스의 heartbeat는 새 서버에도 계속 들어왔다.

　이어서 Pi 연결 서비스 0.7.0을 `deploy_central_agent.py`로 올렸다. 03:24에 다시 시작한 뒤 로그에 `INVENTORY_SENT devices=3`이 찍혔다. A50에도 에어컨·문 센서·온습도 센서 3개가 들어왔다. 에어컨의 공간은 거실로 왔지만 두 센서는 Pi에서 공간을 정하지 않아 "공간 미지정"으로 왔다. 재시작 직후 제어 연결 경고가 한 번 있었고 반복되지는 않았다.

　확인 도구 `verify_central_agent.py`는 A50 쪽 검사 하나에서 멈췄다. A50의 예전 허브 연결 기록 파일에 원래 키 값이 아직 남아 있다는 검사다. 이번 배포 전부터 있던 상태이고, 지우는 일은 등록 정보 삭제라 사용자 확인을 받기로 했다. 기록 파일은 `server/docs/assets/terminal/252`~`264`번이며 PNG도 함께 만들었다.

## 앱을 다시 만들고 A50에서 직접 눌러 봤다

　앱 작업이 끝났다. 홈은 "지금 확인할 것", 종류별 모아보기, 즐겨찾기, 공간별 3열 타일 순서다. 아래 탭은 홈·알림·설정 세 개로 줄였고 기록 탭은 알림 탭에 합쳤다. 앱을 열면 집 목록을 거치지 않고 마지막으로 연 집으로 바로 들어간다. 기기 화면은 기능 블록을 쌓아서 그린다. 알림 설정은 일곱 종류 × 네 단계와 방해 금지 시간으로 바꿨다. 예전 서버이면 제어 목록과 최근 기록으로 기기를 만들어 보여주도록 했다. 단위 확인은 88개로 늘었고 모두 통과했다.

　A50 안에서만 도는 가상 서버(가상 계정, 가상 기기 4개, 배터리 15% 센서)를 띄우고 시험 앱을 설치해 화면을 눌러 봤다. 처음에는 A50이 옆으로 놓여 있어 화면이 가로였다. 세로 기준으로 짠 스와이프 좌표가 화면 밖을 가리켜서 스크롤이 안 됐고, 기기 화면이 열리지 않은 채 뒤로 가기를 눌러 앱이 닫혔다. 자동 회전 설정은 기기 설정이라 바꾸지 않았다. 대신 캡처 도구가 화면 크기를 읽어 좌표를 정하고, 대상이 안 보이면 스크롤하며 찾게 고쳤다.

　다시 찍은 화면에서 실제 버그 두 개를 찾았다.

- 공간 이름 줄만 나오고 그 아래 기기 타일이 하나도 안 보였다. UI 덤프를 보니 타일 줄 높이가 1픽셀이었다. 한 줄에 기기가 3개보다 적으면 남는 칸을 높이 1픽셀 빈 칸으로 채우는데, 타일은 "부모 높이에 맞춤"이라 줄 높이 계산에서 빠졌다. 가상 데이터는 공간마다 기기가 1~2개라 모든 줄이 이 경우였다. 타일이 자기 내용 높이를 쓰도록 바꾸자 타일이 나왔다.
- "현관문"이 공간 이름 "현관"을 뗀 "문"으로 보였다. 공간 이름은 띄어쓰기로 떨어진 경우에만 떼도록 바꾸고 단위 확인을 추가했다.

　설정 화면에서 "방해 금지 시간"이 부제목과 스위치 이름에 두 번 나와서 스위치 이름을 "정한 시간에는 조용히 받기"로 바꿨다. 고친 뒤 다시 찍어서 홈·에어컨·종류별·문 센서·배터리 부족 센서·알림·설정·집 바꾸기 화면이 모두 열리는 것을 봤다. 알림 탭에서 문 기록 두 건이 "현관문 열림·닫힘 2번"으로 접히고, 끔으로 둔 정기 보고 3건이 숨겨지는 것도 봤다. 가상 서버는 끝난 뒤 멈췄고 실제 서비스와 DB는 바뀌지 않았다.

　정식 APK 0.6.1(빌드 번호 11)을 다시 빌드했고 `verify_family_apk.py` 검사를 통과했다. 디버그가 꺼져 있고 시험용 자료가 없는 것도 확인했다. 바탕화면 `가족-스마트홈-v0.6.1.apk`로 복사했고 해시가 빌드본과 같다. 가로 화면 사진 9장을 `server/docs/assets/hardware/family-app/` 36~44번으로 넣었고 사진 메타데이터 검사는 0건이었다. 앱 README와 루트·서버 README, `server/docs/aircon-app-control.md`의 버전 표기를 고쳤다. `server/MANIFEST.json`은 519개 항목으로 다시 만들었다. 마지막으로 돌린 테스트는 서버 596개(3개 건너뜀), 루트 221개였다.

　남은 일:
- 가족 휴대폰과 A50에 0.6.1 설치는 아직이다. 설치 뒤 실제 집 화면과 실제 FCM 수신을 확인해야 한다.
- 세로 화면에서 에어컨 화면이 스크롤 없이 들어가는지는 계산만 했고 실측하지 않았다. A50을 세로로 세우거나 회전 고정을 허락받으면 다시 찍는다.
- Pi의 문 센서와 온습도 센서 공간이 "공간 미지정"이다. Pi 화면에서 공간을 정하면 앱에 공간별로 나뉜다.
- A50의 예전 허브 연결 기록 파일에 키 원문이 남아 있다. 지우는 일은 사용자 확인 뒤에 한다.
- 노션 연결 도구가 없어 이 기록은 노션에 저장하지 못했다.


## 새 변경을 확인하고 공개할 파일을 골랐다

　사용자가 새로 올라온 내용과 일기를 확인하고 GitHub에도 올려 달라고 했다. 개인정보는 올리지 말라고 했다. 기존 로컬 기록을 읽고 중앙 서버·Pi 연결 서비스 0.7.0과 가족 앱 0.6.1의 변경을 확인했다. 공간별 기기 목록, 기능 블록에 따른 화면, 일곱 알림 종류와 네 중요도, 방해 금지 시간, 마지막 집 바로 열기가 추가됐다. 새로 만든 서버·기기 목록 API와 예전 앱을 위한 호환 처리도 확인했다.

　노션의 실제 날짜 위치를 읽어 16일 안에 일기와 스마트홈 알림 페이지를 만들었다. 로컬에만 있던 오늘 새벽 기록을 옮겼고, 15일에 빠진 보안 수정·배포·UI 작업 기록도 15일 페이지에만 이어 적었다. 다른 프로젝트의 일정과 완료 체크는 바꾸지 않았다.

　현재 코드의 확인 결과는 Pi 쪽 221개, 서버 쪽 596개(환경에 맞지 않는 3개 건너뜀), 웹 화면 54개, Android 단위 확인 88개 통과였다. Android 가상 서버용 빌드도 성공했다. 이전에 전달한 정식 APK는 바꾸지 않았고 보관본과 해시가 같은 것을 확인했다. 이번에는 운영 서버 배포·앱 설치·에어컨 조작·기기 재부팅을 하지 않았다.

　글과 코드에서 실제 비공개 설정값·키를 찾지 못했다. 처음 걸린 항목은 시스템 서비스 이름, 가짜 시험 주소·시험 이메일, 오류 출력의 메모리 주소였다. 메모리 주소는 공개 캡처에서 가리고 PNG를 다시 만들었다. 사진 633장의 위치·촬영 정보는 0건이었다. 새 화면 사진은 직접 읽었고 가상 계정 표시만 있는 것도 확인했다. 블로그를 따라 할 코드 251개도 공개 검사를 통과했다.

　추가 실행 기록에는 예전 A50 허브 기록의 키 원문이 이미 제거된 결과가 있었다. 다른 작업에서 끝낸 일로 구분했고 이번 게시 작업에서 키나 등록 정보를 지웠다고 쓰지 않았다. 기존 로컬 수정과 브랜치를 보존하려고 원격 main에서 업로드용 복사본을 만들었다. 비공개 설정·키·DB·APK는 복사하지 않았다. 게시 결과는 확인한 뒤 아래에 이어 쓴다.


## GitHub main에 올리고 원격 결과를 확인했다

　공개 후보에서 해결하지 못한 개인정보 항목은 0건이었다. 시스템 서비스 이름과 가짜 시험 자료 때문에 걸린 항목은 실제 정보와 구분했다. 작성자에는 GitHub의 비공개 이메일 표기를 사용했다. 비밀번호·SSH 키·Firebase 설정·FCM 전송 키·허브 키·개인 노션 경로 캐시·실제 DB·APK는 올리지 않았다.

　게시 준비 중 들어온 에어컨 부가 기능 줄바꿈 수정도 새 사본에 넣고 앱을 다시 빌드했다. 단위 확인 88개와 빌드가 통과했다. Git에 저장될 실제 파일과 목록의 해시를 비교하니 Windows 줄바꿈 때문에 84개가 맞지 않았다. 내용은 유지하고 줄바꿈을 맞춘 뒤 `server/MANIFEST.json`을 공개 파일 기준으로 다시 계산해 불일치가 0개인 것을 확인했다.

　코드·README·연결 그림·공개용 사진·설치와 오류 해결 기록을 GitHub main에 올렸다. Git의 원격 main과 GitHub API에서 읽은 커밋이 게시한 커밋과 같은 것을 확인했다. 이번 코드 게시 커밋은 `5e8f96983745`다. 게시 결과만 읽는 명령과 실제 출력은 `docs/assets/terminal/382-smart-home-github-publication.txt`와 PNG로 남겼다. 이 일기와 게시 확인 자료도 같은 저장소에 이어 올린다.

　기존 로컬 브랜치와 작업 파일은 유지했다. 작성 중이어서 터미널 원문과 그림이 짝을 이루지 못한 자료는 이번 사본에 넣지 않았다. 이번 작업에서는 운영 장비를 다시 배포하거나 실제 에어컨 명령을 보내지 않았다. 가족 휴대폰의 정식 앱 설치·실제 알림 수신과 A50 전체 재부팅 시험은 별도 확인으로 남겼다.

## 허브 기록을 정리하고 세로 화면을 다시 찍었다

　아침에 사용자가 A50의 예전 허브 연결 기록은 허브 ID만 남기라고 했고, A50을 세워 뒀다고 했다. 휴대폰에는 최신 버전을 직접 설치하겠다고 했다.

　먼저 이 기록 파일을 읽는 도구를 찾아봤다. 연결 도구는 파일이 있는지만 보고, 확인 도구는 허브 ID만 읽었다. Pi는 자기 설정 파일에 키를 따로 갖고 있어서 정리해도 연결에는 영향이 없었다. A50에서 허브 ID가 DB의 사용 중인 허브와 같은지 확인한 뒤, 같은 폴더에 권한 0600으로 새 파일을 써서 바꿨다. 키 값은 출력하지 않았다. 결과는 필드가 `hub_id` 하나만 남았고, A50 서버의 다른 파일에서도 같은 키 원문은 0건이었다. 새벽에 멈췄던 `verify_central_agent.py`도 다시 돌렸고 Pi와 A50 두 단계가 모두 통과했다(`PROVISIONING_RECORD=hub_id_only`).

　A50 화면이 세로(1080×2340)로 바뀐 것을 확인하고, 가상 서버를 다시 띄워 시험 앱 화면을 모두 다시 눌러 봤다. 에어컨 화면은 세로에서 스크롤 없이 한 화면에 들어가는 것을 이번에 실제로 확인했다. 다만 부가 기능 버튼 줄의 마지막 "표시등 바꾸기"가 오른쪽 끝에서 잘려 있었다. 옆으로 밀면 보이는 줄이었지만 아래 공간이 넉넉해서 두 줄로 넘기게 바꿨다. 바꾼 뒤에도 한 화면에 들어갔다.

　사용자가 막 0.6.1을 설치하려는 중일 수 있어서 바탕화면 0.6.1 파일은 그대로 두었다. 이 수정을 넣은 앱은 0.6.2(빌드 번호 12)로 따로 만들었다. 단위 확인 88개와 APK 검사를 통과했고 `가족-스마트홈-v0.6.2.apk`로 바탕화면에 두었다. 세로 사진 9장을 `server/docs/assets/hardware/family-app/` 45~53번으로 넣었다. 앱 README 표는 세로 사진으로 바꾸고 가로 사진은 36~44번으로 남겼다. 사진 메타데이터 검사는 0건이었고, `server/MANIFEST.json`은 552개 항목으로 다시 만들었다.

　A50 DB를 읽기만 해서 보니 휴대폰 한 대가 새 앱으로 등록돼 일곱 종류 알림 설정이 저장돼 있었다. 새 중요도 API가 실제 휴대폰에서도 동작한 것이다. 어느 버전을 설치했는지는 서버에서 알 수 없다.

　같은 시간에 다른 작업이 원격 main 복사본으로 GitHub 게시를 하고 있었다. 이 폴더의 파일 몇 개가 동기화로 수정 시각만 바뀐 것을 보고 내용이 그대로인지 확인했다. 이 단락의 0.6.2 변경과 세로 사진은 그 게시 뒤에 생긴 로컬 변경이다.

　남은 일: 휴대폰에서 시험 알림과 실제 문 열림 알림이 오는지 확인하기, Pi 화면에서 문·온습도 센서의 공간 정하기. 0.6.2 변경과 세로 사진은 아직 커밋하지 않았다.

## iPhone 가족도 홈 화면 웹앱으로 쓸 수 있는지 물어봤다

　사용자가 초대한 가족이 iPhone을 쓰면 웹으로 홈 화면에 추가해서 열 수 있는지 물었다. 중앙 서버 코드를 확인해 보니 `roomrelay.top`의 첫 화면은 상태 표시 페이지 하나이고 나머지는 앱용 API뿐이었다. Pi 웹 화면은 Tailscale 안에서만 열리므로 초대한 가족이 쓸 수 없다. 그래서 지금은 iPhone에서 쓸 방법이 없다고 답했다.

　같은 API를 쓰는 웹앱을 만들면 가능하다고 정리했다. 확인이 필요한 점은 세 가지였다. iOS 16.4 이상에서 홈 화면에 추가한 웹앱만 푸시를 받을 수 있다. Safari의 Google 로그인은 리디렉션 방식에 제약이 있다. 웹 푸시는 받은 알림을 숨길 수 없어서 방해 금지 시간을 서버에서 처리해야 한다. 아직 만들지는 않았다.


## 0.6.2 추가 변경과 세로 사진의 공개 준비를 했다

　사용자가 개선된 내용을 확인하고 일기를 쓰며 GitHub에도 올려 달라고 했다. 원격 main과 현재 파일을 비교했다. 부가 기능 버튼 줄바꿈 코드는 이전 게시에 이미 들어 있었고, 이번에는 앱 버전 0.6.2·빌드 번호 12, README의 세로 사진과 설명, 허브 기록 정리·빌드·화면 확인 자료가 추가됐다. 운영 서버의 실행 코드는 이전 게시와 같았다.

　세로 사진 아홉 장을 직접 읽었다. 에어컨의 다섯 부가 기능 버튼과 아래 전송 버튼이 한 화면에 있었고 가상 계정·가상 집 표시가 있었다. 실제 계정이나 접속 주소는 보이지 않았다. 정식 앱 빌드에 들어간 실행 코드와 현재 코드가 같은 것도 확인했다. 최신 빌드의 단위 확인 결과와 APK 서명·권한, 공개할 파일의 개인정보·사진 위치 정보를 이어 확인한다.

　이번 작업에서는 휴대폰 설정·허브 등록·운영 DB를 바꾸거나 Pi와 A50에 다시 배포하지 않았다. 앞서 다른 대화에서 끝낸 허브 키 정리와 화면 시험은 남아 있는 실행 자료를 읽어 확인한 일로 구분했다. iPhone 웹앱 질문도 오늘 기록에 이어 넣으며, 웹앱 구현을 완료한 것으로 적지 않았다.


## 0.6.2 빌드 결과와 공개 자료를 확인했다

　완성된 정식 빌드의 결과 파일을 읽어 단위 확인 88개가 실패 없이 통과한 것을 확인했다. 현재 실행 코드와 빌드 사본의 내용도 같았다. 이번에 빌드 도구·공개 묶음·허브 기록 확인 관련 테스트 42개를 다시 돌렸고 모두 통과했다. APK의 서명·알림 권한·시험 자료 제외·HTTPS 설정 확인도 다시 통과했다.

　앞선 기록에는 0.6.2를 바탕화면에 뒀다고 되어 있었지만, 이번에 읽었을 때는 0.6.1 파일만 있었다. APK 안의 버전을 읽어 기존 파일은 0.6.1·빌드 번호 11이고 정식 빌드 결과는 0.6.2·12인 것을 확인했다. 기존 파일은 유지하고 확인한 정식 0.6.2를 `가족-스마트홈-v0.6.2.apk`로 다시 복사했다. 복사본과 정식 파일의 해시는 같다.

　사진 655장의 위치·촬영 정보는 0건이었다. 새 세로 화면 사진에는 실제 계정과 접속 정보가 없었다. 확인 명령과 실제 결과를 `docs/assets/terminal/383-family-app-062-publication-checks.txt`와 PNG로 남겼고, APK 확인 원문도 `server/docs/assets/terminal/284-a50-family-apk-verification.txt`와 PNG로 남겼다. 공개할 복사본의 비공개 정보와 Git에 들어갈 실제 파일 해시를 마지막으로 확인한 뒤 게시한다.


## 0.6.2 공개 사본의 마지막 결과를 확인했다

　공개 후보 1,792개 파일에서 실제 설정값·개인정보·키를 찾지 못했다. 가짜 개인정보 차단 시험 자료와 시스템 서비스 이름은 실제 계정 정보와 구분했다. 사진의 위치·촬영 정보도 남아 있지 않았다. Git에 저장될 파일과 `server/MANIFEST.json` 554개 항목을 비교했을 때 기록 두 개가 Windows 줄바꿈 때문에 달랐다. 내용은 유지하고 줄바꿈과 해시 목록을 맞춘 뒤 불일치가 0개인 것을 확인했다.

## 0.6.2 추가 변경을 GitHub main에 올렸다

　가족 앱 0.6.2·빌드 번호 12, 세로 화면 아홉 장, README와 설치 설명, 허브 기록 정리·앱 빌드·이번 확인 자료를 GitHub main에 올렸다. 코드 게시 커밋은 `82ab55b9ed30`다. Git 원격 main과 GitHub API를 각각 읽어 같은 커밋이 올라간 것을 확인했다. 이번 추가 게시의 변경 파일은 40개였다.

　노션에는 오늘의 기존 스마트홈 알림 페이지를 그대로 사용해 빠진 기록과 이번 이슈·해결·결과를 이어 적었다. 이전 기록과 다른 날의 일정은 유지했다. 개인정보·비밀 키·실제 DB·APK는 GitHub에 올리지 않았다. 새 APK는 로컬 바탕화면에 별도로 두었다. 이번 작업에서 운영 장비에 다시 배포하거나 휴대폰에 앱을 설치하지 않았다.

　남은 일은 가족 휴대폰에서 실제 시험 알림과 문 열림 알림을 받아 보기, Pi에서 문·온습도 센서의 공간을 정하기다. iPhone용 웹앱은 질문과 방향만 정리했고 구현하지 않았다. 이번 게시 결과와 일기도 이어 커밋한다.

　이어서 비용이 드는지 물었다. 기존 기록에서 Firebase 프로젝트가 결제 수단 없는 Spark 무료 요금제인 것과, 13일에 확인한 `roomrelay.top` 다음 해 갱신 가격(약 5,400원, 바뀔 수 있음)을 다시 읽었다. 웹앱으로 만들면 Apple 개발자 등록비와 Mac이 필요 없고, Google 로그인·FCM·Cloudflare 터널은 지금처럼 무료라 새로 드는 비용은 없다고 답했다. iPhone 전용 앱으로 만들면 Apple 개발자 등록비가 매년 들고 Mac이 필요하다는 점도 구분했다.

## iPhone용 홈 화면 웹앱을 만들기 시작했다

　사용자가 iOS용 웹앱을 만들어 달라고 했다. 먼저 형식을 `docs/decisions/0020-ios-home-screen-web-app.md`에 정했다.

- A50 서버가 `https://roomrelay.top/app/`에서 웹앱을 직접 내준다.
- 화면과 규칙은 Android 앱 0.6.2와 같게 한다. 소유자 관리 기능은 1차에서 빼고 Android 앱에서 하도록 안내한다.
- Safari가 다른 도메인의 로그인 저장소를 막기 때문에 로그인 도메인을 `roomrelay.top`으로 두고, `/__/auth/` 요청을 Firebase로 전달한다.
- Firebase 웹 SDK는 2주가 넘은 12.19.0을 받아 웹앱 폴더에 넣는다. 9일 전에 나온 13.0.0은 쓰지 않는다.
- iPhone 웹 푸시는 받은 알림을 숨길 수 없다. 그래서 방해 금지 시간은 서버가 휴대폰 시각 기준으로 확인해 보내지 않는다.

　서버 0.8.0(DB 스키마 8)과 웹앱 화면을 나눠 동시에 만들기 시작했다. 실제 로그인을 하려면 사용자가 Firebase와 Google Cloud 콘솔에서 웹 앱 등록, 허용 도메인 추가, 리디렉션 주소 추가를 해야 한다. 실제 iPhone 확인은 초대받은 가족의 휴대폰으로 한다.

　서버 0.8.0과 웹앱이 끝났다. 서버에는 웹앱 파일 제공, `/__/auth/` 로그인 전달, 서버 방해 금지 시간(`PUT /v1/installations/<id>/quiet-hours`, DB 스키마 8), FCM 웹 푸시 설정이 들어갔다. 웹앱은 Android 앱과 같은 홈·에어컨·알림·설정 화면을 그리고, 계산 규칙은 Android 단위 확인을 옮긴 Node 테스트 96개로 확인했다. 배포 도구는 웹앱의 PNG 아이콘이 줄바꿈 변환으로 깨지지 않도록 글자 파일만 변환하게 고쳤다. 테스트가 실수로 만든 빈 `C:	mp` 폴더는 지웠다.

　웹앱 쪽에서 문제가 하나 나왔다. Firebase 리디렉션 로그인은 `https://apis.google.com/js/api.js`를 페이지에 불러오는데, 서버의 웹앱 보안 정책이 같은 출처 스크립트만 허용해서 브라우저가 막았다. 이대로면 실제 iPhone에서 로그인이 끝나지 않는다. 정책에 `https://apis.google.com` 하나만 더 허용하고 결정 문서에도 예외로 적었다. 웹앱 테스트 파일에 토큰처럼 보이는 문자열이 있어 공개 묶음 검사가 실패한 것도, 실행할 때 만들도록 바꿔 통과시켰다.

　PC에서 실제 서버 코드로 가상 데이터 서버를 띄우고 브라우저를 아이폰 크기(390×844)로 맞춰 눌러 봤다. 홈, 에어컨, 알림, 설정이 Android와 같은 구성으로 나왔고 에어컨 화면은 스크롤 없이 들어갔다. 1도 올려 보내니 확인 창을 거쳐 "방금 · 냉방 25° · 전달됨"으로 바뀌었다. 콘솔 오류는 없었다. 화면 4장을 `server/docs/assets/hardware/family-web/`에 넣었다.

　테스트는 서버 729개(4개 건너뜀), 웹앱 96개, 웹 설정 도구 8개가 통과했고 공개 묶음 검사도 통과했다. A50에 서버 0.8.0을 사전 안내 뒤 배포했다. DB는 스키마 8이 됐고 집·허브·가족·설치 수는 그대로였으며 서버 지문도 같았다. `roomrelay.top/app/`과 `/__/auth/handler`는 200이었다. `/app/config.json`은 Firebase 웹 설정을 아직 넣지 않아 503 `web_not_configured`였다. 이건 예상한 결과다.

　남은 일: 사용자가 Firebase 웹 앱 등록, 로그인 허용 도메인 추가, OAuth 리디렉션 주소 추가를 하면 `set_a50_web_config.py`로 설정을 넣는다. 그 뒤 초대받은 가족의 iPhone으로 로그인과 알림을 확인한다. 안내는 `server/docs/ios-web-app.md`에 있다.

## 콘솔 설정을 마치고 웹앱 로그인 페이지까지 확인했다

　사용자가 Firebase 웹 앱 등록, 허용 도메인 추가, OAuth 리디렉션 주소 추가를 마쳤다고 했다. 사전 안내 뒤 `set_a50_web_config.py --apply`를 실행해 PC에 붙여넣기 창을 띄웠고, 사용자가 설정을 붙여넣었다. 도구는 웹 앱 프로젝트가 서버 프로젝트와 같은 것을 먼저 확인했다(`PROJECT_ID_MATCHES_SERVER=TRUE`). 그다음 기존 설정을 백업하고 `web_app` 항목을 넣은 뒤 서버를 다시 시작했다. 값은 출력하지 않았고, 서버가 돌려주는 웹 설정이 넣은 값과 같다는 결과만 남겼다(`APP_CONFIG_MATCHES=TRUE`).

　공개 주소 `roomrelay.top/app/config.json`이 200을 돌려주는 것을 확인했다. 로그인 도메인은 `roomrelay.top`이었다. 브라우저를 아이폰 크기로 맞춰 웹앱을 여니 로그인 화면이 나왔다. "Google로 계속하기"를 누르자 Google 로그인 페이지로 넘어갔고, 화면에 "roomrelay.top(으)로 이동", 돌아올 주소에 `https://roomrelay.top/__/auth/handler`가 보였다. 리디렉션 주소 오류는 없었다. 계정 입력은 사용자 몫이라 여기서 멈췄다.

　남은 일: 실제 로그인 뒤 홈 화면 확인, iPhone 홈 화면 추가와 알림 받기 확인.

　사용자가 아이폰에서 웹앱을 설치하는 순서를 물어 단계별로 정리해 답했다. 초대는 소유자가 Android 앱에서 가족의 Google 이메일로 만든다. 홈 화면 앱은 Safari와 로그인 정보를 따로 보관하므로 홈 화면 아이콘으로 연 뒤에 로그인해야 한다는 점도 넣었다.

　이어서 위젯으로도 쓸 수 있는지 물었다. Android 앱에는 홈 화면 위젯을 추가로 무료로 만들 수 있다고 답했다. 아이폰은 웹앱이 위젯을 만들 수 없고, 위젯은 정식 iOS 앱(Apple 개발자 등록비와 Mac 필요)에서만 된다. 무료로 비슷하게 하려면 단축어 위젯이나 Scriptable 같은 앱에 위젯 전용 제한 키를 넣는 방법이 있지만, 서버에 새 키 기능이 필요하고 키 관리 부담이 생긴다고 구분했다. 아직 만들지 않았다.


## iPhone 웹앱 변경과 연결 그림을 확인하기 시작했다

　사용자가 업데이트를 확인해 GitHub에 올리고 오늘 일기도 쓰되 개인정보는 올리지 말라고 했다. 이어서 README의 연결 그림도 새 구조에 맞게 바꿔 달라고 했다. 이전 게시 이후 파일을 비교하니 중앙 서버 0.8.0·DB 스키마 8, iPhone 홈 화면 웹앱과 웹 로그인 보조 경로, 서버 방해 금지 시간, 배포 도구와 실행 자료가 추가돼 있었다. Android 앱 실행 코드는 이번 변경에 없었다.

　웹앱·서버 코드와 이전 대화의 배포·설정 실행 자료를 읽었다. 이번 게시 작업에서 운영 장비를 다시 배포하거나 설정·계정을 바꾼 것으로 적지 않았다. 웹앱 Node 확인 96개는 모두 통과했고 서버 전체 확인은 진행 중이다. 연결 그림에는 Android APK와 iPhone 홈 화면 웹앱, A50이 웹 화면과 로그인 보조 경로를 내주는 일, 기기 목록 전송과 웹앱 방해 금지 시간을 넣었다. 실제 iPhone 로그인과 푸시 수신은 아직 남아 있음을 함께 표시했다.


## README 전체와 설치 안내를 현재 구조에 맞췄다

　사용자가 GitHub 안의 내용, 특히 README를 모두 최신 상태로 바꿔 달라고 했다. 공개 README 27개와 관련 설치·사용 문서를 찾아 읽었다. 최신 코드가 0.4.0이라고 적힌 시작 안내, 임시 주소를 현재 주소로 설명한 앱·Pi 안내, 아직 고정 주소와 허브 연결이 없다고 적힌 서버 설명을 고쳤다. 현재 중앙 서버 0.8.0·DB 8, Android 0.6.2, Pi 연결 서비스 0.7.0과 iPhone 웹앱 범위가 이어지게 했다. 예전 실험은 당시 기록임을 표시했다.

　연결 그림을 SVG와 PNG로 다시 만들었다. Android와 iPhone을 따로 표시하고 A50의 웹 화면·로그인 보조 경로, Pi의 기기 목록과 공간 전송, 웹앱 방해 금지 시간을 넣었다. 직접 그림을 읽고 선이 글자를 가리는 곳도 고쳤다. 웹앱 사용 안내는 홈 화면에 추가한 뒤 그 아이콘으로 열어 로그인하는 순서로 바꿨다. 실제 iPhone 로그인·푸시 수신은 확인하지 못한 범위로 남겼다.

　서버 전체 확인은 729개 통과·4개 건너뜀이었고 웹앱은 96개가 통과했다. 문서 변경 뒤 자료 묶음 관련 확인 34개도 다시 통과했다. 새 코드 링크 하나가 자료 묶음에서 끊긴 것으로 나와 실제 파일 링크로 고쳤고, 웹 도구와 그림 생성기도 자료에 포함했다. 자료 309개의 개인정보 검사와 README의 파일 링크 220개 확인이 통과했다. Firebase SDK 원본 해시도 고정값과 같았다.

　새 배포 캡처와 예전 확인 캡처에서 서버 지문을 발견했다. 비밀 키는 아니지만 이 서버를 식별하는 값이라 두 캡처의 원문과 PNG에서 가렸다. 처음에는 예전 캡처에 같은 값의 다른 표기가 남아 공개 검사가 멈췄고 그 표기도 함께 가렸다. 실제 계정·키·DB·비공개 설정과 노션 위치 캐시는 공개하지 않는다. 이번에는 운영 장비에 다시 배포하지 않았다. 확인 원문은 `docs/assets/terminal/384-ios-webapp-and-documentation-checks.txt`와 PNG로 남긴다.


## 공개할 코드와 문서의 마지막 상태를 확인했다

　수정한 README와 사용 안내, 연결 그림을 공개 사본에 모았다. 새 변경은 118개 파일이었다. 공개 사본 전체에서 실제 설정값·계정·키를 찾지 못했고, 이번 변경 파일도 따로 확인해 남은 항목이 0개였다. 가짜 차단 시험 자료와 시스템 서비스 이름은 실제 개인정보와 구분했다. 서버 지문의 두 표기도 공개 원문과 그림에서 제거했다.

　Git에 들어갈 실제 파일 624개와 해시 목록이 모두 같았다. Windows에서 내려받을 때 줄바꿈이 바뀌어 고정 SDK 해시가 달라지지 않도록 서버 텍스트는 LF로 받게 했다. 이미지 바이트와 원본 SDK의 확인된 공백은 유지한다. 공개 사본의 SDK 해시도 다시 통과했고 연결 SVG가 생성 코드와 같은 것도 확인했다. 운영 설정·키·DB·APK는 넣지 않았다. 노션 저장과 GitHub 원격 결과는 게시 뒤 한 번 더 읽어 확인한다.


## iPhone 웹앱과 전체 안내 업데이트를 GitHub에 올렸다

　중앙 서버 0.8.0·iPhone 웹앱 코드와 README·설치 안내·연결 SVG/PNG·공개 캡처·일기를 GitHub main에 올렸다. 코드 게시 커밋은 `c3a5fa7588c3`다. Git 원격과 GitHub API를 각각 읽어 같은 커밋인 것을 확인했다. 현재와 맞지 않는 안내를 고쳤고, 기록 당시 버전의 실험 자료는 시점을 알 수 있게 유지했다.

　마지막 비교에서 줄바꿈 규칙을 추가하며 기존 PowerShell·이미지 규칙 일부를 덮어쓴 것을 발견했다. 기존 규칙을 복원하고 서버 텍스트의 LF와 SDK 공백 예외만 더했다. 실제 속성을 읽어 PowerShell은 CRLF, SDK는 LF, PNG는 바이너리로 처리되는 것을 확인했다. 이 수정과 게시 결과를 이어 올린다.

　오늘 노션의 스마트홈 알림 일기에 빠진 웹앱 작업·설정 과정, 이번 문서와 그림 수정·실패 원인·해결·게시 결과를 이어 적었다. 비공개 설정·계정·키·실제 DB·APK와 노션 위치 캐시는 올리지 않았다. 실제 iPhone 로그인·홈 화면 추가·푸시 수신, 가족 휴대폰의 실제 문 알림과 장시간 운영은 남아 있다. 이번 게시 작업에서 운영 장비를 다시 배포하거나 물리 에어컨 명령을 보내지 않았다.
