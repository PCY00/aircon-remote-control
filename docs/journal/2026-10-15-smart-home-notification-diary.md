# 2026-10-15 스마트홈 알림 일기

## 로그인 뒤 결제가 멈춘 이유를 확인했다

　앞서 고른 `roomrelay.top`을 구매하려고 로그인까지 했지만 다음에 어떻게 진행하는지 모르겠다고 했다. 오늘 한국시간 날짜를 확인하고 15일 일기의 실제 위치를 읽었다. 13일에 찾아본 가격과 결제 안내는 이전 배경으로 두고 오늘 확인한 화면을 따로 기록했다.

　현재 Spaceship 장바구니에는 도메인 1개와 등록 기간 `1 year`, 무료 개인정보 보호가 표시됐다. 위에는 `Before we proceed, a couple of things...` 안내가 있었고 `Domain Contacts` 아래에 `Info required`가 보였다. 도메인 소유자 연락처가 비어 있어 다음 단계로 넘어가지 못한 상태였다. 결제 수단 오류라고 확인된 것은 아니다.

　`Edit`을 열고 `Add Address Required`를 눌러 `Add your first address` 양식까지 열었다. 이름·성·주소·국가·지역·도시·우편번호·이메일·전화번호 등을 입력하는 칸과 `Save` 버튼을 확인했다. 주소를 저장한 뒤 앞의 `Domain contacts` 창에서 `Apply`를 눌러야 장바구니에 반영되는 흐름이었다. 소유자와 관리·기술·청구 연락처를 같은 주소로 쓰는 체크는 이미 켜져 있었다. 회사 주소 체크와 팩스는 개인 구매에 맞춰 구분해 안내했다.

　본인 정보는 사용자가 사이트에 직접 입력하도록 안내했다. 실제 연락처·주소·결제 정보는 읽어 다른 곳에 옮기거나 대신 입력하지 않았다. 개인정보가 비어 있는 양식 화면만 `server/docs/assets/domain/2026-10-15-domain-contact-required.jpg`에 남겼다. 주소 저장과 구매 결제, 도메인 등록 완료는 아직 확인 전이다. 서버나 DNS 설정은 바꾸지 않았다.

## 요청받은 주소를 입력하고 결제 버튼을 다시 보이게 했다

　이어서 사용자가 집 주소를 알려주며 직접 입력해 달라고 했다. 처음에는 건물명과 상세 호수만 있어 도로명주소를 물었다. 상세주소와 도시를 먼저 입력했고, 도로명주소를 받은 뒤 거리 주소와 지역을 영문으로 입력했다. 국가도 대한민국으로 골랐다. 각 입력칸에 의도한 내용이 들어갔는지 비교해 확인했다. 실제 이름·주소·호수·이메일·전화번호는 이 일기와 공개 자료에 옮기지 않았다. 당시 비어 있던 이메일·전화번호와 선택 우편번호는 임의로 채우지 않았다.

　사용자가 다음에 어디를 눌러야 결제되는지 다시 물었다. 현재 화면에서는 소유자 정보가 도메인의 모든 연락처에 연결된 것을 확인했다. 구매 버튼이 안 보이는 이유는 장바구니의 항목 선택으로 `Bulk Actions` 모드가 켜져 있었기 때문이었다. `Close Bulk Actions`를 눌러 닫자 화면 아래에 `Checkout`과 합계 1.60달러가 나타났다. 사용자가 이어서 결제 단계로 이동하는 동안 `Add payment method Required`, `Pay now`와 PayPal 연결 대기 안내가 나타난 것도 읽었다. 결제 정보는 대신 입력하지 않았고 결제 버튼도 대신 누르지 않았다.

## 도메인 구매 완료 화면을 확인했다

　사용자가 구매를 마친 뒤 끝났는지 물었다. 주문 결과 화면의 `Made it! You’re ready to unbox and get set up` 문구와 `roomrelay.top`의 1년 등록, 실제 결제 합계 1.60달러, `Auto-renew On - Yearly`, 무료 개인정보 보호 표시를 읽었다. 구매 완료는 확인됐고 자동 갱신은 켜진 상태였다. 지금 표시된 갱신 가격이 영구히 유지된다고 보장하지 않았다.

　구매 뒤 뜬 `Unbox`와 무료 체험 추천은 추가 상품 안내였다. 새 상품을 연결하거나 신청하지 않고 안내창과 개인 이메일이 표시된 알림만 닫았다. 완료 문구와 도메인·등록 기간·금액이 보이도록 화면 위로 이동해 `server/docs/assets/domain/2026-10-15-roomrelay-top-purchased.jpg`에 사진을 남겼다. 공개용 사진에 실제 이름·주소·이메일·주문 식별값은 넣지 않았다.

　도메인 구매는 끝났지만 A50 서버에 고정 주소를 붙이는 작업은 아직 남아 있다. Cloudflare 연결·네임서버 변경·정식 터널 전환은 하지 않았다. 현재 운영 서버 주소가 새 도메인으로 바뀌었다고 표시하지 않았다.

## 고정 주소 연결을 시작하고 요청 흐름을 그림으로 나눴다

　구매한 도메인을 A50에 연결해 달라는 요청을 받았다. 기존 Cloudflare 계정을 그대로 쓰고, 다른 서비스는 건드리지 않기로 했다. 공식 안내에서 무료 플랜의 도메인 연결과 터널 방식, 비공개 토큰 파일로 실행하는 방법을 읽었다. A50의 현재 중앙 API가 정상 응답하고 기존 시험 터널의 관리 파일 8개가 배포 당시와 같은 것을 확인했다. 아직 A50과 Pi 설정은 바꾸지 않았다.

　Cloudflare에 `roomrelay.top`을 추가하고 무료 플랜을 골랐다. 기존 주소 기록 두 개가 자동으로 읽혔고, Cloudflare에서 지정한 네임서버 두 개를 확인했다. 이 단계까지는 도메인의 실제 주소 관리 서버를 바꾸지 않았다. 기존 시험 주소는 계속 살아 있었다.

　사용자가 앱·도메인·Cloudflare·A50·Pi가 어떻게 이어지는지 모르겠다고 했다. 실제 코드의 요청 방향을 따라 벡터 그림과 PNG를 만들었다. 앱은 Cloudflare를 거쳐 A50으로 요청을 보내고 A50은 로그인과 집별 권한을 확인한다. Pi는 중앙 서버에 먼저 접속해 대기 중인 명령을 가져간다. 문·온습도 기록은 반대 방향으로 올라오고, 휴대폰 알림은 A50에서 FCM을 거쳐 따로 전달되는 것으로 그렸다. 도메인 구매처는 주소 구매와 갱신만 맡는다고 덧붙였다. 그림에는 고정 연결이 아직 설정 중이라고 표시했다.

　그림 파일은 `server/docs/architecture/connection-flow.svg`와 `server/docs/architecture/connection-flow.png`에 두었다. 실제 연결을 마친 뒤 상태 표시와 설명을 갱신하고 README에도 넣을 예정이다.

## 주소 관리 서버를 바꾸고 A50 전용 터널을 연결했다

　도메인의 DNSSEC가 이미 켜져 있어 주소 관리 서버 이전 전에 처리가 필요했다. 브라우저 안전 규칙에 따라 DNSSEC를 이전 동안 잠시 해제하고 네임서버를 바꾼 뒤 다시 켜는 일, A50 전용 터널 연결 키와 공개 경로를 만드는 일을 한 번에 확인받았다. 사용자가 이 범위로 적용하겠다고 답했다.

　Spaceship에서 DNSSEC를 해제한 뒤 Cloudflare가 지정한 두 네임서버를 저장했다. 저장 완료 안내와 전파 중 표시를 확인했다. PC의 일반 DNS 조회에서는 처음에 서버 오류가 나왔지만, 이어 Google 공개 DNS 조회에서는 Cloudflare 네임서버 두 개와 이전 DS 기록이 없는 결과를 받았다. 새 주소가 모든 곳에서 바로 동작한다고 표시하지 않았다.

　A50용 `roomrelay-a50` 터널을 만들었다. 연결 키는 화면이나 로그에 출력하지 않고 비공개 전송 파일을 거쳐 A50 설정에 넣었다. 명령행에는 키 내용 대신 비공개 파일 경로만 전달하도록 했다. 기존 시험 터널과 별개로 실행하는 `aircon-fixed-tunnel` 서비스를 로컬에서 준비하고 관련 자동 확인을 실행했다. 21개가 통과했고 Windows에서 표현할 수 없는 Unix 파일 권한 확인 1개는 건너뛰었다. 미리보기 뒤 실제 배포를 실행해 소스와 실행 파일의 해시가 같은 것을 확인했다. Cloudflare 화면에도 연결 성공과 Healthy가 표시됐다.

　중앙 서버의 저장 파일, 집·가족 등록, SSH 자동 시작 설정과 기존 시험 연결은 유지했다. 아직 새 도메인의 공개 경로와 HTTPS 접속, Pi 주소 전환, DNSSEC 재연결은 남아 있다. 그림과 쉬운 설명을 `README.md`, `server/README.md`, `server/docs/connection-flow.md`에 넣었다.

## 고정 주소로 접속하고 Pi 연결과 재시작 후 주소를 확인했다

　Cloudflare에 도메인에서 A50 내부 API로 보내는 공개 경로를 저장했다. 처음에는 터널이 연결돼 있어도 HTTPS 확인을 통과하지 못했다. 화면의 경고를 읽어 보니 DNS 기록 자동 생성에 실패한 상태였다. 기본 안내 페이지용 A 기록 두 개가 같은 이름을 쓰고 있었다. 원래 값을 비공개 복구 자료에 남긴 뒤 터널용 CNAME으로 바꿨다. 다시 접속하니 HTTPS 인증서와 준비 응답이 정상이고 로그인 없는 계정·집 조회, 잘못된 로그인 증명은 401로 차단됐다. 집 두 개와 허브 한 개, 중앙 서버의 저장소 식별 정보가 유지된 것도 확인했다.

　Pi의 준비 확인은 처음에 403을 받았다. Python 기본 요청 표시와 우리 프로그램 이름을 넣은 요청을 같은 주소로 비교했더니 뒤쪽만 200을 받았다. Cloudflare 내부의 정확한 차단 규칙까지 알아낸 것은 아니다. 보안 기능을 끄지 않고 Pi의 알림 전송과 명령 조회 요청에 프로그램 이름을 넣었다. 연결 설정 확인 도구에도 같은 용도의 표시를 넣었다.

　로컬 Pi 연결 코드에는 아직 배포하지 않은 센서 알림 빈도 제한·재시도 수정 등이 더 있었다. 이번 주소 연결과 섞어 배포하지 않도록 현재 운영 코드가 관리 기록과 같은지 먼저 확인했다. 그 운영 코드에 요청 표시 두 군데만 추가한 로컬 배포본을 준비했다. 다른 로컬 수정은 보존했다. 관련 자동 확인은 59개 통과, Windows와 맞지 않는 3개 건너뜀으로 끝났다. 배포할 작은 버전에서도 알림 전송과 명령 조회의 인증 헤더·요청 표시를 직접 확인했다. 새 자동 확인의 준비 값이 빠진 부분과 기존 운영 버전의 200 응답에 맞지 않던 시험 응답은 고쳐 다시 실행했다. 실제 배포 뒤에는 Pi 코드와 준비한 파일의 해시가 같았다.

　Pi의 기존 허브 키를 유지한 채 중앙 서버 주소만 바꾸고 연결 서비스를 다시 시작했다. 24초 동안 계속 실행 상태였고, A50에서는 활성 제어 허브 한 개와 기기 한 개가 보였다. 기존 Pi 웹앱과 센서 DB를 교체하거나 다시 시작하지 않았다. 인증 없는 제어와 가짜 허브 키는 401로 차단됐다. 에어컨에 물리 명령은 보내지 않았다.

　Cloudflare에서 DNSSEC를 다시 켜고 새 DS 값을 Spaceship에 등록했다. 저장 성공 안내와 Cloudflare의 보호 완료 문구를 확인했다. 공개 DNS 조회에서도 DS 기록과 인증된 주소 응답이 확인됐다. 실제 주소·연결 키·계정 이메일·터널 식별값을 공개 자료에 옮기지 않았고, 공개 도메인 이름만 설명에 사용했다.

　고정 터널을 한 번 다시 시작했다. 첫 확인 스크립트에는 모듈 가져오기가 빠져 있어 고쳤다. 다음에는 Android에서 자식 프로세스 목록 파일을 제공하지 않아 ps로 부모·자식 관계를 읽는 방법으로 바꿨다. 두 경우 모두 새로 재시작하지 않고 읽기 확인만 이어 했다. 최종적으로 프로세스가 바뀌어도 도메인이 같고, 실제 연결 키가 프로세스 명령행에 들어 있지 않으며 A50 설정 파일은 소유자만 읽을 수 있음을 확인했다. 재시작 뒤 HTTPS와 로그인 차단도 다시 통과했다. A50 전체 재부팅 시험은 이번에는 하지 않았다.

　연결 그림의 상태를 완료로 바꾸고 SVG와 PNG를 다시 만들었다. 루트와 server의 README에 그림을 넣고, 구성 요소 설명과 주소 변경·실패·해결·실제 결과를 `server/docs/connection-flow.md`, `server/docs/fixed-server-address.md`와 외부 연결 프로그램 안내에 남겼다. PC의 임시 키 전송 파일은 제거했다. 이번에는 APK를 변경하거나 새 설치 파일을 만들지 않았다.

　남은 사용자 작업은 가족 앱의 연결 설정에 `https://roomrelay.top`을 한 번 저장하고 같은 Google 계정으로 다시 로그인해 기존 집을 보는 것이다. 실제 사용자 휴대폰에서 주소를 바꾼 결과와 새 주소를 거친 알림 수신·실물 에어컨 반응은 아직 확인하지 않았다. 전환하는 동안 기존 앱 연결이 갑자기 끊기지 않도록 Quick Tunnel은 유지했다. 다른 미배포 로컬 수정은 이번에 올리지 않았으며 GitHub에 이번 변경을 게시하지도 않았다.

## 보안 쪽을 전체적으로 살펴봤다 (다른 대화)

　같은 날 다른 대화에서 보안을 한번 봐 달라고 했다. 공격 표면별로 여섯 영역(공개 인터넷에 열린 A50 중앙 서버, Tailscale 안의 Pi API와 MQTT·Zigbee, 가족 앱, A50 관리 앱과 PC 도구, H2 펌웨어, 저장소의 비밀값)으로 나눠 읽었고, 가능한 것은 실제로 공격을 재현해 봤다. 저장소와 커밋 이력 31개 전체에서 비밀값은 없었고 사진 메타데이터도 없었다. SQL 주입, 경로 탐색, 명령 주입, XSS, 토큰 검증 우회, 집 간 권한 격리는 모두 막혀 있었다. 펌웨어 파서는 26만 번 퍼징해도 경계를 넘지 않았다.

　40건이 나왔고 높음 1, 중간 5, 낮음·정보 34건이었다. 가족 앱이 사용자가 붙여넣은 HTTPS 주소라면 어디든 Google ID 토큰을 보내는 점, Pi API가 `Origin`과 `Host`를 확인하지 않아 외부 웹페이지가 가족 브라우저를 통해 호출할 수 있고 업로드 총량 제한이 없는 점(다른 출처 헤더로 201이 나오는 것을 재현), 해킹된 Pi가 기록을 무한히 보내도 서버가 막지 않는 점, 설치 도구가 기본으로 디버그 APK를 설치하는 점, `.deploy/`가 OneDrive 동기화 안에 있는 점이 중간 이상이었다. 결과를 반박해 보는 검증은 세션 사용 한도에 걸려 멈췄고, 중간 이상 5건은 직접 재현하거나 코드를 읽어 확인했다.

　중간 이상 전부와 코드로 고칠 수 있는 낮음까지 고치기로 했다. 앱 주소 신뢰는 서버 신원 확인 방식으로 정했다. 일곱 영역으로 나눠 고쳤다.

- Pi 앱: Host 허용 목록(`AIRCON_ALLOWED_HOSTS`), 요청 출처 검사, 본문 1MiB·업로드 용량(`AIRCON_DEVICE_REQUEST_QUOTA_BYTES`)·시간당 20회 제한, SSE 32개 상한, 문 기록 센서당 2000행, 가입 허용을 코디네이터 대상·5분 쿨다운으로, 키오스크 VT 전환 끄기, MQTT 비밀번호를 명령줄에서 빼고 앱 전용 브로커 계정과 ACL 추가.
- 중앙 서버(0.6.0, DB 스키마 6): 설치 때 만드는 서명 키와 `GET /v1/server-identity`, 허브별 분당 120·하루 20000건 제한, 집별 기록 5000건·푸시 대기 500건 상한, 사용자별 집·초대 할당량, 중첩 JSON·거대 정수 처리, 토큰 시각 60초 허용, 제어 문자 거부, FCM 토큰 선점 정책.
- 가족 앱: 처음 연결 때 서버 지문을 기억하고 주소가 바뀌어도 서명·호스트를 검증한 뒤에만 토큰을 보낸다. 지문이 다르면 막고 소유자 확인 후 다시 고정한다. JSON 파싱 보호, 초대 코드 클립보드 민감 표시.
- A50 도구·관리 앱(0.4.1): 설치 기본을 release로, 디버그 APK 거부, 화면 열릴 때 자동 복구 제거, 덤프 삭제, 빌드 임시 파일 정리, 가림 패턴 보강, ssh 사용자 검증.
- Pi 연결 서비스: 센서 토글 폭주를 합치고 온습도는 센서당 60초 간격, 문·경고를 먼저 보냄, 허브 키 원문 저장 중단, Pi 캡처 가림, 429 재시도.
- 저장소 위생: 하드코딩 경로 16개 제거, 캡처 2개 계정명 가림과 PNG 재생성, 번들 검사 패턴, `.gitignore`, Gradle 해시 고정.
- 펌웨어: 코디네이터에서 온 명령만 수락, 명령 간 2초·0.5초 간격.

　고친 코드를 다시 읽는 검토에서 7건이 더 나왔다. 온습도 보고가 서버의 하루 허용량 2000건을 평소 트래픽만으로 소진해 문 알림이 181초 늦어지는 문제, 서버 신원 엔드포인트의 전역 속도 제한으로 누구나 앱 전체를 막을 수 있는 문제, 출처를 호스트만 비교해 같은 IP의 다른 포트가 통과하는 문제 등이었다. 하루 허용량을 20000건으로 올리고 온습도 간격·우선순위를 넣었고, 속도 제한은 접속 주소별로, 출처는 스킴·포트까지 비교하도록 고쳤다. 고치는 중에 사용량 한도에 두 번 걸렸고, 풀린 뒤 멈춘 곳부터 이어서 끝냈다.

　같은 날 다른 대화가 고정 도메인 작업을 같은 폴더에서 하고 있었다. 작업 트리의 `agent.py`에 들어간 `User-Agent` 표시는 보존했고, 새 도메인 사진 11장은 메타데이터 검사를 통과했다. 새 `connection-flow.md`가 폴더와 SVG에 링크해 번들 검사가 실패해서, 폴더 링크는 그 폴더의 README로 읽고 SVG를 번들 대상에 넣었다.

　결과: 루트 테스트 221개(이전 180), 서버 464개(이전 327, 3개 건너뜀), Node 54개, 가족 앱 JVM 28개(이전 22)와 모든 빌드 종류 컴파일, 펌웨어 호스트 테스트 20개와 로컬 빌드, 사진 581장 메타데이터 없음, 번들 215개 파일 검사 통과. `server/MANIFEST.json`을 다시 맞췄다. Pi·A50 배포와 H2 굽기, 커밋은 하지 않았다. 노션 연결 도구가 없어 이 보안 기록은 노션에 저장하지 못했다.

　남은 일: Pi(앱·연결 서비스·MQTT ACL 재배포), A50(스키마 6 서버·관리 앱 0.4.1), 가족 앱 새 APK 배포를 사전 안내 뒤 진행한다. 서버를 올린 뒤 `python -m central_server.admin identity`로 지문을 읽어 앱과 비교한다. `.deploy/`를 OneDrive 밖으로 옮길지, Zigbee 설치 코드 정책, 가족 앱 README의 0.4.0 표기는 사용자가 정한다.

## 보안 수정을 Pi와 A50에 배포했다

　사용자가 정한 순서(Pi → A50 → 가족 앱)대로 사전 안내 뒤 배포했다. 고정 도메인 `roomrelay.top`을 쓰는 중이라는 점을 반영했다. 먼저 읽기 전용으로 상태를 봤다. Pi 파일 대부분은 10월 13일 배포본과 같았다. `app/automations/store.py` 하나만 첫 Git 커밋보다도 오래된 버전이었는데, Pi에서 고친 흔적이 아니라 예전 배포에서 갱신되지 않고 남은 파일로 판단해 백업 뒤 덮어썼다. A50의 배포 기록과 원격 파일 26개는 모두 같았다. 문 기록은 센서당 최대 686건, A50 기록은 1,036건이라 새 보관 상한으로 지워지는 데이터는 없었다.

　Pi에서는 코드·설정과 SQLite 일관 백업을 `runtime/backups/2026-10-15-security`에 만들고 `deploy.ps1`로 90개 파일, 보조 스크립트 6개, Zigbee 스택 파일을 올렸다. 모두 체크섬이 같았다. `setup_zigbee_stack.sh`로 ACL을 붙여 Mosquitto와 Zigbee2MQTT를 다시 만들었고, 네트워크 키 파일 해시가 전후로 같은 것을 확인했다. `setup_app_mqtt.sh`로 앱 전용 계정 `aircon-controller`를 만들고 웹앱을 새 코드로 다시 시작했다. 외부 Host는 400, 다른 출처의 요청은 403으로 막히고 같은 주소의 요청과 키오스크 화면은 200이었다.

　그런데 앱의 MQTT 연결이 `not authorised`로 거절됐다. 스크립트가 비밀번호 파일을 `mv`로 바꿨는데, Mosquitto는 그 파일 하나만 바인드 마운트하기 때문에 실행 중인 컨테이너는 예전 파일을 계속 보고 있었다. 컨테이너 안의 계정 목록에 새 계정이 없는 것으로 확인했고, `docker restart aircon-mosquitto` 뒤 새 계정으로 연결됐다. 스크립트는 같은 파일에 덮어쓰도록 고치고 테스트를 추가해 다시 올렸다. 거절은 22:54의 약 1분 동안 6번 있었다.

　Pi 연결 서비스도 새 릴리스로 바꿨다. 다른 대화에서 넣은 Cloudflare용 요청 표시는 그대로 들어 있다. 전송 대기 DB에 새 표와 열이 생겼고 A50에서 Pi의 연결 신호가 몇 초 간격으로 보였다. 이전 버전 로그에 보이던 제어 시간 초과는 22:45 이전의 기록이었다.

　A50 중앙 서버는 설치 도구가 DB를 일관 백업한 뒤 0.6.0으로 바꿨다. 스키마는 6이 됐고 집 2·허브 1·가족 2·기록 1,036·설치 4가 그대로 남았다. `https://roomrelay.top/v1/server-identity` 응답의 `host`가 `roomrelay.top`이고 서명이 유효하며 지문이 A50의 `admin identity` 출력과 같은 것을 PC에서 확인했다. 로그인 없는 요청은 401이었다. Android 앱과 같은 User-Agent는 Cloudflare를 통과했다.

　A50 관리 앱 0.4.1은 빌드했지만 설치하지 못했다. A50의 무선 디버깅은 켜져 있었으나 PC가 같은 Wi-Fi에 있지 않아 찾지 못했다. 기기에는 아무것도 바꾸지 않았다. 가족 앱은 0.6.0으로 올려 같은 서명으로 만들고 검증을 통과했다(디버그 불가, 시험용 자료 없음, HTTPS 전용). 바탕화면 `가족-스마트홈-v0.6.0.apk`에 저장했고 해시가 빌드본과 같았다. 휴대폰 설치는 하지 않았다.

　남은 일과 확인 못 한 것:
- Zigbee2MQTT 재시작(22:53) 뒤 23:06까지 센서 보고가 들어오지 않았다. 평소 저녁 간격은 2~12분이었다. 브로커 거절은 없고 앱과 Zigbee2MQTT 모두 연결돼 있어, 밤이라 센서가 보고하지 않는 것인지 더 지켜봐야 한다.
- Zigbee2MQTT는 H2 노드를 시작 시 `offline`으로 표시한다. 이번 배포 전부터 저장돼 있던 상태로 보이며 실제 명령 확인은 하지 않았다.
- 키오스크 시스템 유닛은 sudo 권한이 필요해 바꾸지 못했다. `run_kiosk.sh` 변경은 다음 재부팅 때 반영된다.
- 관리 앱 설치, 가족 휴대폰 APK 설치·지문 비교·실기기 확인, H2 펌웨어 굽기(별도 승인)가 남았다.
- 노션 연결 도구가 없어 노션에는 저장하지 못했다.

## 가족 앱 화면을 다시 그리기로 했다

## A50 무선 디버깅이 안 되던 이유를 찾았다

　화면 캡처와 관리 앱 0.4.1 설치를 하려고 A50에 무선 adb로 붙으려 했지만 실패했다. SSH는 되는데 adb만 안 됐다. adb는 무선 디버깅 포트를 mDNS 광고로 찾아야 하는데, 95초 동안 A50의 광고가 한 번도 보이지 않았다. Termux 권한으로는 A50 쪽 포트도 읽을 수 없었다.

　사용자가 무선 디버깅은 켜져 있고 포트 번호를 알려줬는데 "페어링된 기기가 없다"고 했다. 이게 원인이었다. A50에 PC 페어링 기록이 없어서 포트로 TCP 연결은 돼도 TLS 인증에서 거절되고 있었다. 예전 페어링 기록이 A50 쪽에서 지워진 것으로 보인다.

　사용자가 페어링 창의 포트를 알려준 뒤 `pair_wireless_adb.py`의 가려진 입력창으로 코드를 직접 넣게 했다. 23:48에 `paired`로 끝났고 페어링 IP가 SSH로 쓰던 A50 주소와 같은 것도 확인했다. 사용자가 채팅에 보낸 6자리 코드는 쓰지 않았다. 이어서 접속한 기기의 일련번호·모델이 저장된 A50과 같은지 확인한 뒤 관리 앱 0.4.1을 설치했다. 설치, 권한 부여, 절전 예외 등록, 화면 실행이 모두 `EXIT_CODE=0`이었다. 페어링 기록은 `server/docs/assets/terminal/244-a50-wireless-adb-pairing.txt`에 남겼다.

## 0.6.1 화면을 A50에서 캡처했다

　실제 서버와 섞이지 않도록 A50 안에서만 도는 가짜 서버(가상의 집·에어컨·문 기록)를 띄우고, 시험용 앱을 설치해 화면을 캡처했다. 처음에는 알림창이 내려와 있어 화면을 가렸고, 집 이름을 눌러도 집이 열리지 않아 탭이 빗나갔다. 알림창을 닫고 "집 열기" 버튼을 누르도록 바꾸니 모든 화면이 잡혔다. 캡처를 보니 바람 막대가 오른쪽으로 몰려 있고 설정 화면 알림 줄 설명이 어색해서 고친 뒤 다시 캡처했다. 가짜 서버는 끝난 뒤 멈췄고 실제 서비스와 DB는 바뀌지 않았다.

　캡처 6장을 `server/docs/assets/hardware/family-app/`에 30~35번으로 넣었고 사진 메타데이터 검사를 통과했다. README와 문서의 앱 버전 표기를 0.6.1로 맞췄다.

## 센서 보고 공백은 조용했던 것으로 확인했다

　배포 뒤 Zigbee2MQTT를 다시 띄운 22:53부터 23:08까지 센서 보고가 없던 문제는, 자정 무렵 다시 봤을 때 문 센서는 19분 전, 온습도 센서는 35분 전에 보고가 들어와 있었다. 재시작 뒤에도 센서가 정상적으로 보고하고 있었고 그 사이 보고할 변화가 없었던 것으로 판단했다.

　남은 일: 가족 앱 0.6.1 화면 구성 확정, A50과 가족 휴대폰 앱 설치, H2 펌웨어 굽기(별도 승인), 키오스크 시스템 유닛 갱신(sudo 필요). 노션 연결 도구가 없어 이 기록도 노션에는 저장하지 못했다.
