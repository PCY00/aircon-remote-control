# 2026-08-29 — 프로젝트 초기 환경 구성

## 목표

- 기존 에어컨 리모컨의 IR 신호를 Raspberry Pi 4B에서 캡처하고 재생한다.
- 제어 웹/API는 포트 `8001`에서 제공한다.
- 외부 접근은 공유기 포트포워딩 없이 Tailscale을 사용한다.
- 로컬 폴더를 기준본으로 두고 승인된 시점에만 Raspberry Pi로 배포한다.

## 확인된 개발 환경

- 로컬 OS: Windows
- Python: 3.12.8
- Git: 2.51.0.windows.1
- OpenSSH: 9.5p2
- Raspberry Pi: Raspberry Pi 4B, Raspberry Pi OS 64-bit Lite
- Raspberry Pi SSH 호스트: `AC` (사설 IP는 공개 문서에 기록하지 않음)

인증 비밀번호는 제공받았지만 프로젝트 파일과 이 기록에는 저장하지 않았다.

## 리모컨 판별 결과

- PCB의 투명 LED에 `IR1` 표기가 있다.
- IR LED 구동용 `Q1` 트랜지스터와 주변 저항을 확인했다.
- MCU 표기는 Sino Wealth `SH66P51F-AE031`이다.
- PCB 표기는 `R51D/E(SH66P51F-044FR).D.20.YP2-1`, 버전은 `V1.8`이다.
- RF 송수신부가 보이지 않아 단방향 IR 리모컨으로 판정했다.
- 반송파 주파수와 데이터 프로토콜은 아직 측정하지 않았다.

## 소프트웨어 결정

- Python과 FastAPI/Uvicorn으로 API 골격을 구성한다.
- UI 구현 전에 `/`와 `/health`로 포트·서비스 운영 환경을 검증한다.
- 로컬 개발은 `127.0.0.1:8001`을 사용한다.
- Raspberry Pi의 실제 바인딩과 방화벽은 Tailscale 구성과 함께 확정한다.

## 로컬 검증 중 발견한 호환성 변화

초기 테스트 2개는 통과했지만 Starlette 1.6.0이 기존 `httpx` 테스트 경로에 사용 중단 예정 경고를 냈다. 공식 문서에서 `httpx2`가 새 테스트 클라이언트 의존성임을 확인해 개발 의존성을 교체했다. 단순히 경고를 숨기지 않고 향후 호환 경로로 전환했다.

## 로컬 검증 결과

- FastAPI: 0.141.1
- Uvicorn: 0.52.4
- Starlette: 1.6.0
- httpx2: 2.12.0
- 테스트: 2개 통과, DeprecationWarning을 오류로 취급해도 통과
- Ruff 정적 검사: 통과
- 실제 서버: `127.0.0.1:8001` 기동 성공

검증 후 개발 서버는 정상 종료했다. 아직 Raspberry Pi에는 연결하거나 파일을 전송하지 않았다.

## Raspberry Pi 읽기 전용 점검

사용자가 제공한 주소의 호스트명이 `AC`로 확인됐다. 사설 IP는 블로그 공개 가능성을 고려해 기록하지 않았다.

- Raspberry Pi 4 Model B Rev 1.4, 2GB
- Debian 13.5 Trixie 64-bit, arm64
- Python 3.13.5
- 저장 공간 26GB 여유
- 온도 36℃, 스로틀링 없음
- SSH 정상, 포트 8001 미사용
- `python3-venv`, `rsync`, `curl`, `gpiod`, `v4l-utils`, `ir-ctl` 설치됨
- Git, Tailscale, LIRC 사용자 도구는 설치되지 않음
- GPIO 장치는 존재하지만 LIRC 장치와 IR 오버레이는 없음
- 프로젝트 대상 경로와 서비스는 아직 존재하지 않음

SSH 호스트 키 자동 조회가 실패해 Ping과 TCP 22를 분리 확인한 뒤 대화형 SSH로 접속했다. 이 진단 과정은 `docs/troubleshooting.md`에 별도로 정리했다.

프로젝트 전용 SSH 키를 Windows에 만들고, 사용자가 공개키를 Raspberry Pi의 `authorized_keys`에 추가했다. 이후 키 접속에서 개인키 passphrase를 요구하는 문제가 발생했다.

비밀번호 인증으로 다시 읽기 전용 접속해 Pi 측을 점검한 결과 `.ssh` 권한은 `700`, `authorized_keys` 권한은 `600`, 소유자는 `air:air`로 정상이다. 등록된 ED25519 공개키 지문도 PC의 공개키 지문과 일치했다. 따라서 공개키 복사나 Pi 권한 문제가 아니라 Windows 개인키에 예상하지 못한 passphrase가 설정된 것이 원인이다. 진단 중 Pi 파일과 시스템 설정은 변경하지 않았다.

사용자 승인 후 기존 키를 보존한 채 암호 없는 `airconpi` 전용 ED25519 키를 새로 생성했다. 새 공개키만 `authorized_keys`에 추가했으며 기존 키는 삭제하지 않았다. 등록 후에도 `.ssh`는 `700`, `authorized_keys`는 `600`, 소유자는 `air:air`로 유지됐다. 마지막으로 암호나 passphrase 입력을 허용하지 않는 `BatchMode` 접속을 사설 IP와 호스트명 `AC` 양쪽에서 실행했고 모두 성공했다. 이로써 7단계 환경 구성 계획 중 1단계인 SSH 공개키 인증을 완료했다.

## 2단계: Raspberry Pi 프로젝트 경로 생성

사용자 승인 후 Pi에 `/home/air/aircon-controller` 디렉터리를 만들었다. 디렉터리는 `air:air` 소유이며 권한은 `755`다. 이 단계에서는 코드 전송, 패키지 설치, 서비스 변경을 수행하지 않았다.

첫 확인 명령에서는 `stat` 형식의 `%n`을 줄바꿈으로 오해해 경로가 항목마다 반복됐다. 생성 작업에는 영향이 없었으며 `readlink -f`와 단순화한 `stat` 명령으로 절대 경로, 디렉터리 형식, 권한과 소유자를 다시 확인했다. 이로써 7단계 계획 중 2단계를 완료했다.

## 3단계: 런타임 코드 전송

실제 전송 전에 로컬 테스트 2개와 Ruff 검사를 다시 실행해 모두 통과했다. 처음 산출한 전체 후보는 약 13.4MB였지만 대부분이 블로그용 리모컨 원본 사진 5장이었다. Pi 운영에 필요하지 않은 사진·문서·가상환경·캐시·실제 환경 변수 파일을 제외하고 실행에 필요한 파일 10개, 총 7,499바이트만 전송 대상으로 확정했다.

반복 가능한 단방향 동기화를 위해 `scripts/deploy.ps1`을 추가했다. 기본 실행은 파일 목록·크기·SHA-256만 보여주는 미리보기이며, 사용자 승인을 받은 뒤 `-Apply`를 지정해야 전송한다. 원격 파일 삭제 기능은 없고, 전송 후 로컬과 Pi의 파일별 SHA-256을 비교한다.

사용자 승인 후 `/home/air/aircon-controller`로 10개 파일을 전송했고 모든 SHA-256이 일치했다. `scripts/run_pi.sh`는 Pi에서 실행할 수 있도록 권한 `755`, 소유자 `air:air`로 확인했다. 전송 후 `.venv`, 실제 `.env`, `__pycache__`가 모두 없음을 확인했으므로 Python 가상환경과 의존성을 다루는 4단계는 아직 시작하지 않았다. 이로써 7단계 계획 중 3단계를 완료했다.

## 4단계: Python 가상환경과 런타임 의존성

사용자와 명령을 한 단계씩 확인하며 프로젝트 경로에 `.venv`를 생성했다. 시스템 Python에 패키지를 설치하거나 `sudo pip`를 사용하지 않았고, 가상환경을 활성화한 뒤 `python -m pip install -e .`로 프로젝트를 편집 가능 모드로 설치했다. 이 방식은 이후 승인된 코드 동기화가 즉시 반영되며 의존성 정의가 바뀌었을 때만 재설치하면 된다.

설치된 핵심 버전은 Python `3.13.5`, FastAPI `0.141.1`, Uvicorn `0.52.4`, Starlette `1.6.0`이다. `pip check` 결과는 `No broken requirements found.`였다. 사용자는 Uvicorn을 `127.0.0.1:8001`에 임시 실행하고 SSH를 통해 Pi 내부 `/health` 확인 단계를 진행한 뒤 서버를 종료했다. 후속 읽기 전용 검사에서 8001에 프로세스가 남아 있지 않음을 확인했으며 자동 실행 서비스와 Tailscale은 아직 구성하지 않았다.

후속 검사 중 Windows→SSH→Python으로 중첩한 버전 출력 명령의 따옴표가 깨져 `SyntaxError`가 한 번 발생했다. 환경 문제가 아니라 진단 명령 작성 문제였으며, 단순한 `pip show` 명령으로 바꿔 버전을 재확인했다. 이로써 7단계 계획 중 4단계를 완료했다.

## 5단계: Tailscale 설치와 Tailnet 연결

설치 시점의 Tailscale 공식 문서를 다시 확인하고 자동 설치 스크립트 대신 저장소 구성이 보이는 수동 설치 절차를 선택했다. `/etc/os-release`에서 `ID=debian`, `VERSION_CODENAME=trixie`를 확인했기 때문에 Raspbian 저장소가 아니라 Debian Trixie stable 저장소를 사용했다.

공식 서명키를 `/usr/share/keyrings/tailscale-archive-keyring.gpg`에 저장하고 `/etc/apt/sources.list.d/tailscale.list`를 추가했다. `apt-get update` 중 Debian 저장소의 Version 값이 `13.5`에서 `13.6`으로 바뀌었다는 알림이 나왔지만 오류가 아니며, 패키지 목록 갱신만으로 운영체제가 자동 업그레이드된 것은 아니다. 이번 범위에서는 전체 시스템 업그레이드를 수행하지 않았다.

Tailscale `1.102.3`을 설치하고 기존 PC와 같은 Tailnet으로 Pi를 인증했다. 후속 읽기 전용 검사에서 `tailscaled`가 enabled·active이고, Tailscale IPv4가 할당됐으며 백엔드 상태가 `Running`임을 확인했다. 실제 Tailscale IP, 계정 이메일과 일회용 인증 URL은 기록하지 않았다.

상태 확인 과정에서 명령 앞에 작은따옴표가 한 번 붙어 Bash 보조 프롬프트 `>`가 나타났다. `Ctrl+C`로 미완성 명령을 안전하게 취소하고 다시 실행해 해결했다. 또한 자동 검증 명령에서 PowerShell의 `$()`가 원격 셸보다 먼저 해석되는 문제가 재발해, 원격 결과를 각각 받아 로컬에서 값 자체를 숨긴 채 검증하는 방식으로 교체했다. 이로써 7단계 계획 중 5단계를 완료했다.

## 6단계: 포트 8001 사용자 서비스 자동 실행

사전 점검에서 포트 8001은 비어 있고 사용자 systemd는 실행 중이었지만, 서비스 파일은 설치되지 않았고 `air` 사용자의 linger는 꺼져 있었다. 로컬 서비스 초안은 Tailscale IPv4를 실행 시 조회해 해당 주소에만 Uvicorn을 바인딩하며, 주소가 없으면 종료해 systemd의 재시도 정책을 사용하도록 설계돼 있었다.

사용자 승인 후 `/home/air/aircon-controller/runtime`을 권한 `750`으로 만들고 배포된 unit 파일을 `~/.config/systemd/user/aircon-controller.service`에 권한 `644`로 설치했다. `sudo loginctl enable-linger air`를 적용하고 사용자 systemd 설정을 다시 읽은 뒤 서비스를 enabled·active 상태로 시작했다. 재부팅은 승인 범위에 없어서 수행하지 않았다.

검증 결과 linger는 yes, 서비스는 enabled·active, 최초 확인 시 메인 프로세스가 존재하고 재시작 횟수는 0이었다. 포트 8001은 `0.0.0.0`, loopback 또는 LAN 주소가 아니라 Pi의 Tailscale IPv4에만 바인딩됐다. Pi 내부에서 해당 주소의 `/health`를 호출해 HTTP 200과 `status=ok`를 확인했다.

첫 자동 health 검사에서는 PowerShell이 원격 명령의 `$()`를 먼저 해석해 curl만 실패했다. 서비스와 소켓은 이미 정상이었으며, Tailscale 주소 조회와 curl을 별도 명령으로 분리해 성공을 확인했다. 실제 Tailscale IP는 기록하지 않았다. 이로써 7단계 계획 중 6단계를 완료했다.

## 7단계: PC에서 Tailscale 경로 검증

Pi에서 현재 Tailscale IPv4를 읽어 형식만 검증하고 실제 값은 출력과 문서에서 제외했다. Windows PC의 Tailscale CLI로 해당 주소에 ping을 실행한 결과 성공했으며 경로는 direct였다. 이어서 SSH 터널, LAN 주소와 시스템 프록시를 사용하지 않고 PC의 `curl.exe --noproxy "*"`로 `http://<PI_TAILSCALE_IPV4>:8001/health`를 직접 호출했다.

HTTP 요청은 성공했고 응답의 `status`는 `ok`, `service`는 `aircon-controller`였다. 이로써 Tailscale에 연결된 별도 장치에서 Pi의 포트 8001 웹 API에 접근할 수 있음을 확인해 초기 7단계 환경 구성을 완료했다.

이번 PC와 Pi는 같은 물리 LAN에 있었으므로 Tailscale 주소를 사용한 암호화 경로는 검증됐지만 집 밖의 셀룰러·외부 Wi-Fi 조건을 물리적으로 재현한 것은 아니다. 실제 외부망 실증은 추후 같은 Tailnet에 연결한 휴대폰이나 외부 PC에서 동일한 `/health` 주소를 호출해 추가 확인한다. 재부팅 후 자동 복구 검증도 별도 승인 전까지 보류한다.

## Step 1 종료와 Step 2 착수

사용자와 프로젝트 단계를 다시 정의했다. 지금까지 완료한 SSH, 코드 배포, Python 환경, Tailscale, systemd와 포트 8001 검증을 Step 1 환경 구성으로 묶는다. Step 2는 기존 리모컨 신호 학습, IR 재생, Python 하드웨어 계층과 API 구현이며 Step 3은 검증된 API를 사용하는 최종 UI다.

Step 2는 장비 식별 없이 GPIO를 연결하지 않는 것부터 시작한다. 수신 학습 경로와 송신 제어 경로를 분리하고, 프로토콜 전체 해독을 기다리기보다 반복 가능한 원시 신호 캡처와 재생을 먼저 검증한다. 상세 순서와 완료 조건은 `docs/plans/step-2-ir-learning-control.md`, 설계 결정은 ADR-0003에 기록했다.

## Step 2.1: 보유 IR 모듈 사진 판독

사용자가 IR 관련 모듈 사진 3장을 제공해 원본을 `docs/assets/hardware/ir-modules/`에 보존했다. 두 장은 같은 수신 보드의 양면이며 앞면에 `IR Receiver`, 뒷면에 `HW-477 V0.2`가 확인됐다. 헤더는 앞면 기준 `GND`, `VCC`, `OUT`이고 뒷면에는 대응하는 `-`, `+`, `S`가 표시돼 있어 학습용 수신 모듈이라는 역할과 핀 이름을 확인했다.

나머지 한 장은 `IR Transmitter` 보드 앞면이다. `GND`, `VCC`, `DAT`, 투명 5mm LED, 극성 표기와 `102`, `221` 저항을 확인했다. 제공된 면에는 별도 트랜지스터가 보이지 않고 뒷면 사진이 없으므로 GPIO 직결 가능 여부, 구동 논리와 허용 전압은 확정하지 않았다.

웹에서 같은 명칭과 유사한 외형의 자료도 확인했지만 무브랜드 보드는 같은 이름으로 회로가 달라질 수 있고 정확한 제조사 회로도를 확보하지 못했다. 따라서 외부 판매 정보보다 실물 사진과 이후 전기적 확인을 우선한다. 송신기 뒷면을 확인하기 전까지 두 모듈 모두 Raspberry Pi에 연결하지 않는다.

### 판매 자료 추가 확인과 수신기 3.3V 시험 결정

사용자가 실제 구매품으로 보이는 판매 자료 두 장을 추가 제공했다. 한 자료는 수신 모듈에 1838 수신 소자를 사용하며 동작 전압 2.7–5.5V, 중심 주파수 37.9kHz라고 설명한다. 다른 자료는 같은 외형의 수신·송신 한 쌍을 5V, 38kHz 제품으로 설명한다. 수신 거리와 각도는 두 자료가 서로 달라 광고값은 신뢰 가능한 확정 사양에서 제외했다.

멀티미터가 없는 상황에서는 수신기를 5V로 구동한 뒤 출력 전압을 추측하는 방식이 위험하다. 판매 자료가 2.7V부터 동작한다고 명시하므로 수신 모듈 전체를 3.3V로 구동해 출력도 3.3V 전원 영역 안에 두는 첫 시험안을 선택했다. 수신 입력은 BCM GPIO17(물리 핀 11), 전원은 물리 핀 1의 3V3, 접지는 물리 핀 6으로 문서화했다. 배선은 Pi 전원을 끈 상태에서 사용자가 직접 수행한다.

송신 자료에는 5V, 940nm, 38kHz 구동 시 약 1.3m라고 적혀 있다. 실물의 양면에 트랜지스터가 보이지 않는다는 사용자 확인까지 더해져 GPIO가 IR LED 전류를 직접 담당할 가능성이 있으므로 직결하지 않기로 했다. Raspberry Pi 공식 문서의 3.3V GPIO 제한과 Raspberry Pi 4의 GPIO 구동 전류 사양을 근거로, 송신기는 추후 트랜지스터 또는 MOSFET 구동 회로를 설계한 뒤 시험한다.

### SN74AHCT125N 활용 검토

사용자가 5V TTL 호환 버퍼 `SN74AHCT125N`을 보유하고 있음을 확인했다. Raspberry Pi 헤더의 물리 핀 2·4는 5V 전원 레일이지만 일반 GPIO 신호는 3.3V라는 점을 구분했다. TI 데이터시트상 AHCT125는 4.5–5.5V에서 동작하고 HIGH 입력 문턱이 2.0V이므로, 3.3V GPIO 신호를 받아 5V 논리 출력으로 만드는 용도에는 맞는다.

다만 TI가 권장 동작 조건으로 제시하는 출력 전류는 채널당 8mA다. 트랜지스터가 없는 송신 보드의 220Ω IR LED 경로와 1kΩ 표시 LED 경로가 `DAT`에 직접 걸려 있다면 8mA를 넘을 가능성이 있어, 절대 최대 정격만 보고 AHCT125를 LED 드라이버로 사용하지 않기로 했다. 송신기의 실제 입력 전류를 측정하거나 별도 NPN/MOSFET 드라이버를 추가하기 전까지 AHCT125 연결은 설계 후보로만 유지한다. 수신기 3.3V 시험은 이 판단과 독립적으로 먼저 진행할 수 있다.

사용자와 최종 운영 구조도 다시 구분했다. IR 수신기는 알 수 없는 기존 리모컨 신호를 캡처하는 학습 단계에서만 필요하며, 캡처와 재생 검증이 끝나면 최종 장치에서 제거할 수 있다. 최종 운영에는 송신 회로만 남긴다.

송신부를 별도의 안정화된 5V 전원으로 공급하고 Raspberry Pi와 GND만 공통으로 묶는 방안도 유효하다. 이 경우 신호는 Pi의 3.3V GPIO에서 AHCT125 입력으로 들어가고, 5V로 구동되는 AHCT125 출력이 송신 모듈 `DAT`로 나가야 한다. AHCT125의 5V 출력을 Pi GPIO에 넣는 반대 방향은 금지한다. 또한 외부 전원은 Pi의 부하를 분리할 뿐 AHCT125의 채널당 8mA 권장 출력 한계를 늘리지 않으므로, IR LED 전류 구동 문제는 별도 트랜지스터 또는 측정으로 해결해야 한다.

### 수신기 디커플링 결정

사용자가 캐패시터를 보유하고 있어 HW-477 수신기의 전원 안정화 구성을 추가로 검토했다. 사진에서는 보조 표시 LED와 1kΩ 저항은 확인되지만 전원 디커플링 캐패시터는 명확히 보이지 않았다. 유사한 38kHz 복조 수신기의 제조사 권장 회로를 참고해, 첫 수신 시험에는 모듈 VCC와 GND 가까이에 100nF 세라믹 캐패시터를 연결한다. 배선이 길거나 실제 캡처에 잡음이 나타날 때만 10µF 전해 캐패시터를 병렬로 추가한다. OUT에는 펄스 왜곡을 막기 위해 캐패시터를 연결하지 않는다.

후속 대화에서 사용자가 질문한 대상은 수신기가 아니라 문제가 남은 송신기 쪽이었음을 정정했다. 송신부의 5V 전원 안정화에는 AHCT125 가까이 100nF 세라믹과 송신 모듈 가까이 10–47µF 전해 캐패시터를 사용할 수 있지만, 캐패시터는 AHCT125의 출력 전류 한계를 해결하지 않는다.

가장 단순한 완제품 대안도 조사했다. 공식 회로와 사용법이 공개된 Adafruit Product ID 5639는 940nm IR LED 두 개와 N채널 FET 드라이버가 실장돼 있으며 3–5V 전원과 논리 입력 세 가닥으로 동작한다. 따라서 새로 구매한다면 기존 무브랜드 송신 보드, AHCT125와 별도 전류 드라이버를 조합하는 것보다 연결과 검증이 단순하다. 비용을 우선하면 940nm LED와 NPN을 직접 구성할 수 있지만, 프로젝트의 재현성과 안전성을 우선한 구매 후보는 이 완제품으로 기록했다.

직접 조립 시 NPN 후보는 제조사 데이터시트가 명확한 ON Semiconductor `P2N2222A` TO-92로 정했다. 940nm LED는 Vishay `TSAL6200`, LED 저항은 첫 시험에서 100Ω, GPIO18과 베이스 사이 1kΩ, 베이스-GND 풀다운 10kΩ을 기본안으로 기록했다. 유사한 2N2222A 계열이라도 제조사별 핀 순서가 다를 수 있어, 실제 구매품의 데이터시트를 확인하기 전에는 물리 배선을 확정하지 않는다.

사용자가 수신기부터 개발하는 동안 `2N2222A`를 구매하는 순서를 제안했다. 공식 자료를 비교하니 원래 2N2222A에는 TO-18 금속 패키지가 있고, 플라스틱 TO-92 호환품은 PN2222A와 P2N2222A 등으로 판매된다. 전기적 성능은 이번 수십 mA IR 구동에 모두 충분하지만, 같은 제조사 계열에서도 PN2222A는 E-B-C, P2N2222A는 C-B-E로 핀 순서가 반대였다. 따라서 실제 구매 링크와 데이터시트 확인 후에만 최종 배선을 확정하는 규칙을 추가했다.

### HW-477 동봉 테스트 리모컨 PCB 발견

사용자가 HW-477과 함께 받은 긴 PCB 사진을 추가 제공했다. `LXZK-IR2101 V1.0` 표기, 끝부분의 투명 IR LED, 8핀 제어 IC, 다수 버튼 배선과 배터리 접점으로 보이는 금속 부품을 확인했다. 정확한 제조사 자료는 찾지 못했지만, 구조와 동봉 맥락상 HW-477 수신기를 시험하기 위한 배터리식 IR 리모컨 PCB로 판정했다.

이 PCB는 수신 배선과 캡처 도구의 1차 정상 여부를 실제 에어컨 조작 없이 확인하는 데 유용하다. 그러나 내장 IC가 자체 고정 코드를 생성하므로 에어컨 리모컨 신호를 대신하지 못하고 최종 Raspberry Pi 송신기로도 사용하지 않는다. 배터리 종류와 버튼 배열은 반대쪽 사진을 확보한 뒤 확인하며, 그전에는 5V나 GPIO를 직접 연결하지 않는다.

### HW-477 첫 배선 완료

Raspberry Pi 전원을 끈 상태에서 사용자가 HW-477 수신기를 직접 연결했다. 모듈 쪽은 `S=노랑`, `+=흰색`, `-=검정`이며, Raspberry Pi 쪽은 `GPIO17/물리 11=노랑`, `3V3/물리 1=흰색`, `GND/물리 9=검정`으로 확인했다. 원래 계획한 GND 물리 핀 6은 듀얼 팬 전원 커넥터가 사용 중이므로 동일한 접지인 물리 핀 9로 변경했다. 전원 차단 상태의 양쪽 배선 사진을 `docs/assets/hardware/ir-modules/`에 보존했다.

이 시점에는 물리 배선만 완료됐으며 Raspberry Pi의 GPIO/IR 수신 설정은 아직 변경하지 않았다. 다음 순서는 전원 투입과 정상 부팅을 읽기 전용으로 확인한 뒤, 별도 승인을 받아 Linux 수신 설정을 적용하는 것이다.

### 수신기 연결 후 첫 부팅 확인

사용자가 전원을 켠 뒤 SSH로 읽기 전용 상태를 확인했다. Pi는 약 1분 전에 정상 부팅됐고 systemd 전체 상태는 `running`이었다. 기존 `aircon-controller` 사용자 서비스는 `enabled` 및 `active`, 포트 8001 리스너는 1개였으며 Tailscale 주소의 `/health`가 HTTP 성공과 `status=ok`를 반환했다. 수신기 연결이 기존 원격 제어 환경의 부팅과 서비스에 영향을 주지 않았다.

`pinctrl get 17` 결과 GPIO17은 입력이며 현재 논리값이 HIGH였다. 약 38kHz 복조 IR 수신기는 신호가 없을 때 일반적으로 HIGH이고 IR 버스트 수신 시 LOW 펄스를 내므로, 이 결과는 수신기 전원과 OUT 배선이 동작할 가능성을 지지한다. 다만 아직 실제 리모컨을 눌러 에지를 측정하지 않았으므로 수신 성공으로 확정하지 않는다. `gpio-ir` Device Tree overlay는 아직 설정되지 않은 상태임도 확인했다.

### 블로그용 터미널 증빙 보존 방식

사용자 요청에 따라 이후 중요한 터미널 단계는 명령과 결과를 텍스트 원본으로 남기고, 블로그에 바로 사용할 수 있는 PNG로 함께 렌더링한다. 실시간 터미널 창을 몰래 캡처하는 방식은 사용하지 않으며, 비밀번호·인증 키·사설 IP 등 민감 정보는 텍스트와 이미지에 포함하지 않는다. 실제 화면 캡처가 아니라 검증된 출력으로 다시 만든 이미지는 상단에 `SANITIZED TERMINAL RECORD`라고 표시해 출처를 구분한다.

첫 증빙으로 GPIO17용 `gpio-ir` 설정 추가 명령과, `/boot/firmware/config.txt` 55번 줄에 설정이 정확히 한 번 존재한다는 읽기 전용 검증 결과를 `docs/assets/terminal/01-gpio-ir-overlay-config.txt`와 PNG에 보존했다. `sudo` 비밀번호 값은 기록하지 않았다.

### gpio-ir 적용 후 재부팅 검증

사용자가 `sudo reboot`를 실행한 뒤 다섯 번째 3초 간격 SSH 확인에서 Pi가 다시 응답했다. 부팅 직후 systemd는 `running`, `aircon-controller` 서비스는 `active`였고 Tailscale 주소의 `/health`도 정상 응답했다. 따라서 GPIO 오버레이 추가와 재부팅이 기존 포트 8001 서비스 자동 복구를 깨뜨리지 않았다.

`/boot/firmware/config.txt`의 `dtoverlay=gpio-ir,gpio_pin=17`을 재확인했고, GPIO17은 pull-up 입력·대기값 HIGH로 표시됐다. `/dev/lirc0`가 `root:video`, 권한 `crw-rw----`로 생성됐으며 `gpio_ir_recv` 커널 드라이버가 로드됐다. `ir-ctl --features`는 이 장치가 raw IR 수신과 디코딩된 스캔코드 보고를 지원하고 송신은 지원하지 않는다고 확인했다. 즉, HW-477용 Linux 수신 장치 구성이 완료됐고 다음 단계는 실제 리모컨 펄스 캡처다.

첫 진단에서 `lsmod` 결과를 골라내기 위해 사용한 원격 `awk` 식이 Windows PowerShell·SSH·원격 셸의 중첩 인용 과정에서 손상돼 구문 오류를 냈다. 장치 생성과는 무관한 보조 출력 오류였으며, 복잡한 `awk`를 제거하고 `grep`과 `cut`으로 다시 확인해 `gpio_ir_recv` 로드를 검증했다. 성공 결과는 `docs/assets/terminal/02-ir-device-after-reboot.txt`와 PNG로 보존했다.

### 첫 실제 리모컨 신호 수신 성공

사용자가 기존 에어컨 리모컨을 HW-477에서 약 5–10cm 떨어진 곳에 두고 에어컨 반대 방향으로 향한 뒤 온도 올림 버튼을 한 번 눌렀다. 20초 제한으로 실행한 `ir-ctl --receive --device=/dev/lirc0`에서 200개의 pulse/space 타이밍 토큰이 수신됐다. `timeout`이 관측 창을 끝내면서 종료 코드는 1이었지만 그 전에 유효 데이터가 출력됐으므로 수신 실패가 아니다.

측정된 데이터 펄스 중앙값은 약 546µs, 짧은 공백은 약 517µs, 긴 공백은 약 1611µs였다. 약 4.3ms 펄스와 4.3ms 공백으로 시작하는 48비트 프레임이 두 번 들어왔으며 두 프레임의 비트열은 같았다. MSB 우선으로 단순 묶은 관측 바이트는 `b2 4d 3f c0 10 ef`이고, 각 두 바이트가 보수 관계인 패턴도 보였다. 이 값은 분석 편의를 위한 관측 표현이며 프로토콜명이나 실제 필드 의미는 아직 확정하지 않는다. 복조 수신기로 반송파 자체를 측정한 것도 아니므로 38kHz는 모듈의 명목 대역으로만 기록한다.

원본 compact 출력, `ir-ctl` 송신용 pulse/space 변환 파일과 메타데이터를 `signals/remote-16214-15597/`에 저장했다. 블로그용 터미널 증빙은 `docs/assets/terminal/03-first-ir-capture.txt`와 PNG로 남겼다. 다음에는 리모컨 LCD 전체 상태를 사진으로 기록한 뒤 동일 상태를 최소 3회 캡처해 반복성을 비교한다.

사용자는 최종적으로 리모컨의 모든 신호를 확보해야 한다는 요구를 확인했다. 에어컨 리모컨이 전체 상태 패킷을 보내는 경우 온도·풍량·모드·풍향·옵션의 단순 조합 수가 매우 커지므로, 모든 조합을 원시 파일로 수집하는 대신 한 상태 요소씩 바꿔 비트 필드와 체크섬을 해독하고 조합을 생성하는 전략을 선택했다. 해독하지 못한 기능만 원시 프리셋으로 보완한다.

이어 사용자가 실제 리모컨 앞면 사진을 제공했다. 자동·냉방·제습 모드, 온도 내림·올림, 운전/정지, 풍량선택, 풍향선택, 풍향고정, 경제운전, 예약선택·취소, LED, 쾌속냉방, 리셋·잠금 핀홀을 확인했다. LCD 풍량 표시는 송풍·강·중·약으로 인쇄돼 있다. 실제 버튼 기준의 전체 수집표와 반복 횟수, 완료 조건을 `docs/plans/ir-signal-capture-matrix.md`에 정리했다.

사용자는 앞면 사진이 첫 온도 올림 캡처 직후 상태 그대로임을 확인했다. 이에 `temp-up-test-01`의 최종 상태를 `냉방 18℃ / 강풍`으로 확정하고 메타데이터를 갱신했다. 사진에 표시되지 않는 전원·풍향 상태와 버튼을 누르기 전 상태는 추측하지 않고 미확정으로 유지했다.

### 두 번째 캡처: 냉방 18℃에서 17℃로 온도 내림

첫 20초 캡처 시도는 사용자 버튼 입력과 관측 창의 타이밍이 맞지 않아 데이터 없이 종료됐다. 재시도에서는 90초 제한과 `ir-ctl --one-shot`을 사용해 먼저 수신 대기 상태를 만든 뒤 사용자가 온도 내림 버튼을 한 번 눌렀고, 메시지 수신 즉시 종료 코드 0으로 완료됐다. 이후 사용자가 LCD가 17℃로 바뀌었음을 확인했다.

두 번째 신호도 동일한 48비트 프레임이 두 번 반복됐고 관측 바이트가 `b2 4d 3f c0 10 ef`로 첫 캡처와 비트 단위로 완전히 같았다. 서로 다른 온도 최종 상태라고 기록된 두 캡처가 같은 결과를 낸 것은 예상 밖이다. 첫 시험에서 실제로 누른 버튼의 방향이 기록과 달랐거나, 이 리모컨이 전체 상태가 아닌 상대 버튼 명령을 보내는 구조일 가능성이 있다. 17℃에서 온도 올림을 눌러 18℃로 돌아가는 신호를 다음 비교 대상으로 정했다.

세 번째로 17℃에서 온도 올림 버튼을 한 번 캡처했다. 신호는 정상 수신됐고 두 프레임도 서로 일치했지만, 관측 바이트가 다시 `b2 4d 3f c0 10 ef`로 온도 내림 신호와 완전히 같았다. 따라서 단순히 첫 캡처의 버튼 방향만 잘못 기록됐다는 설명으로는 부족하다. 전혀 다른 기능인 풍량선택을 다음에 캡처해 모든 버튼에서 같은 공통 프레임만 보이는지 확인하고, 필요하면 rc-core 수신 timeout을 늘려 현재 잘리는 후속 프레임이 있는지도 시험한다.

사용자가 세 번째 캡처 후 LCD가 18℃로 바뀌었음을 확인해 최종 상태 메타데이터를 확정했다.

### 네 번째 캡처: 풍량선택으로 약풍 전환

사용자가 강풍에서 풍량선택을 한 번 눌러 LCD 풍량 화살표가 사라지는 상태로 전환했지만 첫 입력은 수신 대기 타이밍보다 빨라 캡처하지 못했다. 사용자는 이 무표시 상태 다음이 약풍이라고 설명했고, 이어진 풍량선택 입력은 정상 캡처됐다. 캡처 후 LCD가 약풍임을 사용자에게 확인했다. 무표시 상태의 정확한 의미는 자동풍량 후보로 남긴다.

풍량선택 신호는 동일한 48비트 프레임을 두 번 보냈고 관측 바이트가 `b2 4d 9f 60 10 ef`였다. 온도 조절의 `b2 4d 3f c0 10 ef`와 비교하면 0부터 센 비트 16, 18, 24, 26이 달랐다. 따라서 수신기가 모든 버튼을 같은 값으로 읽는 문제는 아니며, 적어도 풍량선택과 온도 조절 명령은 구분된다. 다음에는 약풍에서 중풍으로 한 단계 더 순환시켜 풍량선택 코드가 상태와 무관한 상대 명령인지 확인한다.

### 다섯 번째 캡처: 약풍에서 중풍

약풍에서 풍량선택을 한 번 눌러 중풍으로 바뀐 것을 사용자에게 확인했다. 관측 바이트는 `b2 4d 5f a0 10 ef`로, 약풍의 `b2 4d 9f 60 10 ef`와 달랐다. 따라서 풍량선택은 동일한 상대 순환 코드를 보내는 것이 아니라 선택 후의 풍량 상태를 패킷에 포함한다. 다음 중풍→강풍 캡처가 `b2 4d 3f c0 10 ef`라면 3·4번째 바이트가 풍량 상태 필드라는 가설을 강하게 지지한다.

### 여섯 번째 캡처: 중풍에서 강풍

중풍에서 풍량선택을 한 번 눌러 강풍으로 바뀐 것을 확인했다. 관측 바이트는 예상대로 `b2 4d 3f c0 10 ef`였으며, 앞선 온도 내림·올림 캡처와도 같았다. 현재 자료에서는 약풍 `9f/60`, 중풍 `5f/a0`, 강풍 `3f/c0`로 3·4번째 바이트가 풍량 상태와 함께 변한다. 온도 조절 캡처에서 온도값이 달라도 코드가 같았던 것은 두 캡처 모두 강풍 상태였기 때문일 가능성이 커졌다. 강풍 다음 무표시 풍량 상태를 캡처해 풍량 필드 가설을 한 단계 더 검증한다.

### 일곱 번째 캡처: 강풍에서 무표시 풍량

강풍에서 풍량선택을 한 번 눌렀고 사용자가 LCD 풍량 화살표가 사라졌음을 확인했다. 관측 바이트는 `b2 4d bf 40 10 ef`였다. 이로써 풍량 상태 후보 네 가지가 무표시 `bf/40`, 약 `9f/60`, 중 `5f/a0`, 강 `3f/c0`으로 분리됐다. 무표시는 풍량 순환상 강 다음·약 이전에 있으므로 자동풍량으로 추정하지만, 정확한 명칭은 추가 확인 전까지 후보로 표시한다.

### 여덟 번째 캡처: 자동풍량 후보에서 18℃→17℃

풍량 화살표가 없는 상태를 유지하며 온도 내림을 한 번 눌렀고 사용자가 LCD 17℃를 확인했다. 관측 바이트는 `b2 4d bf 40 00 ff`였다. 직전 18℃·동일 풍량의 `b2 4d bf 40 10 ef`와 비교하면 풍량 바이트 `bf/40`은 유지되고 5·6번째 바이트만 `10/ef`에서 `00/ff`로 바뀌었다. 따라서 풍량과 온도 필드가 분리되며, 17℃=`00`, 18℃=`10`이라는 온도 인코딩 가설을 세웠다. 다음 17℃→18℃ 반복 캡처로 동일 전환을 재검증한다.

### 아홉 번째 캡처: 자동풍량 후보에서 17℃→18℃

동일한 무표시 풍량 상태에서 온도 올림을 한 번 눌러 LCD 18℃를 확인했다. 관측값은 예상한 `b2 4d bf 40 10 ef`와 정확히 일치했다. 이에 3·4번째 풍량 필드와 5·6번째 온도 필드, 17℃=`00/ff`, 18℃=`10/ef` 가설을 왕복 캡처로 검증했다. 다음 19℃ 캡처에서 `20/df`가 나오는지 확인해 1℃당 상위 니블 1단계 증가 규칙을 시험한다.

### 열 번째 캡처: 자동풍량 후보에서 18℃→19℃

동일한 풍량 상태에서 온도 올림을 한 번 눌러 LCD 19℃를 확인했다. 관측값은 단순 선형 증가로 예상했던 `20/df`가 아니라 `b2 4d bf 40 30 cf`였다. 신호는 48비트 동일 프레임 두 번으로 정상 수신됐고, 마지막 바이트가 앞 바이트의 보수인 구조도 유지됐다.

이 결과는 오류라기보다 그레이 코드와 일치한다. `(온도-17)`을 기준으로 17℃의 0은 그레이 코드 0, 18℃의 1은 1, 19℃의 2는 3이므로 실측 상위 니블 `0, 1, 3`을 정확히 설명한다. 그레이 코드는 인접 상태 사이에서 한 비트만 바뀌는 인코딩이다. 이 가설이면 다음 20℃는 오프셋 3의 그레이 코드 2이므로 `20/df`가 나와야 한다. 20℃를 실측해 단순 증가 가설을 폐기하고 그레이 코드 가설을 확정할지 판단한다.

### 열한 번째 캡처: 자동풍량 후보에서 19℃→20℃

다음 수신 대기를 시작한 직후 사용자가 온도 올림을 눌렀고, 이후 LCD가 20℃임을 확인했다. 관측값은 `b2 4d bf 40 20 df`로 직전 단계에서 예측한 값과 정확히 일치했다. 이로써 5번째 바이트 상위 니블이 `(온도-17)`의 이진 그레이 코드이고 6번째 바이트가 그 보수라는 온도 인코딩 규칙을 확정했다.

규칙을 해독했으므로 남은 모든 온도 조합을 각각 원시 캡처할 필요는 없다. 대신 실제 최고 온도 경계를 확인하고, 생성한 경계값과 대표 중간값을 송신 단계에서 검증한다. 다음 캡처부터는 정보량이 더 큰 운전 모드 필드로 이동한다.

### 열두 번째 캡처 묶음: 운전 모드 4개 연속 수집

수집 속도를 높이기 위해 원격에서 `ir-ctl --one-shot`을 네 번 연속 실행하고 사용자가 각 버튼 사이에 약 2초 간격으로 운전선택을 눌렀다. 사용자 확인 순서는 제습 → 송풍 → 자동 → 냉방이며 온도 17℃·강풍을 기준으로 했다. 네 신호 모두 199개 타이밍 토큰과 동일한 48비트 프레임 2회를 포함했다.

- 제습: `b2 4d 1f e0 04 fb`
- 송풍: `b2 4d 3f c0 e4 1b`
- 자동: `b2 4d 1f e0 08 f7`
- 냉방: `b2 4d 3f c0 00 ff`

냉방·제습·자동의 5번째 바이트 하위 니블은 각각 `0/4/8`이지만, 3번째 바이트도 모드에 따라 `1f`와 `3f`로 바뀌었다. 송풍은 마지막 바이트쌍이 `e4/1b`인 특수 상태다. 즉 현재 패킷은 단순히 온도·풍량·모드가 완전히 독립된 바이트에 있는 구조라기보다 모드별 허용 상태가 함께 인코딩되는 것으로 보인다. 원시 파일 네 개와 메타데이터, 블로그용 통합 터미널 기록을 보존했다.

### 열세 번째 캡처 묶음: 운전/정지 OFF·ON

냉방 17℃·강풍에서 운전/정지를 두 번 눌러 OFF와 ON을 연속 수집했다. OFF는 `b2 4d 7b 84 e0 1f`, ON은 `b2 4d 3f c0 00 ff`였다. ON 값은 앞서 운전 모드 순환 마지막에서 얻은 냉방 17℃·강풍 값과 정확히 일치한다.

따라서 이 리모컨은 동일한 토글 코드를 보내는 방식이 아니라 OFF 전용 패킷과 현재 설정을 포함한 운전 패킷을 구분한다. 향후 API도 `POWER_TOGGLE`이 아니라 명시적 `POWER_OFF`와 원하는 운전 상태 전송으로 설계할 수 있다. 다만 사용자는 두 번의 버튼 입력 완료를 확인했지만 LCD의 꺼짐·복귀 모습은 별도로 문장 확인하지 않았으므로 메타데이터에 그 구분을 남겼다.

### 열네 번째 캡처 묶음: 경제운전·쾌속냉방

경제운전 두 번과 쾌속냉방 두 번을 연속 수집했다. 처음에는 각각 ON/OFF가 될 것으로 예상했지만 신호 구조가 그 가정과 달랐다. 경제운전 첫 입력은 특수 프레임 `b2 4d e0 1f 03 fc` 1회 뒤 냉방 17℃·무표시 풍량 후보 코드 `b2 4d bf 40 00 ff`를 2회 보낸 총 3프레임 메시지였다. 두 번째 입력은 뒤의 상태 프레임만 2회 보냈다.

쾌속냉방은 두 입력 모두 `b5 4a f5 0a a2 5d`를 2회 보냈다. 기존 일반 상태 패킷과 시작 바이트가 다르지만 모든 바이트쌍의 보수 관계는 유지된다. 따라서 원시 데이터는 ON/OFF로 잘못 명명하지 않고 1차·2차 입력으로 보존했다. LCD에서 실제로 어떤 표시·온도·풍량 변화가 있었는지 사용자 확인을 받아 의미를 보강해야 한다.

사용자가 뒤이어 LCD 동작을 확인했다. 경제운전 첫 입력에서는 강풍 화살표만 사라지고 냉방·17℃는 유지됐으며 옵션 아이콘은 나타나지 않았다. 이미 무표시 상태에서 두 번째로 눌렀을 때는 추가 변화가 없었다. 무표시 상태에서 풍량선택을 누르면 약풍부터 시작하므로 풍량 무표시는 자동풍량 계열로 보는 것이 자연스럽다. 첫 경제운전의 3프레임은 특수 동작 프레임 뒤에 변경 결과 상태를 두 번 통지하는 구조로 해석한다.

쾌속냉방은 두 입력 모두 LCD에 아무 변화가 없었다. 매번 동일한 별도 패킷을 보내므로 리모컨이 ON/OFF 상태를 추적하는 토글이 아니라, 에어컨 본체가 즉시 처리하는 명령으로 분류한다. 이 의미를 네 메타데이터에 반영했다.

### 열다섯 번째 캡처 묶음: LED·풍향고정

LED 두 번과 풍향고정 두 번을 연속 수집했다. LED는 두 입력 모두 `b5 4a f5 0a a5 5a`를 두 프레임 보냈다. 쾌속냉방의 `b5 4a f5 0a a2 5d`와 앞의 두 바이트쌍이 같아 별도 즉시 명령 계열로 묶을 수 있다.

풍향고정은 두 입력 모두 `b2 4d 0f f0 e0 1f`였지만, 기존 상태 패킷처럼 두 번 반복하지 않고 48비트 프레임 한 번만 보냈다. 같은 버튼을 다시 눌러도 동일해 풍향고정 역시 리모컨 내부 ON/OFF 상태를 구분하지 않는 즉시 명령으로 보인다. LCD 변화는 사용자에게 별도로 확인받기 전까지 미확정으로 기록한다.

사용자는 LED 버튼이 에어컨 본체의 표시 LED를 토글하는 기능으로 보인다고 설명했다. 두 입력이 동일 패킷이고 리모컨 LCD가 결과 상태를 추적하지 않는 점이 이 해석과 일치한다. 다만 본체를 향해 송신해 실제 LED가 켜졌다 꺼지는 것은 아직 검증하지 않았으므로 사용자 추정과 송신 검증 대기로 구분했다.

### 열여섯 번째 캡처 묶음: 풍향선택 스윙 토글

풍향선택을 네 번 연속 수집했고 네 입력 모두 `b2 4d 6b 94 e0 1f`를 동일한 48비트 프레임 두 번으로 보냈다. 사용자는 첫 입력에서 본체 날개가 계속 움직이기 시작하고 두 번째 입력에서 현재 위치에 멈추는 것을 확인했다. 따라서 풍향선택은 본체 상태에 따라 스윙 시작과 정지를 번갈아 수행하는 무상태 토글 명령이다. 세 번째·네 번째도 같은 패킷임은 확인했지만 본체 결과는 별도 문장 확인이 없으므로 메타데이터에서 추론으로 구분했다.

### 예약 기능 재조사와 제조사 설명서 확인

예약선택의 첫 동작을 보기 위해 15초 동안 IR 수신을 열었지만 출력이 한 건도 없었다. 사용자는 이 시험에서 얻은 내용을 지우고 조작 규칙과 제조사 설명서를 기준으로 다시 진행하자고 요청했다. 저장된 신호 파일은 원래 없었으며, 빈 시험 결과도 예약 캡처로 보존하지 않았다.

사용자 관찰에 따르면 예약선택 첫 입력은 0.0h 편집 화면을 열고, 추가 입력마다 10h까지 0.5h씩, 이후 24h까지 1h씩 증가한다. 24h 다음은 0.0h로 돌아간다. 0.0h에서 입력을 멈추면 약 1초 뒤 표시가 사라지고, 다른 값에서는 TIMER ON이 유지된다. 예약취소 버튼은 TIMER OFF 시간을 같은 규칙으로 설정하며 켜짐·꺼짐을 동시에 둘 수 있다.

제공된 Carrier CS-A Series 설명서 32쪽 중 리모컨 관련 PDF 21–26쪽을 텍스트 추출하고 이미지로 렌더링해 확인했다. 설명서의 TIMER ON/OFF 시간 증가와 취소 규칙은 사용자 관찰과 일치했다. 또한 예약 설정 시 리모컨을 본체로 향하게 두라는 주의사항과 미수신 시 약 15분 지연 가능성이 있어, 리모컨이 카운트다운 후 운전·정지 신호를 보내는 구조로 판단했다. Raspberry Pi 구현에서는 예약 버튼 신호를 복제하지 않고 서버 스케줄러가 명시적 ON/OFF 패킷을 실행하도록 결정했다. 상세 근거는 `docs/references/carrier-cs-a-series-manual.md`에 정리했다.

### TIMER ON 커밋 패킷 발견과 가설 수정

리모컨을 리셋한 뒤 12초 수신창에서 0.0h와 1.0h 설정을 시험했지만 출력이 없었다. 그러나 SSH 명령 호출이 사용자 안내 전에 약 10초를 소비했기 때문에 실제 조작 시점에는 관측창이 거의 끝나 있었다. 이는 예약 무신호를 입증하는 실험이 아니며 결과를 저장하지 않았다.

60초 원샷 수신으로 다시 시험했다. 사용자가 TIMER ON 1.0h에서 예약선택을 한 번 눌러 1.5h로 만들고 약 1초 기다리자 `b2 4d 3f c0 03 05`가 동일한 두 프레임으로 들어왔다. 따라서 정확한 동작은 버튼 입력 중 로컬 편집, 0이 아닌 값에서 약 1초 정지 시 예약 커밋 패킷 전송이다.

5번째 바이트 `03`은 0.5h 세 단계와 일치하고, 마지막 `03 05`는 보수쌍이 아니다. 앞선 리모컨 내부 카운트다운 전용 가설을 폐기하고 예약시간을 본체에 전달하는 패킷 구조로 수정했다. 웹 기능은 여전히 Pi 서버 스케줄러를 기본으로 하되, 리모컨 호환을 위해 예약 패킷 인코딩도 해독한다.

추가로 TIMER ON 2.0h·2.5h와 TIMER OFF 값을 네 번 연속 수집하려고 원샷 대기를 열었다. 사용자는 실제 제품에서 예약 시각을 Raspberry Pi가 관리하고 이미 확보한 ON/OFF 패킷을 보내면 예약 프로토콜 전체 해독이 불필요하다고 지적했다. 이 판단이 웹 예약 조회·취소·재부팅 복구·실행 로그 요구에도 더 적합하므로, 버튼 입력 전에 수신 루프를 중단했고 추가 데이터 파일은 생성하지 않았다.

TIMER ON 1.5h 패킷은 프로토콜 연구와 블로그 자료로 유지한다. 제품 예약 기능은 Pi가 예약을 영속 저장하고 실행 시점에 명시적 운전 상태 또는 OFF를 전송하도록 확정했다. 결정 근거는 `docs/decisions/0004-server-side-scheduling.md`에 별도로 남겼다.
