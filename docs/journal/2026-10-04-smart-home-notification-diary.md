# 2026-10-04 스마트홈 알림 일기

기록 날짜: 2026년 10월 4일 일요일, 한국시간.
오늘은 앞서 만든 A50 서버와 가족 앱의 기록을 읽으며 블로그 1\~9편과 따라 하기 자료를 정리했다. 작업하면서 생긴 실패도 지우지 않고 남겼다. 이제부터는 대화할 때마다 그날의 스마트홈 알림 일기를 이어 쓰기로 했다.
## 먼저, 처음 보는 사람도 따라갈 수 있게 정리했다
글만 읽고 명령어를 실행하려면 PC에 무엇을 깔아야 하는지, 어느 폴더에서 실행하는지부터 알아야 했다. 시작 안내에 PC 도구, 코드 위치와 본인 값으로 바꿀 항목을 모았다. 각 편에도 준비할 것, 실행 순서, 정상일 때 보이는 결과와 다음 편으로 넘어가는 기준을 넣었다.
최신 서버와 앱 0.4.0을 한 번 설치하는 흐름으로 맞췄다. 예전 화면을 보고 옛 버전을 차례대로 설치해야 한다고 생각하지 않게 했다. Pi 연결도 이미 있는 센서 기록을 보내는 단계라고 풀었다. 센서 프로그램 자체를 처음부터 만드는 글과는 구분했다.
공개 코드에 남아 있던 내 접속 대상과 사용자명은 비공개 로컬 설정으로 옮겼다. 따라 만드는 사람은 자신의 장비 정보를 넣도록 예시와 준비 도구를 만들었다. 기존 설정이 있으면 덮어쓰지 않게 했다.
## 새 폴더에 풀어보니 빠진 파일이 있었다
따라 하기 ZIP을 새 폴더에 풀고 독립적인 Python 환경에서 실행해봤다. 처음에는 코드 형식을 확인하는 도구가 지적한 부분을 고쳤다. 그다음 새 환경의 시험에서 HTTPS 통로 프로그램을 찾지 못하는 오류가 나왔다.
내 작업 폴더에는 파일이 있었지만, ZIP 목록에 `services/central-tunnel`이 빠져 있었다. 필요한 소스를 묶음에 넣은 뒤 같은 독립 환경에서 다시 실행했다. 117개 시험이 통과했고 2개는 Windows에서 실행하지 않는 Linux 파일 연결 시험이라 건너뛰었다. 도구 4개의 도움말도 열렸다.
첫 실패 자료와 다시 통과한 자료를 모두 남겼다. 위 과정은 오늘 날짜의 작업일지와 실제 실행 기록 366\~369를 읽어 정리한 내용이다. 노션에 옮기면서 같은 시험을 다시 실행한 것은 아니다. 새 휴대폰과 새 Firebase 프로젝트로 전체 과정을 끝까지 다시 해본 결과도 아직 없다.
## 글을 내 말투로 다시 썼다
설명은 있어도 직접 해본 글처럼 읽히지 않는 부분이 있었다. 어려운 말보다 왜 시작했고 어디서 막혔는지부터 보이게 바꾸고 싶었다.
기존에 확인한 [내 GPIO 버튼 글](https://kksp12y.tistory.com/230), [액자를 만든 글](https://kksp12y.tistory.com/100), [Pi OTG를 다시 시도한 글](https://kksp12y.tistory.com/126)의 흐름을 참고했다. 1\~9편과 목차를 “\~했다”, “\~해보자” 중심으로 다시 썼다. “검증했다” 같은 표현 대신 무엇을 확인했는지 적었다.
옛 작업 기록을 읽고 다음 장면을 원고에 넣었다.
- 1\~2편에는 SSH는 됐지만 무선 디버깅은 끊겼던 일, 드래그 잠금화면에서 멈췄던 일과 앱을 정리해도 전체 여유 메모리는 늘지 않았던 결과를 넣었다.
- 3\~7편에는 Google 로그인과 가족 권한의 차이, 서버 주소 연결, 실제 알림 수신과 Pi 기록 조회를 차례대로 풀었다. 서버의 전송 성공과 폰의 수신을 같은 것으로 쓰지 않았다.
- 8\~9편에는 이해하기 어려웠던 등록 충돌 안내, 휴대폰별 알림 선택, 버튼을 누르면 맨 위로 올라가던 문제와 스크롤 위치를 기억하도록 고친 과정을 넣었다.
이 문제들이 오늘 새로 생겼다는 뜻은 아니다. 앞서 겪었던 과정을 오늘 원고에 다시 풀어 쓴 것이다. 실제로 안 해본 결과를 넣어 경험처럼 꾸미지는 않았다.
## 사진과 표를 넣고 실제로 열어봤다
원고와 함께 HTML 미리보기도 만들었다. 내 블로그처럼 표 머리행을 청록색으로 맞췄다. Chrome에서 2편의 표와 본문 간격을 봤고, 8편의 실제 휴대폰 화면 3개가 모두 열리는 것도 확인했다. 폰 사진은 너무 크게 늘어나지 않게 폭을 줄였다.
볼드 표시 안의 따옴표 때문에 버튼 이름에 별표가 그대로 보이는 부분도 있었다. 강조할 버튼 이름과 따옴표를 정리한 뒤 다시 열어봤다.
명령어는 건드리지 않았다. 주요 9편의 코드 묶음 38개가 수정 전과 같았고, 도구 명령 49개의 참조 파일이 있었다. 표는 총 20개다. 목차 진입 페이지를 포함한 미리보기 21개와 내부 파일 링크 86개도 확인했다.
## 개인정보와 묶음 파일을 다시 확인했다
본문에 실제 이메일이나 임시 서버 주소가 남지 않게 했다. 이전 오류 자료에 보이던 PC 사용자 폴더도 가렸고, 같은 TXT의 PNG를 다시 만들었다. 실제 오류와 실패 사실은 유지했다.
최종 읽기 자료의 그림 19개에는 위치정보 같은 숨은 사진 정보가 남아 있지 않았다. 텍스트에도 확인 대상인 실제 비공개 설정 값이 없었다. 다만 모르는 개인정보나 모든 이미지의 글자를 자동으로 찾아낸 결과라고 쓰지는 않는다.
바탕화면에는 다음 두 파일을 저장했다.
- `smart-home-reader-v0.4.0.zip`: 글, 필요한 코드와 공개용 화면을 묶었다. 183개 파일이고 기준 소스 181개가 실제 ZIP과 같았다.
- `A50-블로그-원고.zip`: 표와 사진 배치를 볼 수 있는 HTML 미리보기다. 압축을 전부 풀고 `index.html`을 열면 된다. 안내와 파일 목록까지 204개 파일이다.
기존 ZIP은 내용이 예상한 파일인지 확인한 뒤 임시 폴더에 따로 보관했다. 바탕화면 복사본도 원본과 같았다. 글과 자료는 로컬에 준비했다. 이번 원고를 티스토리에 게시하거나 자동 예약까지 한 것은 아니다.
## 15:05 · 날짜별 노션 일기를 기본으로 정했다
대화 중에 생긴 이슈, 해낸 일, 바꾼 것과 해결 과정을 매번 그날 일기에 쓰기로 했다. `AGENTS.md`에 이 규칙을 저장했다.
4일 항목에는 기존 작업일지가 있었고 “일기” 페이지는 없었다. 처음에는 4일 항목을 일반 페이지처럼 부모로 지정했다가 위치를 찾지 못하는 오류가 났다. 실제로는 접힌 항목이었다.
10월 일정에 일기 페이지를 먼저 만든 뒤 4일 안으로 옮겼다. 원래 위치에 같은 페이지를 둔 채 새로 추가하는 방식도 거절돼서, 기존 위치를 빼고 원하는 위치에 넣는 두 변경을 한 번에 적용했다. 다시 읽어 4일 아래에 들어간 것을 확인했다. 기존 작업일지와 다른 일정은 유지했다.
앞으로는 그날의 “일기 → 스마트홈 알림”을 먼저 읽고 이어 쓴다. 5일이 되면 5일로 넘어간다. 페이지가 없으면 만들고, 있으면 새로 만들지 않는다. 질문을 받거나 중요한 결과가 나올 때 기록하고, 긴 작업은 중간에도 남긴다.

## 21:47 · 티스토리 말투와 게시 형식을 다시 확인했다

원고를 그대로 블로그에 붙여 넣으려 했는데, 내 글과 다른 부분이 남아 있다는 이야기를 들었다. 문단은 들여쓰고 “~했다”로 쓰며, 부제목에는 숫자를 붙이지 않고 글 제목에도 “1편”, “2편”을 붙이지 않기로 했다. 부제목 바로 아래에는 줄을 넣는다는 기준도 다시 정했다.

[GPIO 버튼 글](https://kksp12y.tistory.com/230), [최근 에어컨 제어 글](https://kksp12y.tistory.com/249), [직접 만든 액자 글](https://kksp12y.tistory.com/100)을 다시 열어 읽었다. 액자 글은 이전 제작의 아쉬운 점부터 시작해 재료를 고른 이유, 조립 중 불편했던 점과 결과로 이어졌다. 표는 머리행이 청록색이고 재료와 스펙이 본문 안에 있었다. 최근 에어컨 글에서도 성공한 부분과 아직 확인하지 못한 부분을 나눠 적는 흐름을 확인했다.

읽은 글들의 실제 서식이 모두 같지는 않았다. 이번 원고는 사용자가 이번 대화에서 직접 말한 들여쓰기와 부제목 아래 줄 기준을 따른다. 표 색과 문장 끝만 맞춰서는 사용자의 작성 방식과 게시 요구를 충분히 반영한 것이 아니었다.

브라우저 화면 캡처는 두 번 모두 시간 초과로 저장하지 못했다. 본문과 표의 실제 문서 요소를 읽어 내용과 서식 값을 확인했다. 캡처가 준비됐다고 쓰지는 않는다.

게시용 원고는 티스토리 HTML 모드에 붙여 넣을 본문으로 준비해야 한다. 내 PC의 다른 파일을 열어야만 설명을 이해할 수 있는 링크는 없애고, 필요한 명령어·코드·결과와 오류 해결 방법을 글 안에 넣어야 한다. 사진도 로컬 경로를 그대로 넣으면 독자에게 보이지 않으므로 티스토리에 올린 사진 주소로 연결해야 한다.

이번 요청은 먼저 블로그를 다시 읽고 이해한 내용을 말하는 단계였다. 원고 전체와 ZIP을 새 형식으로 다시 만드는 일은 아직 하지 않았다. 실제로 하지 않은 시험을 경험처럼 꾸미지 않고, 개인정보를 가리는 기준도 그대로 유지한다.

## 21:54 · 게시용 원고를 바꾸기 시작했다

티스토리 작성 방식에 맞춰 원고를 고치기로 했다. 제목과 부제목의 번호를 빼고, 문단 첫 줄을 들여쓰며 부제목 바로 아래에 줄을 넣는다. 로컬 파일에 연결하던 설명과 실행 결과를 본문으로 옮기고, 티스토리 HTML 모드에 붙여 넣을 본문 파일을 준비한다.

기존 원고와 실제 실행 기록을 먼저 읽었다. 성공한 시험과 아직 남은 시험은 그대로 구분한다. 현재는 수정 중이며, 새 게시용 파일이나 사진이 티스토리에 올라간 상태는 아니다.

## 22:03 · 글 안에 필요한 설명과 실제 출력을 넣었다

원고 9개의 제목과 부제목 번호를 빼고 문단 첫 줄을 들여썼다. 각 부제목 바로 아래에 줄을 넣었다. PC에 Python·ADB·JDK를 준비하는 과정은 A50 접속 글에 넣었고, 따로 열어야 했던 문서 링크는 본문에서 없앴다.

화면을 끈 뒤 SSH가 된 결과, 재부팅 직후 시간 초과와 이후 다시 연결된 결과, 서버 재시작과 기록 유지, 통로 시작 오류와 실제 알림 수신 결과를 본문으로 옮겼다. 화면 확인 도구가 실패한 출력과 다시 통과한 출력도 함께 넣었다. 시험 내용이 실패했는데 명령 종료값은 0이었던 점을 같이 설명했다.

게시용 본문 HTML과 작성자용 사진 미리보기를 따로 만들었다. 첫 생성에서 본문 9개, 부제목 52개와 코드 묶음 49개를 확인했다. 본문 안의 클릭 링크와 로컬 사진 주소는 모두 없었다. 사진 13곳은 게시할 때 실제 사진을 넣도록 별도 파일과 배치 안내를 준비했다.

Chrome에서 알림 선택 글을 열어 문단의 17px 들여쓰기, 부제목 바로 다음의 가로줄과 청록색 표 머리행을 확인했다. 사진 3개도 모두 표시됐다. 문장이 어색하게 이어지는 부분은 다시 다듬고 있다. 티스토리 편집기에 실제로 붙여 넣거나 사진을 업로드한 결과는 아니다.

## 22:09 · 티스토리에 붙여 넣을 원고 묶음을 저장했다

원고 9개와 목차를 수정했다. 게시용 본문 HTML에는 문단 첫 줄 들여쓰기와 부제목 바로 아래 가로줄을 넣었다. 제목과 부제목 번호를 뺐고, 표 머리행은 청록색으로 맞췄다. Chrome에서 처음에는 표가 내용 너비만큼 좁게 보이는 부분을 발견해 표를 감싸는 방식을 바꿨다. 다시 열어 표 전체가 본문 폭으로 표시되는 것을 확인했다.

게시용 본문 9개의 클릭 링크와 로컬 사진 주소는 0개였다. 부제목 52개와 코드 묶음 49개를 확인했고, 기존 명령어 묶음 38개는 모두 수정 전과 같았다. HTML에서 복사할 코드가 원고와 같은 내용인지도 비교했다. 실제 부팅 파일과 집 권한 확인 코드, 화면 위치를 저장하는 코드 일부를 글 안에 넣었다.

작성자용 미리보기와 게시용 본문은 따로 뒀다. 제목 파일, 공개용 사진 13개와 사진 배치표, 따라 하기 코드 ZIP을 함께 준비했다. 코드 ZIP에는 177개 파일이 있었고, 게시용 묶음에는 총 46개 파일이 있었다. 알고 있는 비공개 설정 값이나 실제 이메일·임시 서버 주소가 본문에 없는지 확인했다. 사용한 사진에도 위치정보 같은 숨은 정보는 없었다.

묶음을 다시 만들자 파일 날짜 때문에 같은 내용의 압축 파일 비교값이 달라졌다. 압축 항목 날짜를 고정하고 두 번 다시 만들었더니 같은 파일이 나왔다. 첫 결과는 로컬에 따로 보관했고, 최신 `A50-티스토리-게시용.zip`을 바탕화면에 저장해 원본과 같은지 확인했다. 터미널의 한글 파일명도 처음에는 깨져 보여 출력 방식을 UTF-8로 맞췄다.

본문과 표·사진 배치를 확인한 화면 2개를 `docs/assets/blog/mobile-app/`에 저장했다. 마지막 생성과 파일 확인 출력은 터미널 기록 371의 TXT와 PNG로 함께 남겼다. 앞으로 같은 형식을 쓰도록 `AGENTS.md`에도 작성 기준을 적었다.

이번에는 원고와 자료를 준비했다. 실제 티스토리 편집기에 붙여 넣고 저장하는 과정과 사진·코드 ZIP 업로드는 아직 하지 않았다. 사진은 자동으로 올라가지 않으므로 본문을 붙인 다음 티스토리에서 직접 넣어야 한다. 실제 센서 알림과 다른 가족 계정의 수신, 장시간 운영처럼 아직 해보지 않은 시험은 원고에도 남겨뒀다.

## 22:31 · 블로그에 첫 글을 올리는 순서를 정리했다

준비한 원고를 지금 올리려고 해서, 게시용 묶음의 안내와 첫 글의 제목·본문·사진 위치를 다시 읽었다. 압축을 풀고 제목을 넣은 뒤, 본문 HTML을 메모장에서 복사해 티스토리 HTML 모드에 붙이는 순서를 안내하기로 했다. 사진은 기본 모드에서 따로 넣어야 한다.

첫 사진은 ‘화면을 끄고 다시 접속해봤다’에서 약 147초 뒤 연결이 돌아왔다는 문단 아래에 들어간다. 따라 하기 코드 ZIP은 ‘PC에 필요한 것부터 준비했다’의 자료 설명 옆에 첨부하도록 정리했다. 게시용 원고 전체 ZIP과 독자가 내려받을 코드 ZIP은 서로 다른 파일이다. 최신 게시용 묶음 안에 들어 있는 코드 ZIP을 사용한다.

글은 파일 이름의 01부터 09까지 차례대로 올린다. 파일 번호는 정리용이고 글 제목에 ‘1편’, ‘2편’을 붙이지 않는다. 세 번째 글에는 사진이 없다. 게시 전에 문단 들여쓰기, 부제목 아래 줄, 표·명령어와 사진, 코드 첨부가 보이는지 확인하는 순서도 안내했다.

실제 티스토리 업로드와 공개 완료는 아직 확인하지 않았다. 원고를 올렸다고 기록하지 않고, 사용자가 글을 올리는 데 필요한 안내를 정리한 단계로 남겼다.

## 22:35 · 소프트웨어 구조를 그림으로 정리하기 시작했다

전체 소프트웨어를 컴포넌트별로 나눠 A0 크기의 벡터 그림으로 만들기로 했다. 본문 글자는 약 12px를 기준으로 하고 GitHub의 `README.md`에도 그림을 넣는다. 실제 코드와 설치 문서를 먼저 읽어, Pi의 에어컨 제어와 A50의 가족 알림이 어디에서 이어지는지 확인하고 있다.

집마다 다른 Pi를 연결하는 방식, 가족 권한과 휴대폰별 알림 선택, Firebase 로그인과 FCM 전송을 구분해 그릴 계획이다. 아직 그림을 완성하거나 GitHub에 올린 상태는 아니다.

## 22:48 · 컴포넌트 그림과 A0 PDF를 만들었다

현재 코드를 읽어 전체 연결, 각 집의 Pi, A50 중앙 서버, 가족 Android 앱, 에어컨 제어, 집별 권한과 실행·복구를 그림으로 나눴다. 31개 상자와 30개 주요 연결을 그렸고, 상자에 연결한 코드 근거 50곳의 파일이 실제로 있는지 확인했다.

첫 생성에서는 좁은 상자에 글자가 넘쳐 도구가 중단됐다. 설명을 줄이고 상자 높이를 바꿨다. 영어 이름이 줄 사이에서 끊기는 곳도 있어 단어 단위로 줄을 바꿨다. 다시 만든 뒤에는 도구의 글자 범위 확인과 코드 형식 확인을 통과했다. 브라우저에서도 요약·상세 그림의 글자가 그림 바깥으로 나가는 곳이 없었다.

벡터 SVG 두 개와 A0 가로형 PDF 한 페이지를 만들었다. 본문은 SVG 좌표 기준 12px이며, README용 요약 그림은 축소해도 읽도록 16px로 따로 준비했다. PDF에서 한글 텍스트를 읽을 수 있었고 래스터 이미지는 없었다. `README.md`에 요약 그림과 펼쳐 볼 상세 그림을 넣고, 컴포넌트 설명·코드 위치·다시 만드는 방법을 `docs/architecture/README.md`에 적었다.

확인한 중요한 차이도 남겼다. 가족 앱은 현재 기록·알림용이고 에어컨 조작은 Pi 웹 화면을 쓴다. Pi 연결 서비스는 원본 DB를 읽기만 한다. 현재 집마다 활성 허브 한 대를 허용한다. 알림 대상과 전송 직전에 가족 권한을 확인하며, 온습도 최소 간격은 휴대폰 설치 전체에 적용된다.

GitHub 기본 브랜치에 다른 원고 작업이 섞이지 않게 이번 그림과 README 파일만 반영할 준비를 하고 있다. 아직 실제 GitHub 화면의 그림 표시까지 확인한 상태는 아니다. 새 기기 시험·서버 배포·서비스 재시작은 하지 않았다.

## 22:54 · GitHub README에 구조도를 올렸다

이번 아키텍처의 README·벡터 그림·PDF·모델·생성 도구 7개 파일만 GitHub `main`에 반영했다. 이전 원고 작업이나 접속 설정은 섞지 않았고, 현재 작업 브랜치와 다른 로컬 수정도 보존했다. 재시도 횟수는 첫 전송을 포함한 전체 시도 횟수라 그림의 ‘8회 재시도’를 ‘8회 시도’로 고쳐 다시 반영했다.

실제 GitHub README를 열어 요약 SVG와 A0 상세 SVG가 모두 불러와지는 것을 확인했다. 상세 그림을 펼쳐 본문 설명도 읽었다. 마지막 변경 뒤 페이지를 다시 열어 두 그림이 표시되는지 확인했다. GitHub 화면 캡처는 전체 화면과 잘라낸 영역 모두 시간 초과로 저장하지 못했다. 대신 로컬 벡터 미리보기 화면을 저장했고, 그 사진에 위치정보 같은 숨은 정보가 없는지 확인했다.

바탕화면의 ‘스마트홈-SW-아키텍처’ 폴더에는 A0 SVG·PDF·블로그용 PNG와 README 요약 SVG를 저장했다. 최종 PDF를 그림으로 열어 한글과 상자·화살표 배치를 다시 봤다. 실행 출력은 터미널 기록 372의 TXT와 PNG로 남겼다. 공개 그림과 설명에는 실제 계정 이메일·집 주소·인증키·기기 고유값을 넣지 않았다.

현재 구조와 남은 시험도 문서에 함께 적었다. 도식을 만든 것이 새 센서 시험이나 장시간 운영 성공을 뜻하지 않는다. 실제 물리 센서부터 다른 가족 휴대폰까지의 시험과 고정 서버 주소는 계속 남아 있다.
