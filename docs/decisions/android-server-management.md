# Android 시험 서버의 자동 관리와 정리 범위

작성일: 2026-10-02. 실제 복구 결과와 후속 실패는 당일 일지와 기록 97·103·104에서 확인한다.

## 사용자 요구

- 1편은 초기화·SSH·백그라운드·재부팅 복구를 한 편으로 묶는다.
- 2편은 운영 환경 정리와 실제 중앙 서버 구축이다.
- 휴대폰 동작에 필요한 구성은 제거하지 않는다.
- 사람이 매번 디버깅을 켜거나 주소·포트를 전달하는 과정부터 줄인다.

## 관리 경로

일반 서버 관리에는 공개키 SSH를 사용한다. 앱 제어와 Android 화면 캡처에는
페어링된 TLS 무선 ADB를 사용한다. ADB 전용 로컬 도구가 mDNS에서 기기를 찾고
모델·고유 식별 정보가 기존 확인값과 일치하는지 검증한 뒤 명령을 실행한다.
변하는 포트를 사람에게 매번 입력받지 않는다.

기기 선택 정보와 최근 접속 주소는 .deploy/a50/adb.json에만 보관하며 Git에서 제외한다.
여러 기기가 모호하게 일치하거나 실제 기기 식별 정보가 다르면 작업을 거부한다.
기기 미발견을 다른 임의 장비 접속이나 전체 포트 탐색으로 해결하지 않는다.

자동 발견은 무선 디버깅이 켜져 있다는 조건이 있다. 재부팅 후 이 조건이 유지되는지는
실물에서 검증한다. 일반 Termux SSH 권한으로 Android 시스템 설정을 바꿀 수 있다고
가정하지 않는다. 자동 접속과 Android의 디버깅 활성화 권한은 구분한다.

## Android 자체 복구 앱

포트 발견만 준비한 첫 시험에서는 ADB가 재부팅 뒤 240초 안에 돌아오지 않았다(97).
자체 관리 앱 com.aircon.a50manager를 로컬에서 빌드·서명해 설치하고 최초 ADB로
WRITE_SECURE_SETTINGS 권한을 부여했다. 앱은 Wi-Fi일 때 adb_wifi_enabled 하나만
복구하며 부팅 완료와 15분 주기의 Android 보조 작업을 사용한다. 예약 실행 시점은
Android가 조정할 수 있다. 일반 SSH 자동 시작은 Termux:Boot가 별도로 맡는다.

실물 재부팅 뒤 포트가 바뀐 ADB와 SSH가 수동 조작 없이 돌아왔다(103).
그러나 4분 뒤 후속 점검에서 ADB가 끊겼고 사용자가 Wi-Fi 허용 팝업을 확인했다(104).
초기 복구 성공을 지속 연결 성공으로 기록하지 않는다. Android의 Wi-Fi 신뢰 허용은
우회하지 않으며, 휴대폰에서 항상 허용을 저장한 뒤 재부팅·연결 유지 재검증이 필요했다.

항상 허용 뒤 재시험도 ADB 복구에 실패했다(105). 사용자가 같은 허용창이 반복된다고
보고했다. 실제 ADB 상태에서 신뢰된 접속 지점 1개가 있고 현재 접속 지점과 일치함을
확인했다. 부팅 로그에는 Expected keyStore, but got tag=null 오류와 Wi-Fi 미연결
시점의 활성화 거부가 있었다(107). 초기 파일이 비었는지, 제조사 동작이 관여했는지,
접속 지점 변경이 있었는지는 아직 확정하지 못했다. 오류만으로 근본 원인을 단정하지 않는다.

0.2.0은 접근성 서비스로 소유자가 이미 허용한 집 Wi-Fi의 시스템 무선 디버깅 허용창만
확인한다. 다른 네트워크와 일반 권한창은 처리하지 않는다. 네트워크 이름은 최초의
권한 보호된 구성으로 등록하며 공개 자료에서 제거한다. 서비스 설정은 기존 접근성
목록에 추가해 다른 설정을 보존한다. SSH로 비밀정보 없는 앱 상태를 읽을 수 있다.
기기 미발견 시 검증된 SSH로 앱을 깨우는 보조 경로를 구성했고 실제 자동 시험은 112다.

112도 240초 안에 ADB 복구에 실패했다. 서비스 상태를 SSH로 읽을 수 있었으나
wifi_adb=0, approval_state=SERVICE_CONNECTED였으며 허용창 처리를 확인하지 못했다.
화면을 켜는 사용자 시험을 요청했다. 실물 System UI APK를 SSH로 읽어 실제 컴포넌트와
문구·체크박스 ID를 확인했다(113). 0.3.0 소스에는 제한된 15초 화면 wake lock과
더 자세한 비밀정보 없는 상태를 추가하고 빌드·서명 검사를 마쳤다(114·115).
화면만 켜는 것으로는 복구되지 않았다. 0.4.0을 실제 설치하고 APK 체크섬 일치를 확인했다.
기존 접근성 서비스를 보존하면서 시스템의 여러 창을 조회하고 검사 대기의 반복 취소를
제거했다. 등록 Wi-Fi 이름과 접속 지점(BSSID)이 모두 정확히 일치하는 시스템 창만 처리한다.
이 값과 복구 난수 토큰은 비공개 설정에 보관하고 공개 기록에서 제거한다.
SSH는 Activity 시작 대신 토큰 보호 복구 수신기를 호출한다. 실제 수락 응답과 기기 검증으로
성공을 판단한다. TermuxAm의 수락 result=1과 종료 코드 1을 함께 처리한다.
실제 집 Wi-Fi 허용창 자동 확인과 화면 꺼짐 상태의 ADB 비활성화 후 9초 복구,
2분 SSH·ADB 유지에 성공했다(123·124). 정상 재부팅·지속성 검증은 별도 기록한다(125).
관련 없는 앱 정리는 계속 보류한다. 신뢰 파일 오류의 근본 원인 해결로 기록하지 않는다.

0.4.0의 첫 재부팅(125)은 사용자 드래그 잠금 해제 후에만 허용창 처리가 완료됐다.
따라서 완전 자동 부팅 결과로 사용하지 않는다. 사용자는 드래그 화면도 제거해 달라고
요청했다. 비밀번호 인자 없는 locksettings verify가 성공한 기기에서 set-disabled true를
적용하고 저장값 true를 확인했다(129). 관리 APK에 잠금 우회 기능을 추가하지 않았다.
PIN·패턴 설정은 건드리지 않았으며 잠금 없는 기기의 실제 재부팅 시험은 기록 130이다.
복구 요청 수락 뒤에도 연결 확인까지 제한된 횟수로 RPC를 재시도한다.
잠금 없음 적용 뒤 새 재부팅에서는 손대지 않고 새 포트의 ADB가 연결됐고,
저장된 잠금 없음 설정도 true였다. 재부팅 명령 뒤 5초 대기 후 자동 발견 대기는 131.7초였다. PC의 SSH RPC 없이 기기 부팅 복구로 자동 허용됐다(130).
이 결과는 기존 암호 없는 조건에서 드래그 화면 제거가 실제 자동 복구를 가능하게 했다는
근거다. 모든 네트워크·장시간·PIN 잠금 조건의 보장을 뜻하지 않는다.
130에서 5분 ADB 유지, 홈 화면에서 화면 꺼짐 2분 SSH·ADB를 모두 확인했다.
133의 최종 라이브 상태도 화면 꺼짐과 두 관리 경로의 정상 응답을 확인했다.
해당 집 Wi-Fi·충전·암호 없는 초기 운영 조건의 관리 복구를 완료로 처리한다.

이 작업은 요청 시 실행하는 접속 도구와 Android 부팅 복구에 관한 것이다.
Pi 자동 배포·상시 감시·클라우드 예약 실행은 포함하지 않는다.

## 앱 정리

Android 핵심 서비스, 홈·설정·키보드·설치 관리자, Wi-Fi·충전·전원 관리,
Google Play 기반 서비스, Termux·Boot, 관리 경로와 공용 의존 구성은 유지한다.
명확한 일반 앱만 실제 기기 정보를 근거로 선정하고 먼저 사용 중지한다.
사용 중지 전 상태와 복원 명령을 기록하고 SSH·화면·네트워크·부팅을 확인한다.

RAM free를 목표 수치로 정하지 않는다. available, 앱별 사용량과 실제 서비스
응답·지속성을 함께 비교한다. 캐시·zRAM을 무조건 비우거나 끄지 않는다.

## 2026-10-02 일반 앱 정리

2026-10-02 후속 앱 정리에서는 검토한 일반 앱 10개만 disable-user로 변경했다.
삭제·데이터 초기화·zRAM 해제·커널 스레드 종료는 하지 않았다.
System UI, 홈, 설정, 키보드, 설치·권한·네트워크 구성, GMS와 원격 관리 앱 등
보호 대상 28개의 활성 상태를 매 앱 적용 뒤 확인했다.

복원 기준은 최초 enabled=0 또는 1을 기록한 비공개 상태 파일이다.
기본 상태와 명시적 활성 상태를 구분해 각각 default-state와 enable로 돌린다.
활성 패키지 블록만 읽고 상시 앱·공용 라이브러리·공유 시스템 UID는 거부한다.
자기 이름 sharedUser는 실제 패키지-UID 목록에서 단독 사용까지 확인된 경우만 허용한다.
보호 검사는 6개 테스트와 기존 접속 검사 11개로 확인했다.

같은 부팅의 화면 꺼짐·충전 측정에서 선택 앱 PSS 약 192 MiB가 목록에서 사라졌지만,
전체 MemAvailable은 1482.8에서 1475.1 MiB로 변했다. 전체 메모리 절감은 확인되지 않았다.
낮은 CPU 사용과 D 상태 커널 작업 17개가 함께 관찰됐다. 높은 load average의
정확한 제조사 커널 원인은 미확정이며 이를 해결하려고 핵심 구성을 끄지 않는다.
실행·사진·측정 원문은 블로그 2편과 기록 135~140에 보존한다.
정리 후 재부팅에서 사용자 조작 없이 121.2초 만에 ADB가 복구됐고 SSH도 응답했다.
보호 대상 28개·대상 10개 상태가 유지됐으며 화면 꺼짐 2분의 ADB·SSH도 통과했다(141).

## 2026-10-02 중앙 서버 실행 기반

가구 인증·FCM 연동 전, 상태 확인용 독립 Python 서비스를 로컬 services/central-server에서
구현해 A50에 명시적으로 배포했다. Flask 3.1.3와 Waitress 3.0.2를 고정하고
Termux Python 3.14.6·SQLite 3.53.4에서 실제 실행했다. Waitress는 별도 컴파일을
요구하지 않지만 Flask의 MarkupSafe 의존성은 장비에서 빌드했다.

이 단계는 127.0.0.1:8001만 사용한다. 인증 없는 상태 확인 기반을 가구 연결 API로
외부에 열지 않는다. 로컬에서 DB 보존·누락 시 503·기존 스키마 거부·재시작 제한을
검증했다. FCM 발송 키·등록 계정·가족 데이터·Pi API는 변경하지 않았다.

소스 해시별 릴리스와 current 링크, 원격 파일 변경 거부와 기본 미리보기로 배포한다.
데이터·로그는 릴리스 외부에 보존한다. 아직 가상환경은 릴리스끼리 공유하므로
향후 의존성 변경 시 이전 버전 복구를 별도로 검토한다.

중앙 서비스만 runit으로 감독한다. 기존 SSH 부팅 파일·기존 sshd/ssh-agent의
down 상태를 보존했다. 5분 내 비정상 종료 5회는 기록 후 자동 중지하고 부팅도
이 표시를 유지한다. 재시작 제한은 로컬 검사, 실제 단일 프로세스 종료 복구는
장비에서 검증했다. 각 로그 1MiB+백업 3개, 부팅 로그 최근 100줄로 제한한다.

실제 준비 확인 8회/4클라이언트·무결성·영구 메타데이터 유지·체크섬 일치와
LAN 주소의 8001 미개방을 확인했다. 서버 RSS 약 35.9MiB는 초기 표본이며
전체 Android RAM이나 3~4가구 처리 성능을 뜻하지 않는다. 기록 143~148 참조.
정상 재부팅에서 사용자 조작 없이 122.0초 만에 관리 연결과 API가 복구됐고,
화면 꺼짐 2분 API·ADB·SSH와 DB 메타데이터·소스·기존 SSH 보존을 확인했다.
최종 배포 보호 검사 포함 12개 통과. 전체 실물 네트워크·장시간 운영은 미검증이다.
